# 02 依赖模型与接口契约

## 1. 现状：dependencies 只支持运行环境依赖

现有 `SkillDependencyKind = "npm" | "pip" | "uv" | "system"`（`packages/domain/src/skill-package.ts:66`），frontmatter 解析也只识别这四类（`packages/services/src/skills/dependencies.ts:3`），并要求**精确版本**、拒绝范围。它解决的是“脚本运行需要什么包/二进制”，**不支持 Skill 对 Skill 的依赖**。

## 2. 新增 skillDependencies

单独增加 `skillDependencies`，不要和软件包依赖混在一起。语义：

| 字段 | 说明 |
| --- | --- |
| `coordinate` | 稳定依赖身份，如 `github:eternityspring/shuohao-skills/skills/novel-outline`；**不能**用可重命名的显示名称 |
| `version` | 版本范围（作者声明），安装计划解析成确切 artifact digest |
| `placement` | `same_runtime` 或 `workflow` |
| `required` | 是否阻断（可选依赖可跳过，但需显式声明） |

- `same_runtime`：当前 Skill 会直接调用它，必须共置安装到同一 Runtime。
- `workflow`：只要求 Workflow 中存在一个可执行节点，不必装到当前 Runtime。
- 版本范围由作者声明，但**安装计划必须解析成确切 artifact digest**（与 0801 “版本号用于沟通、digest 用于执行”一致）。

```yaml
skillDependencies:
  - coordinate: github:eternityspring/shuohao-skills/skills/novel-outline
    version: "^1.1.0"
    placement: workflow
    required: true

  - coordinate: github:eternityspring/shuohao-skills/skills/novel-art
    version: "^1.1.0"
    placement: same_runtime
    required: true
```

### 为什么依赖身份用 coordinate 而不是显示名称

当前导入按名称做冲突处理，支持 `rename/replace/skip`（`packages/services/src/skills/import.ts:442`）。按名称关联依赖会产生歧义：两个工作区里同名 Skill 可能是不同实现，重命名后依赖即失效。`coordinate` 是内容寻址之外、稳定的逻辑坐标，解析时映射到当前工作区已导入的具体 artifact digest。

## 3. planSkillRollout 深模块

### Interface

```ts
planSkillRollout({
  rootArtifactDigest,
  targetScope: { workflowId } | { employeeIds } | { runtimeIds } | "all-compatible",
  dependencyMode: "required-only" | "include-optional",
}): SkillRolloutPlan
```

```ts
interface SkillRolloutPlan {
  planId: string;
  planDigest: string;              // 闭包 + runtime 集合 + policyVersion + 风险项 的哈希
  root: { artifactDigest: string; coordinate?: string };
  closure: Array<{
    coordinate: string;
    artifactDigest: string;         // 已锁定的确切 digest
    requestedVersion: string;
    placement: "same_runtime" | "workflow";
    required: boolean;
  }>;
  items: Array<{
    runtimeId: string;
    artifactDigest: string;
    revision: string;
    state: "ready" | "installing" | "pending";  // 去重后的结果
  }>;
  risks: RiskSummary;               // 汇总自各 artifact 的风险项
  requiredCount: number;
  readyCount: number;
  pendingCount: number;
}
```

### Implementation 统一完成

1. 解析传递依赖并检测循环（图内环路直接报 `skill_dependency_cycle`）。
2. 检测同名、版本范围冲突、Runtime 兼容冲突。
3. 将版本范围锁定为 artifact digest（复用现有 release-lock/artifact 解析链）。
4. 去除已经 `ready` 或正在安装的 `Runtime × Artifact`。
5. 生成 `Runtime × Artifact` 安装项（按 placement 映射 Runtime）。
6. 汇总风险，用户只批准一次完整计划（`skill_rollout_plan`）。
7. 幂等创建各 Runtime operation（下发到 daemon 队列）。
8. 必需目标全部 `ready` 后才允许 Workflow 激活。

### 深模块边界

- 调用方只给根 digest + 目标范围 + 依赖模式，不关心闭包如何展开。
- 内部处理循环/冲突/去重/风险，全部结果沉淀进 `SkillRolloutPlan`。
- 失败与风险在返回结构里表达，不靠异常抛给 UI 再拼装。

## 4. Artifact Revision 契约与 quality-report.json

这是 novel-production 编排（见 03）依赖的统一契约，先把跨产物一致性的数据面定下来：

- 每个生产 Skill（`cast`/`art`/`script`/`storyboard`）产出**带 revision 的 artifact**：`{artifactId, revision, digest, producedBy, inputRefs[], schemaVersion}`。
- `quality-report.json` 统一记录质量门结果：

```json
{
  "schemaVersion": 1,
  "subject": { "artifactId": "script", "revision": "r2", "digest": "..." },
  "checks": [
    { "id": "cross-cast-consistency", "status": "pass|block", "detail": "..." }
  ],
  "blockingCount": 0,
  "maxRounds": 3,
  "round": 2
}
```

- 节点只返回 `artifactId + digest + 校验摘要`，完整 JSON 走 artifact manifest（见 03 §5 的 256 KB 约束）。

## 5. 两个现有实现的配合调整

### 5.1 原子 upsert

`createSkillInstallationSync` 当前是“先 `readSkillInstallationByLockSync` 再 INSERT”（`packages/db/src/skill-installations.ts:78`）。并发批量安装可能撞 `UNIQUE(workspace_id, runtime_id, artifact_digest, revision)`。改为数据库原子：

```sql
INSERT INTO skill_installation (...)
VALUES (...)
ON CONFLICT (workspace_id, runtime_id, artifact_digest, revision)
DO UPDATE SET updated_at = EXCLUDED.updated_at
RETURNING id, status, revision;
```

保留“幂等返回现有记录”的语义，但消除读写竞态。

### 5.2 批量审批

当前单 installation 消费一次审批（`packages/services/src/skills/installations.ts:140`）。批量安装改为：创建 `skill_rollout_plan`，一次审批绑定“依赖闭包 + 目标 Runtime 集合 + planDigest”，所有子安装引用该批准记录（`rolloutPlanId`），而非各自消费独立审批。子安装创建时校验 `rolloutPlanId` 存在、`decision=approved`、`planDigest` 匹配、且未超出该 plan 声明的闭包范围。
