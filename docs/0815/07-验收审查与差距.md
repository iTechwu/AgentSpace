## 五、复核说明

本次整理前对审查报告的关键发现做了逐项核对（读源码对应行）：

- P1-1 笛卡尔积：`buildSkillRolloutItemsSync` 确为 `runtimeIds × digests`（root + 全部 closure）双重循环，无 placement 区分。
- P1-2 缺 planDigest/consumedAt：`installations.ts:145-152` 仅 `readSkillRolloutPlanSync` + `assertRolloutPlanCoversInstallationSync`，无 planDigest 入参、无 consumedAt 检查。
- P1-3 缺 UNIQUE：`skill_rollout_plan` 仅两个普通索引，无 `UNIQUE(workspace_id, plan_digest)`。
- P2-7 冲突去重：`uniqueSkillDependencies` 仅按 `coordinate.toLowerCase()` 去重保留首条，无版本/placement 冲突检测。
- P2-8 缺 planId：`SkillRolloutPlan` 接口仅 `planDigest`，无 `planId`。
- S2 未使用导入：`rollout.ts:10` 的 `import type { SkillArtifactRecord }` 未见使用。

其余发现（P1-4/P1-5/P2-6/S1/S3/S4）为审查报告原始结论，未逐一复核，但与前文已核实项同源、可信度高。

## 六、独立复核结论（本次审查）

本次对 `7f360d27..585ab010` 的落地代码做独立复核（基线 `585ab010` 之后的 HEAD 对技能安装代码无改动，仅 `index.ts` 新增 6 行无关导出），逐项读源码确认：

- **P1/P2/S 全部命中属实**：P1-1 笛卡尔积、P1-2 缺 planDigest/consumedAt、P1-3 缺 UNIQUE、P1-4 dispatch 门禁绕过、P1-5 产物契约未落地、P2-6~P2-8、S1~S4 均与源码一致（P1-4 的 `validateWorkflowNodeForDispatchSync` 确未传 `workspaceId`/`runtimeBindings`，闭包校验被防御性短路；S2 `rollout.ts:10` 的 `SkillArtifactRecord` 确未使用；S3 `import.ts` 的 artifact 持久化注释确被 `deriveSkillCoordinate` 隔断而悬空）。
- **新增 G1（编排端到端缺失，比 P2-8 更高层）**：`planSkillRollout` 是纯函数（只返回计划不持久化）、`createSkillRolloutPlanSync` 只写库、`createSkillInstallationPlanSync` 只接收既有 `rolloutPlanId`——三者之间没有编排函数把它们串成「一次操作 → 生成计划 → 一次审批 → 派发 N 个子安装」。`consumeSkillRolloutPlanSync` 当前为死代码（无人调用）。因此「安装 novel-production → 补齐 5 Skill × 3 Runtime」的用户体验尚未闭环。
- **P1-3 是设计决策而非简单补 UNIQUE**：04/05 文档 DDL 指定 `UNIQUE(workspace_id, plan_digest)`，但实现为「非唯一 + 每次审批新建一行」以支持同闭包重新审批（消费后再次安装）。直接补 UNIQUE 会与重放防护（P1-2）冲突——同一 planDigest 消费后无法再建新计划。正确做法是先明确二选一（UNIQUE + 换重审批键，或非唯一 + consumedAt/planDigest 防重放），再一并落地 P1-2/P1-3。
- **验证结果更新**：installations 测试本次复跑 30/30 通过（原报告 27/30 为锁竞争瞬时失败）；rollout 6/6、`git diff --check` 通过。

**结论**：07 文档审查结论成立——当前为「部分完成」，不满足 0815 完整验收。在 P1-1~P1-5 与新增 G1（编排闭环）修复前，不建议作为完整验收版本。
