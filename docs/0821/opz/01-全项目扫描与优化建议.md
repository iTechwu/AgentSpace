## 3. P0：进入 CI Docker 前必须完成

### P0-01 恢复可执行的质量门

**证据**

- `scripts/verify-test-inventory.mjs` 期望 172 个 deferred 测试，当前实际为 173；新增项来自 `packages/daemon/src/local-managed-node-env-config.test.ts`，添加后未更新归属或摘要。
- Web lint 有 504 个 error，其中 495 个集中在 7 个 channels 拆分文件，表现为复制后的 import 未清理；其余分布在 dashboard、knowledge 和 i18n。
- 现有 `pnpm run build` 会成功，说明 lint 不是构建阻断项。

**建议**

1. 先判断新增 daemon 测试应进入默认测试脚本，还是明确留在 deferred 集，再更新摘要；不要仅机械替换 hash。
2. 清理 channels 拆分残留，并检查这些文件是否存在未使用的重复实现或未完成抽取。
3. 增加单一入口 `ci:verify`，顺序为 inventory/engines/env -> typecheck -> lint -> 受限并发测试。
4. CI 的 Docker build 必须依赖该 job 成功，不能把 build 成功当作质量通过。

**验收**

- `node scripts/verify-test-inventory.mjs`、`pnpm run typecheck`、`pnpm run lint:web` 全绿。
- 根 `pretest` 通过后，`pnpm exec turbo run test --concurrency=2` 全绿；E2E 作为单独 lane 有明确触发条件。

### P0-02 从 Node 25 EOL 迁移到受支持 LTS

**证据**

- 本机为 Node 25.9.0；根和 10 个 workspace 均声明 `^25.9.0`。
- 主要 Dockerfile 使用私有 `node:25.9-bookworm-slim` 标签；provider runtime 的最终阶段继承可配置的 provider 基础镜像，Node 版本需要单独准入。
- [Node 官方发布页](https://nodejs.org/en/about/previous-releases) 在 2026-08-21 将 v25.9.0 标记为 EOL，将 v24.19.0 标记为 Latest LTS。
- 当前 engines 审计还需要为 `jsdom@30.0.1` 保留 Node 25 例外，Node 24.15+ 本身是其支持范围。

**建议**

1. 以 Node 24 最新补丁版建立兼容分支，先跑 typecheck、测试、Next build、daemon dist smoke、真实 Docker egress gate。
2. 同步修改 engines、审计目标、esbuild target、开发版本文件、根 `README.md`、`CONTRIBUTING.md`、`docs/0814/node-runtime-matrix.md` 和所有基础镜像。
3. 对每个 provider 基础镜像执行 `node --version`、daemon 启动和 provider smoke；不接受只验证 wrapper build stage。
4. 私有基础镜像同时锁定内容 digest；tag 只用于可读性。
5. `deploy/daemon/Dockerfile.provider-runtime` 的最终阶段继承 `${PROVIDER_BASE_IMAGE}`，必须在每个 provider 基础镜像内执行 `node --version`、daemon 启动和 provider smoke；不能只验证统一 wrapper 镜像。
6. 将 Node 升级做成一个独立提交，避免与镜像瘦身或业务修改混合；同步维护 `README.md`、`CONTRIBUTING.md` 与 `docs/0814/node-runtime-matrix.md`。

**验收**

- 本机、CI build stage、普通 runtime stage 与每个 provider 最终镜像使用同一 Node major/minor 契约，相关权威文档同步更新。
- 官方支持状态检查成为季度维护项；生产镜像不存在 EOL runtime。

### P0-03 把发布模型改成“CI 构建一次，按 digest 部署”

**证据**

- `.github/workflows/deploy-production.yml` 当前在生产目录执行 `git fetch/reset --hard`、全量安装和本机构建，服务停止后才构建候选版本。
- 回滚也会重新 reset、安装、构建，依赖外部 registry 和部署机状态。
- self-hosted Compose 使用 `build:`，没有生产 `image@sha256` 清单。
- 多处 runtime 镜像默认回退 `latest`。

**建议**

- CI 先通过质量门，再用 BuildKit/buildx 构建一次；生成 OCI revision/source/version labels、SBOM、漏洞报告和 provenance。
- 推送 `git-<full_sha>` 标签，部署清单最终只引用 registry digest。
- 部署阶段仅拉取、启动、readiness、smoke；schema 迁移由 `../docker-helm.dofe.ai` 所属的获准外部控制流程执行，AgentSpace 的 Dockerfile/Compose 不创建数据库服务或初始化 job。
- 回滚直接恢复上一组 digest，不重新构建。

详细流水线见 [02-CI-Docker迁移路线.md](./02-CI-Docker迁移路线.md)。

### P0-04 将大文件数据面改为流式 I/O

**证据**

- `workspace-blobs/[sha256]/route.ts` 允许 512 MiB，PUT 使用 `request.arrayBuffer()`，GET 先把完整对象读入内存，再做 range slice。
- TOS 同步路径用 `spawnSync("curl")`，下载 `maxBuffer` 为 64 MiB；同步过程阻塞 Node 事件循环。
- 知识上传允许 50 MiB，同样经过 `formData()` + `file.arrayBuffer()`。
- 会话附件也先解析完整 multipart，再将字节交给服务层。

**建议**

1. workspace blob 使用 Web Stream -> hash/size Transform -> 对象存储流式上传；GET 透传对象存储 Range，不先下载完整对象。
2. 浏览器上传优先使用短期预签名直传，控制面只提交元数据和摘要；服务端必须再次验证租户、对象 key、size 和 digest。
3. 保留小对象同步 API 只作为过渡，设置远低于容器内存预算的硬上限，并记录淘汰日期。
4. 为上传、下载、断流、digest 错误和对象存储超时补充容器内压力测试。

**验收**

- 512 MiB 上传时 Web RSS 增量保持在固定流缓冲预算内，而不是随文件线性增长。
- 并发上传期间事件循环延迟和普通 API p95 不突破预算。

### P0-05 修复生产依赖漏洞并缩小 Prisma 运行时依赖面

**证据**

- 使用 npm 官方审计端点后，生产依赖报告 1 个 high：`deepmerge-ts < 8`。
- 路径为 `packages/db -> prisma -> @prisma/config -> deepmerge-ts`。
- `prisma` CLI 当前在 `dependencies`，导致 Web、CLI、daemon、worker、proxy 的生产依赖树都携带 CLI 与配置解析链。
- 项目默认 registry `npmmirror` 不实现 npm audit endpoint，直接执行 audit 会报 endpoint 不存在。

**建议**

- 在验证 Prisma 版本兼容后升级到包含修复链的版本；若 `@prisma/client` peer 仍要求 CLI，在镜像构建阶段生成 client，运行阶段仅携带必要 runtime。
- 将 Prisma CLI 移到 dev/build 依赖，使用 `pnpm deploy --prod` 或 Next standalone 产出生产依赖闭包。
- CI 安装可继续使用内部/镜像 registry，但安全审计必须显式使用受支持的审计源，或接入企业 SCA。

**验收**

- `pnpm audit --registry=https://registry.npmjs.org --prod --audit-level=high` 无 high/critical。
- 生产镜像中不存在 Prisma CLI 命令和 `@prisma/config`，除非有已证明的运行时需求。

## 4. P1：高收益结构优化

### P1-01 最小化并复用生产镜像

**现状**

- `deploy/self-hosted/Dockerfile` 将 build stage 的整个 `/srv/DofeAgent` 复制到 runtime，包含源码、完整 workspace `node_modules` 和开发工具。
- Next 配置未启用 `output: "standalone"`，虽然本地 Next 16 文档明确支持只复制运行所需文件。
- Workflow Worker 单阶段安装全 workspace，直接运行 TS 源码；它没有 Dockerfile 专用 ignore，当前本机仓库约 13 GiB，其中 `.next` 约 11 GiB、`node_modules` 约 1 GiB，可能全部进入 build context。
- self-hosted 多个服务重复声明同一 build；BuildKit 可复用部分层，但部署仍在目标机现场构建。

**建议**

- Web 使用 Next standalone，runtime 只复制 standalone server、`.next/static`、public 和必要资源。
- Workflow Worker 用 esbuild/tsc 生成单一 JS 产物，runtime 不运行 TS、不安装 pnpm。
- daemon 延续 tgz/dist 模型；MCP proxy 已是单文件 bundle，可作为样板。
- 给仓库增加统一 `.dockerignore`，再为特殊 Dockerfile做窄化；统一 BuildKit pnpm cache mount。
- 为每个镜像设置压缩体积、解压体积、层数和 cold start 预算。

### P1-02 收敛数据库同步门面，按业务域完成 Prisma 异步切流

**现状**

- 生产代码有 6,000+ 个 `*Sync` 调用样式；DB 包导出约 757 个同步函数。
- `database.ts` 通过 worker thread 内单个 `pg.Client` 执行查询，主线程用 `Atomics.wait` 轮询结果，所有 legacy 查询在每个进程内串行。
- `.env.example` 有大量 Prisma read/shadow/write 开关且默认关闭；说明迁移基础已存在，但尚未形成明确完成顺序。
- DB schema 已有 198 个索引、24 处 concurrent index 处理，迁移守卫基础较好。

**建议**

- 按“读多且无事务 -> 写路径 -> claim/lock 高风险路径”排序迁移，每个域经历 shadow read、对比、主读、主写、删除 legacy 五步。
- 使用已有 `prisma:pool:evidence`、loadtest 和 cutover SLO，给每个域记录 p50/p95、fallback、mismatch、连接数和死锁率。
- `FOR UPDATE SKIP LOCKED`、advisory lock、在线 DDL 等保留经过审查的原生 SQL，不追求形式上的全 Prisma。
- 所有 Web request path 最终不得通过 `Atomics.wait` 或同步对象存储访问阻塞主线程。

### P1-03 修复无界会话读取和 workspace 全量状态依赖

**证据**

- 会话 messages GET 读取整个 `workspace_state`，过滤目标 conversation 后全部返回，无 cursor/limit。
- 数据库已经有 `conversation_message` 表和 `(conversation_id, created_at)` 索引，也已有按 conversation 查询函数，但 route 仍使用 JSON 状态作为消息真相。
- 多个 API/Action 为查找单个对象读取完整 workspace state。

**建议**

- 会话消息 API 改为 `(conversation_id, created_at, id)` 稳定 cursor，默认 50、上限 200。
- 在完成一致性回填和双读对比后，将 `conversation_message` 设为读取真相，workspace JSON 保留兼容窗口后下线消息集合。
- 对 `readWorkspaceStateSync(...).items.find/some/filter` 建立清单，逐项替换为按 workspace + resource id 的索引查询。

### P1-04 清理 27 条源码循环依赖

主要循环组：

- CLI daemon runtime/task-runner。
- CLI 飞书 evidence core/failures/interactions/proofs/satisfaction。
- DB `database <-> postgres`、`task-execution-events <-> task-queue`、external integration 三角环。
- Web dashboard data 的 agent/inbox/runtime/skills 聚合环。
- daemon remote worker 与 operation worker 环。
- services 飞书 guest/binding 和 skill GitLab/http helper 环。

建议先为 CI 增加排除生成目录后的循环依赖快照，禁止数量增长；再把共享类型、纯函数、端口接口下沉到无副作用模块。不要通过新增 barrel 掩盖循环。

### P1-05 建立前端性能预算并拆分全局 CSS

**证据**

- `apps/web/app/globals.css` 为 38,093 行、约 802 KiB；生产 CSS chunk 约 628 KiB，gzip 约 104 KiB。
- 最大 JS chunk gzip 约 223 KiB；当前没有 route 级 bundle budget。
- 有 107 个生产 `use client` 文件；13 个 client 文件超过 800 行，最大 2,461 行。

**建议**

- 将 globals 仅保留 reset、tokens、layout primitives；功能样式迁入 CSS Modules 或与 feature 同目录的样式入口。
- 用构建产物 manifest/分析器确定最大 JS chunk 的模块组成，再决定动态加载边界。
- 在 CI 记录 CSS、关键 route 首载 JS、字体和媒体体积；初始阈值取当前基线，随后逐步收紧，避免一次性硬套通用数字。
- 在真实浏览器测 LCP/INP/CLS；本次静态扫描不能替代用户侧性能数据。

### P1-06 补齐 readiness、结构化日志和请求链路

**证据**

- `/api/health` 只返回固定 JSON，不能区分进程存活与数据库不可用。
- self-hosted 6 个服务中只有 Web 有 healthcheck；worker、maintenance 和两个 daemon 缺少容器健康检查。
- 应用没有直接的 OpenTelemetry/Prometheus 依赖；日志结构化程度不一致，daemon 仍有大量自由文本输出。

**建议**

- 分离 `/health/live` 与 `/health/ready`；readiness 检查 DB 轻量查询、schema 版本、必需密钥配置和进程角色依赖，但不调用慢外部供应商。
- Worker/daemon 暴露状态命令或本地 HTTP 健康端点，Compose/Kubernetes 使用同一契约。
- 统一日志字段：timestamp、level、service、version、requestId/traceId、workspaceId（可安全记录时）、operationId、durationMs、errorCode。
- 为 API、DB、对象存储、队列 claim 和 provider 调用建立 RED 指标；告警基于 p95/error/saturation，而非日志关键字。

### P1-07 完成 Web 安全响应和入口限流基线

**证据**

- Next 全站只显式设置 HSTS，nginx 也未补 CSP、frame、MIME、Referrer、Permissions Policy。
- Web/API 没有统一的速率限制实现；MCP egress proxy 自身已有 per-connection 限制。
- 认证、daemon token 绑定和 workspace 一致性检查总体为 fail-closed，这是应保留的优点。

**建议**

- 在报告模式观察后启用 CSP；补 `frame-ancestors`/X-Frame-Options、`nosniff`、Referrer-Policy 和最小 Permissions-Policy。
- 在外部入口层对 SSO start/callback、上传、搜索、daemon register/claim 和内部 webhook 分别设置限额；多副本环境使用集中式限流能力，而不是单进程内存计数。
- cron/internal bearer 校验收敛为一个 helper，统一缺失配置、常量时间比较、审计和错误响应。

## 5. P2：工程效率与长期维护

### P2-01 扩展 Turbo 任务图

当前 `turbo.json` 只定义 test，build/typecheck/lint 由根脚本串行手工编排，且没有有效 outputs。建议为 build、types、lint、test 定义依赖和缓存产物；数据库 generate 作为显式前置任务，避免一个 build 内重复 generate/typecheck。

### P2-02 改造测试分层和覆盖度

- 529 个测试中当前 173 个（约 32.7%）处于 deferred 集。
- Web E2E 被 inventory 视为 owned，但不属于默认 Vitest/Turbo test 命令，应在 CI 中有独立 lane。
- 没有代码覆盖工具或阈值配置。

建议按 pure unit、DB integration、Docker integration、browser E2E、external smoke 分层；每层明确 owner、环境、超时和触发方式。覆盖率优先约束认证、租户隔离、claim/lease、计费、迁移和恢复分支，不追求单一全仓百分比。

### P2-03 控制巨型模块继续增长

41 个生产文件超过 1,000 行，热点包括 channels client、chat primitives、飞书 inbound/data-plane/outbound、DB postgres/index、documents sync、MCP connections。先以 1,500 行为“必须解释并禁止增长”阈值，按领域状态/IO/纯转换/展示组件拆分，并用 lint/依赖规则保护边界。

### P2-04 统一本机与 CI 的契约，而不是强迫本机容器化

- 本机继续使用原生 `pnpm dev` 和本机 daemon，获得最快反馈。
- 增加版本文件和 `doctor` 检查，确保 Node/pnpm、外部服务 URL、CA、架构与 CI 一致。
- 提供 `ci:verify` 和最小容器 smoke，使开发者在提交前可以复现 CI，而不启动 Jenkins。
- `deploy/postgres/docker-compose.yml` 已删除；`deploy/postgres/` 仅保留外部基础设施连接说明。任何本机、CI 或发布脚本都必须显式拒绝创建或引用 PostgreSQL、Redis、RabbitMQ 服务与数据卷。

## 6. 已有优势，应保留

- daemon token 与 runtime/workspace 绑定、跨租户访问审计、remote mode fail-closed。
- MCP egress 的 lease、JTI 防重放、策略摘要、只读文件系统、cap drop 和网络隔离。
- PostgreSQL schema/advisory lock/在线索引/前向版本守卫与 Prisma shadow SLO。
- 环境模板审计、Node engines 审计、测试 inventory 的“禁止静默增长”意图。
- daemon dist smoke、流式 content-addressed blob 路径、worker SIGTERM/SIGINT 退出处理。
- self-hosted 主栈已连接外部 PostgreSQL，没有在该 Compose 中创建 PG/Redis/RabbitMQ。

## 7. 建议追踪指标

| 维度 | 首批指标 |
| --- | --- |
| 质量 | pretest/typecheck/lint/test/E2E 成功率与耗时 |
| 镜像 | build context、压缩/解压体积、层数、CVE 数、cold start |
| Web | LCP、INP、CLS、首载 JS/CSS、API p50/p95/p99、event-loop lag |
| DB | query p95、连接池占用、等待、fallback/mismatch、deadlock、statement timeout |
| Worker | tick duration、queue age、claim rate、retry/failure、graceful shutdown duration |
| Blob | 并发吞吐、RSS 增量、对象存储延迟、断流/摘要失败率 |
| 发布 | lead time、部署耗时、readiness 时间、回滚耗时、变更失败率 |
