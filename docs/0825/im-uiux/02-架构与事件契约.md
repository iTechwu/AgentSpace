# IM 架构与事件契约

## 1. 参考 Harness 的可复用设计

参考目录 `../deepseek-harness/packages/client/ui-conversation` 与 `packages/client/runtime`，本方案采用以下四个原则：

1. **稳定 Node key**：会话读取模型先把事件投影为 `ChatNode[]` 和 `order[]`，列表排序变化与节点内容变化分离。
2. **单节点订阅**：类似 `ChatNodeSeat`，每个 UI 行只读取一个 node key，assistant delta 不导致兄弟节点 remount。
3. **累计 partial**：类似 `PartialAccumulator`，按 block index 累计 text/reasoning/tool-call，只有对应 block 的引用改变。
4. **帧级通知**：类似 `Notifier.markFrameDirty()`，结构变化用 microtask，流式可见变化按 animation frame 合并。

Harness 的 `ReasoningRow` 与 `ToolRow` 还提供了本项目需要的交互基线：整行 disclosure、摘要滚动到最新行、运行中 sweep、详情内部滚动、工具 IN/OUT 分栏。

## 2. 当前数据路径与改造点

```text
daemon POST /api/daemon/tasks/:taskId/messages
  -> appendTaskMessageSync(task_message)
  -> updatePendingAgentChannelReplySync(text delta)
  -> recordAgentChannelProgressSync(process projection)
  -> publish channel.thread.changed
  -> channel SSE
  -> refreshChannelData() 全量读取
  -> channels-page-client liveMessages 折叠 carrier
  -> ConversationMessageBubble / TaskExecutionTimeline
```

目标路径：

```text
daemon POST .../messages
  -> task_message 持久化（seq 单调）
  -> conversation stream invalidation（带 taskId/lastSeq）
  -> client GET conversation snapshot?afterSeq=<n>
  -> ConversationStreamStore upsert node / block
  -> order[] 稳定，单 node 局部重渲染
  -> MessageNode / ReasoningRow / ToolRow / StatusRow
```

### 2.1 保留的事实来源

- `packages/db/src/task-messages.ts` 的 `TaskMessageRecord` 是 Harness task stream 的持久化来源。
- [packages/services/src/messages/messages.ts](../../../packages/services/src/messages/messages.ts) 仍负责频道消息投影、pending 回复和 realtime publish。
- Conversation 过滤继续以 `conversationId` 为唯一消息范围，不能退回以 channel 作为消息主键。
- 现有 SSE 路由继续做授权、heartbeat、persisted poll 和失效通知。

### 2.2 需要新增的读模型

建议新增 `apps/web/features/chat/conversation-stream/`（名称可按现有目录规范调整）：

```ts
type ConversationNodeKind =
  | "user"
  | "assistant-text"
  | "reasoning"
  | "tool-call"
  | "status"
  | "usage"
  | "error"
  | "unknown";

interface ConversationNode {
  key: string;                 // `${taskId}:${seq}` 或 `${messageId}`
  taskId?: string;
  messageId?: string;
  conversationId: string;
  seq: number;
  kind: ConversationNodeKind;
  status: "running" | "completed" | "error";
  createdAt: string;
  updatedAt: string;
  summary?: string;
  text?: string;               // cumulative assistant/reasoning text
  tool?: {
    name: string;
    refId?: string;
    parentRefId?: string;
    input?: string;
    output?: string;
    inputContent?: NodeContentRef;
    outputContent?: NodeContentRef;
  };
  payload?: string;            // usage/unknown/error safe detail
  payloadContent?: NodeContentRef;
  sourceType: string;          // original task_message.type
}

interface NodeContentRef {
  preview: string;
  byteLength: number;
  complete: boolean;
  contentId?: string;          // complete=false 时用于受权懒加载
}

interface ConversationStreamSnapshot {
  conversationId: string;
  nodes: ConversationNode[];
  lastSeqByTask: Record<string, number>;
  snapshotVersion: number;
}
```

约束：

- `key` 不使用数组 index，不因工具结果回填或分页而改变。
- `seq` 只负责同一 task 内排序；跨 task 使用 `createdAt` + message insertion order，无法比较时使用稳定 key 兜底。
- `text` 是累计值，不是 delta；服务端接口可传 delta，但 store 必须在提交前合并。
- `payload` 必须经过安全化，原始 provider diagnostics 不进入普通 IM。
- `NodeContentRef.complete=false` 时 UI 必须显示截断状态和总大小；不得把 preview 伪装成完整输出。完整内容仍保存在 task stream/内容存储中，通过受权分段读取获得。
- `sourceType` 为开放字符串，未知 required event 必须投影为 `unknown`，不能因为类型不认识而丢弃。

## 3. HTTP 与 SSE 契约

### 3.1 增量读取

保留现有 `GET /api/workspaces/:workspaceId/conversations/:conversationId/messages`，增加可选参数：

```http
GET /api/workspaces/:workspaceId/conversations/:conversationId/messages?afterSeq=120&limit=200
```

返回：

```json
{
  "conversation": { "id": "conv_01", "runState": "running" },
  "snapshotVersion": 7,
  "lastSeqByTask": { "task_01": 124 },
  "messages": [],
  "executionNodes": [
    {
      "key": "task_01:121",
      "taskId": "task_01",
      "conversationId": "conv_01",
      "seq": 121,
      "kind": "tool-call",
      "status": "completed",
      "sourceType": "tool_use",
      "tool": { "name": "search", "refId": "call_7", "input": "{...}", "output": "..." }
    }
  ]
}
```

规则：

- 首次请求不带 `afterSeq`，返回当前会话完整 snapshot；后续只返回 seq 大于客户端已确认值的事件和被更新节点。
- `afterSeq` 只在同一 task 内有意义；多个 task 使用 `lastSeqByTask`，不能用一个全局 seq 假设跨 task 严格有序。
- 结果必须按权限过滤；服务端不能让客户端自行拼 taskId 读取其它 conversation。
- `limit` 有上限，超出时返回 `hasMore` 和 `nextAfterSeq`，客户端按批次追加并保持锚点。

超大节点内容使用独立的受权读取接口，避免 snapshot 一次返回多 MB payload：

```http
GET /api/workspaces/:workspaceId/conversations/:conversationId/execution-content/:contentId
  ?cursor=<opaque>&limitBytes=65536
```

返回 `content`、`nextCursor`、`complete`、`byteLength` 和校验摘要。接口必须验证 contentId 属于该 conversation，限制单次字节数；复制完整内容时由客户端逐段读取，下载则使用短期授权响应。服务端保留完整内容，聊天内预览截断与持久化截断是两回事。

### 3.2 SSE 失效事件

在现有 `channel.thread.changed` payload 中增加可选字段：

```json
{
  "type": "channel.thread.changed",
  "channelName": "contact:Codex",
  "conversationId": "conv_01",
  "taskId": "task_01",
  "lastSeq": 124,
  "changedAt": "2026-08-25T12:01:02.123Z"
}
```

要求：

- SSE 只携带定位和失效信息，不携带完整 reasoning/tool payload。
- `conversationId` 缺失时客户端按现有频道级兼容逻辑刷新；新增路径必须尽量带上。
- 客户端收到事件后取消同一 conversation 的重复请求，按 task 的 `lastSeq` 合并拉取。
- 重连后先执行一次 snapshot 校验，再恢复监听；事件丢失不影响最终一致性。

### 3.3 幂等与顺序

- `taskId + seq` 唯一；重复事件只确认，不重复追加节点。
- seq 出现缺口时保留已有节点，显示“正在同步最新输出”，拉取缺失区间；不能把后续节点错误标记为完成。
- `tool_result` 先按 `refId`，再按同 task 未关闭工具栈兜底；无法配对时生成独立 result 节点。
- 同一节点的迟到更新以 `seq`/`updatedAt` 较新者为准；终态不能被旧 pending 更新回退。

## 4. 客户端渲染结构

建议将 `ConversationShell` 的消息渲染从“消息列表 flatMap”拆为三层：

```text
ConversationShell
  └─ ConversationStreamView
       ├─ StreamNodeSeat(key=user-message)
       ├─ StreamTaskGroup(taskId)
       │    ├─ StreamNodeSeat(key=status)
       │    ├─ ReasoningRow(node)
       │    ├─ ToolRow(node)
       │    ├─ AssistantMarkdown(node)
       │    └─ UsageRow / ErrorRow / UnknownRow
       └─ StreamNodeSeat(key=assistant-message)
```

实现要求：

- `ConversationStreamStore` 是 React 外部状态源，组件只通过明确的 selector 读取；不要在 presentation component 内手写订阅。
- 结构性更新（新 node、删除/重排）使用 microtask；流式 text/reasoning 更新使用 frame-batched notify。
- 每个 `StreamNodeSeat` 使用 `memo` + 稳定 `key`，不把完整 nodes 数组作为每一行 prop。
- 展开集合是独立的 view state，key 为 node key；不得写入 task/message 事实数据。
- 现有 `ConversationScrollAnchor` 迁移为同时保存 `anchorNodeKey`，旧 `messageId` 仍可作为兼容字段。

## 5. 安全与可见性

- provider 原始 stderr、绝对路径、凭据、内部 endpoint 和诊断堆栈默认在服务端过滤；UI 不依赖正则猜测是否安全。
- usage 显示协议报告的 token/计费字段；没有权威值时显示“未知/待同步”，不估算成实际费用。
- unknown event 只显示 type 和安全 payload，禁止把任意 JSON 直接当 HTML 或 Markdown 执行。
- 超大详情按 contentId 懒加载并限制单次字节数；完整读取仍经过 conversation 授权和服务端安全化，不能让浏览器直接访问 runtime 文件。
- 附件、链接、文件路径沿用现有授权和短期 URL 机制。
