# DeepSeek Harness Runtime 实施路径与改动清单

## 1. 阶段总览

| 阶段 | 目标 | 产物 | 退出条件 |
| --- | --- | --- | --- |
| W0 | 依赖与镜像 spike | 部分：版本/Compose/安装命令已固定；镜像未构建 | 阻断：批准 Node 24.19 基础镜像返回 `not found` |

| W2 | Runtime provisioning | 部分：类型、模板、env、health、本地 allowlist、DeepSeek provisioning 审计元数据完成 | 真实 managed runtime 创建/注册/回收未验证 |
| W3 | 产品与灰度 | 部分：创建入口、Provider 账户、模型选择、feature flag、provider health、公开 health 投影、本地 usage 协议归属、headless 能力说明、MCP fail-closed 和 provisioning 审计完成 | canary、真实 billing 对账和 rollback 证据未完成 |

## 2. W0：依赖与镜像 spike

1. 固定 `deepseek-harness` 版本（当前 checkout 为 `0.1.1-rc.2`），记录 Node/pnpm/系统依赖。
2. 构建一个只包含 Node、dsh 构建产物和受控 profile 的 `dofe/agent-runtime-deepseek-harness:<tag>` 镜像；不得在 Docker Compose 中新增 PostgreSQL、Redis 或 RabbitMQ。
3. 验证以下命令和输出边界：

   ```bash
   dsh --version
   dsh --profile headless --help
   dsh --profile headless "reply with OK"
   ```

4. 记录 `DEEPSEEK_BASE_URL` 的直连和 models gateway 两种模式，不把 endpoint 写死在 adapter。
5. 用无密钥 mock/loopback server 验证 stdout、stderr、退出码、超时和 SIGTERM 行为。

| 文件 | 改动 |

| `packages/daemon/src/agent-router/adapters/index.ts` | 注册 adapter |

| `packages/daemon/src/provider-runtime/agent-router-task.ts` | provider 分发、model 传递、session fallback 策略 |
| `packages/daemon/src/provider-runtime/catalog.ts` | provider catalog、默认模型、executable/version 探测 |
| `packages/daemon/src/provider-runtime/provider-env.ts` | managed key 清理与 `DEEPSEEK_*` redaction |
| `packages/daemon/src/agent-router/*.test.ts` | adapter unit、stdout/stderr、timeout、signal、auth/model failure |

Adapter 的 `buildLaunch` 应将 task prompt 作为单一 positional argument，禁止 shell 拼接；`DSH_HOME` 使用 runtime metadata 指定的隔离目录。P0 不支持 `sessionId` resume，收到该参数时要么显式忽略并记录 diagnostic，要么直接返回 `harness.session_missing`，不能静默误恢复。

## 5. W3：产品和灰度改动

1. `apps/web/features/runtimes/*`、`apps/web/features/agents/*`：provider 下拉、model picker、health badge、headless 能力说明和 feature flag。
2. `apps/web/features/agents/*`：绑定确认页显示 `DeepSeek Harness · model`，并提示 headless 无 resume。
3. billing/usage：将 provider、model、protocol、input/output token（若 P0 无可靠 token event，则标记估算/未知）写入统一 usage contract；managed JSON-RPC queue 已保留 provider cache read/write/reasoning usage 事件用于审计，完成回传只采信带 gateway request id 的 Models gateway usage 并保留合并后的 `cacheTokens`，避免双计费；真实 gateway 对账仍是发布门禁。
4. audit：记录 runtime 创建、credential 绑定、模型切换、health failure 和 rollback；provisioning 事件必须保留 provider/protocol/model 等非敏感上下文。公开 runtime/任务详情只投影状态、原因、时间和结构化错误码，不暴露原始 provider 错误文本。
5. fallback：canary 失败时只切换 employee binding，不删除 runtime 或 session 证据。

## 6. W4：JSON-RPC/ACP

优先实现 JSON-RPC，因为上游已有 `examples/jsonrpc-agent` 和 SDK client；ACP 仅作为外部 automation surface。W4 不再作为一个不可验证的大包实施：

1. W4a-0 已实现默认关闭的一次性协议基础：锁定当前 `0.0.1` server identity，验证 prompt receipt、durable seq/time、turn/step 边界、七类 `StreamChunk` 的 block/usage/finish 状态、同 step 部分输出 retry 的失败 attempt 丢弃与状态重置、逐类型 text/tool/usage 事件、canonical usage 一致性、未知 required event、reasoning 诊断隔离、不可逆协议失败、launch 释放，以及 ACK/无 ACK 两路的有界 EOF→SIGTERM→SIGKILL 退出；不发布 session id。
2. W4a-1 已交付 queue 的代码级准入：只有 daemon 操作员同时设置显式开关、carrier/config 绝对路径，以及 carrier、config、`-rg` 和 macOS `-spawn-helper` 的精确 SHA-256 时才选择 JSON-RPC；显式开启但平台所需配置不完整时 catalog fail-closed，不回退或执行 PATH 上的 legacy CLI。Cordis 文件还必须匹配仓库内固定 tag 的批准模板，任意自签名摘要同样拒绝。task/Skill 无法覆盖 Cordis 路径、daemon PATH 或动态加载/解释器启动环境，release 控制变量不进入 provider child；脚本 carrier 必须固定绝对解释器，bundle 任一文件、摘要或执行约束不一致均在 spawn 前拒绝。health 复用同一 verifier，完整 pin 未通过前不执行 carrier；通过后执行有界 initialize/shutdown 握手并锁定 server identity，无 credential/model canary 时状态为 degraded。专用 managed Dockerfile 通过命名 build context 接收 production carrier/`-rg`；wheel 导入器先锁定 fork commit、发行名/版本、Linux x64 tag、唯一 carrier 集合以及 wheel/carrier/sidecar 摘要并原子生成 `provenance.json`，构建脚本和镜像层再使用同一结构化 verifier，随后复制批准 Cordis 模板并烘焙 attestation marker。镜像把 provenance 路径、固定 source commit 和 wheel 摘要传给 daemon；catalog、task、health 在每次准入时重新读取严格 manifest，并绑定同目录 carrier/`-rg` pin，不能只凭 marker 或 label 放行。缺失、篡改或 detached provenance 均零 spawn；standalone 不受 managed-only provenance 要求影响。镜像构建后、tag 前还必须执行容器内 `verify-deepseek-release`，结构化 verifier 只接受与当前 pin 完全一致的 server identity、initialize/shutdown 和 stdout purity evidence，并原子保留最近一次有效证据。上游固定 tag 已有 Python wheel/单文件 carrier 构建链，但本机尚未取得真实 wheel、Docker daemon 或网络资产，也未实际 build/publish image digest 或执行真实载体 smoke/模型 E2E。bounded worker 还要求上游按 session 隔离 task-scoped 环境；在此之前直接复用会跨任务泄漏 Skill/credential attribution 环境，必须保持关闭。
3. W4a-2 已交付发布后双模型 canary 执行链：daemon 的 `verify-deepseek-model-canary` 使用受控 release pin 和隔离环境依次执行 `deepseek-v4-flash`/`deepseek-v4-pro` 完整 JSON-RPC 回合，要求精确响应、无工具调用和唯一 canonical usage；staging runner 只接受 repository、独立 64 位摘要与完整 immutable ref 三者完全一致的镜像，将公钥/release evidence 冻结为私有快照，并要求公钥匹配独立批准 SHA-256；随后才在 Docker/API key 暴露前执行隔离且有界的 `cosign verify`，仓库/摘要不符、拒签或挂起均零 Docker 调用。验签通过后 runner 显式覆盖常驻 entrypoint，以宿主 deadline/输出上限/Docker client TERM→KILL/无条件按名称删除约束容器，以环境变量名传递 key，并把无 prompt/output/credential/明文 endpoint 的结果与签名公钥摘要、release evidence、endpoint 身份精确绑定、原子落盘。受控 `deploy-deepseek-runtime.sh` 在同一环境运行上述 canary，成功后才以 `--pull never --no-build` 启动专用 Compose；该 Compose 只按 `${repository}@sha256:${64hex}` 构造引用，不允许 DeepSeek 远端 build 或 mutable tag fallback。通用 remote-images 不依赖 DeepSeek 变量，本地 compose 保留构建职责。fake carrier、cosign、Docker runner/deploy shim 覆盖已通过；真实已签名 image digest、测试 key 和 endpoint evidence 尚未取得，因此发布门禁仍未通过。
4. W4b 在 `../deepseek-harness` fork 继续补协议版本协商、turn cancel ACK、逐请求 approval、session close；现有 cancel/resume/approval-policy/per-session endpoint overlay 先经过真实载体验证，再实现 AgentSpace bounded connection manager、provider session 映射与恢复状态机。
5. 任一能力缺少上游方法、载体或 E2E 时必须保持 feature flag 关闭，并继续使用 P0 headless；禁止用 JSONL 文件存在推断 resume 成功。

## 7. 测试顺序

1. 无 key unit：adapter launch、argv 注入、redaction、错误分类。
2. mock HTTP/model：模型选择、重试、空响应、stderr 污染、超时。
3. daemon task-runner：queue claim、binding generation、runtime-output、失败收口。
4. managed runtime：provisioning stages、health、credential bundle、cleanup。
5. 真实 DeepSeek canary：flash smoke、pro coding task、tool task、取消、重试和回滚。

遵循仓库测试资源限制：单文件测试优先，Jest 使用 `--maxWorkers=2`；不要执行无约束的全量 `pnpm test`。

实际实施文件、提交和测试命令见 [05-实施记录与验证证据.md](./05-实施记录与验证证据.md)。
