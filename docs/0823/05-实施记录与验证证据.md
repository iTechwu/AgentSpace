## 3. As-built 行为

1. `deepseek-harness` 已加入 `DaemonProvider`、AgentRouter harness 与 provider catalog。
2. 默认模型为 `deepseek-v4-flash`，可选 `deepseek-v4-pro`；其他模型在 runtime-local allowlist 阶段被拒绝。
3. 启动命令为 `dsh --profile headless --patch <overlay> <prompt>`，prompt 作为单一 argv 参数，不经过 shell 拼接。
4. 每个 task 使用 fresh headless session。直接传入 `sessionId` 返回 `harness.session_missing`；provider queue 路径记录 `provider_session_unsupported` 后启动 fresh session。
5. `DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL` 进入 managed credential 白名单和脱敏清单；launcher 不包含明文 secret。
6. health 先执行 `dsh --version`，再以 stdin 传递 header 的子进程请求 `${DEEPSEEK_BASE_URL}/models`；key 不进入 argv 或 metadata。
   对 DeepSeek 请求会解析非敏感的 model id 摘要，并要求 `deepseek-v4-flash` 与 `deepseek-v4-pro` 同时存在；缺失时返回 `provider.model_unavailable`，不会把 endpoint 2xx 误判为模型可用。
7. Web 创建入口默认关闭，设置 `NEXT_PUBLIC_DEEPSEEK_HARNESS_RUNTIME_ENABLED=1` 后显示 provider 与两个原生模型。
8. P0 overlay 固定 `workspace-write`，设置 `DSH_TELEMETRY_DISABLED=1`，禁用 Web search、subagent、workflow 和 Ralph。实时 tool event、resume 和 AgentSpace approval bridge 不在 P0 中。
9. 每次 headless 调用使用 `.dofe-deepseek-harness.patch-<uuid>.yml` 临时 overlay，并在成功、失败、超时或取消后清理；同一持久化会话工作目录中的并发调用不会覆盖彼此的模型配置。
10. AgentRouter 的 `harness_started` 事件会映射为 provider status 消息，远端任务可在 headless 进程启动后立即显示执行中状态；不会伪造实时文本或工具事件。
11. 新任务启动前只清理匹配命名且修改时间超过 24 小时的 DeepSeek overlay，用于回收 daemon 强制退出留下的残留文件；近期文件不会被误删。
12. 每个 headless task 使用独立 UUID `DSH_HOME`，即使同一持久化工作目录并发执行，也不会共享 DeepSeek settings/cache/session；任务结束后该目录递归清理。
13. DeepSeek 健康检查在模型目录 probe 前先执行 `dsh --profile headless --help`；版本可执行但 headless profile 失败时返回 `provider.profile_missing`，不会误标为 healthy。
14. `runProviderTask` 在已有健康快照时再次检查所选模型；若模型不在已验证目录中，返回 `provider.model_unavailable`/`model`，不会启动 provider 子进程。
15. `pollRemoteTasks` 对 provider health 为 `broken` 的 DeepSeek runtime 停止新 task claim，但不跳过前置运维操作队列，便于修复后恢复领取。
16. `runProviderTask` 在任务 claim 后再次检查 DeepSeek provider health；若 heartbeat 已将 runtime 标记为 `broken`，会在启动 `dsh` 前失败，避免健康状态竞态导致新执行。
17. 健康门禁不会把 `providerHealth.reason` 原样写入任务错误；对外仅返回固定的可行动文案，避免敏感 provider 输出进入审计链。
18. Web 创建入口只有在 `NEXT_PUBLIC_DEEPSEEK_HARNESS_RUNTIME_ENABLED=1` 时才开放 DeepSeek Harness；`0`、空值及其他字符串均保持关闭。
19. 频道聊天 composer 接受所有合法 `DaemonProvider` 绑定；DeepSeek Harness 不再被误判为无 runtime，权限菜单只显示 Runtime 默认，不暴露 Codex 专属完全访问选项。
20. 托管运行时列表服务统一解析 `metadataJson`/`lastError` 为 `RuntimeProviderHealth`；Web 列表和详情对 `broken` 显示“供应商不可用”并进入“需要处理”筛选，对 `degraded` 显示降级诊断但保持可用，对 `unknown` 显示待验证并不宣称已可调度；旧测试/历史 fixture 未提供健康快照时保持原展示兼容。
21. AI 员工执行引擎选项直接复用托管运行时已规范化的 provider health；只有缺失健康快照的历史 fixture 才使用兼容 fallback，DeepSeek broken 状态不会在员工绑定界面被重新显示为可用。
22. 状态优先级先判断 runtime offline，再判断 provider unusable/degraded/unknown；离线节点显示心跳诊断，在线但 DeepSeek provider broken 仍进入“需要处理”，避免两类故障混淆。
23. 新员工绑定路径现在同时受 UI 与服务端门禁保护：provider health `broken`/`unusable` 的 managed runtime 不可绑定，并显示 provider 原因；`unknown` 仍允许绑定以兼容首次探测和历史记录，但任务领取/执行健康门禁仍然生效。
24. 聊天模型覆盖和有效模型解析对 `deepseek-harness` 使用 runtime-local `deepseek-v4-flash`/`deepseek-v4-pro` 目录，不依赖 Models 服务是否已经返回 `deepseek_native`；解析结果仍标记为未验证，任务启动必须继续通过 provider health 的已验证 `modelIds` 门禁。
25. 托管任务 usage 以上下文 runtime provider 的主协议作为兜底：DeepSeek provider event、网关日志缺失 protocol 时仍记录 `deepseek_native`；网关明确返回的 protocol 优先。这样不依赖 provider 是否提供 gateway request id，也不会把原生 usage 误归类为 OpenAI 协议。
26. 员工绑定的执行引擎元信息对 `deepseek-harness` 明确显示 `Headless · no resume`，让 P0 的 fresh-session 边界在绑定时可见，不把 DeepSeek Harness 误认为支持现有 provider resume。
27. provisioning 的请求、凭证签发和 runtime ready 审计现在保留 provider、协议、默认模型和 allowlist 等非敏感元数据；DeepSeek 创建记录可以证明使用 `deepseek_native`，不记录明文 key。

## 5. 镜像构建阻断

执行 DeepSeek wrapper build 时，Docker 在拉取 `uhub.service.ucloud.cn/techwu/node:24.19-bookworm-slim` 阶段失败，registry 返回 `not found`。构建尚未进入 `npm install @deepseek-ai/dsh@0.1.1-rc.2`，因此不能声称镜像可运行，也没有 `dsh --version`、headless help、端口或 SIGTERM 的真实容器证据。

不得改用本机已有的 Node 25 镜像绕过该问题。后续应先发布或修正批准的 Node 24.19 基础镜像，再构建并以 digest 锁定 `dofe/agent-runtime-deepseek-harness`。
