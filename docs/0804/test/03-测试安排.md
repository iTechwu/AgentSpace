# 03. K22 Runtime 与 AI 员工测试安排

## 1. 周期与策略

计划周期：`2026-08-04（周二）` 至 `2026-08-07（周五）`。

按依赖顺序执行，不以并行创建换速度：先固定 K22 与环境，再创建两个 Runtime；随后配置 CLI/MCP 和 Skill；最后创建员工、同题双跑、异常回归和清理。上游资源未 ready 时，下游场景记为阻塞，不绕过门禁。

## 4. 人员与职责

| 角色 | 主要职责 |
| --- | --- |
| QA 主责 | K22/账号基线、用例执行、双 Runtime 对照、证据、缺陷与清理核对 |
| Runtime/后端负责人 | 节点、部署、模型协议、任务状态机、幂等、审计和恢复 |
| 能力平台负责人 | CLI 目录、MCP egress/Secret/工具授权、Skill 安装与 readiness |
| 前端负责人 | 表单、路由、状态刷新、响应式、错误反馈和可访问性 |

最少需要 QA、Runtime/后端、能力平台三类职责有人承担；涉及 tenant、余额或目录缺失时必须有运营支持。

## 5. 环境与数据准备清单

### 08-04 前必须准备

- K22 tenant 对测试账号可见，管理员角色已授予。
- 至少一个在线托管节点，具备创建两个独立 Runtime 的容量。
- Codex `openai_response` 和 Claude Code `anthropic` 兼容模型目录可用。
- K22 测试余额足够完成两个 Runtime 与任务，不使用生产计费账户。
- CLI 市场至少一个低风险、可做版本探针的目录项。
- MCP 目录至少一个低风险、确定性只读工具，测试 Secret 已在凭据中心准备。
- Skill 可创建/导入/发布，且 CLI/MCP catalog slug 已确定。

### 不足时的处理

| 缺失项 | 状态 | 处理 |
| --- | --- | --- |
| K22 不可选择或身份不明 | 阻塞全部 | 不进行任何写操作，交 tenant 管理员处理 |
| 无在线节点 | 阻塞 Runtime 及下游 | 只执行权限/页面负向用例 |
| 单类模型目录缺失 | 阻塞对应 Provider | 另一 Provider 可独立执行，但专项不准出 |
| CLI/MCP 目录无低风险项 | 阻塞能力链路 | 不临时接入未知公网服务 |
| Secret 缺失 | 阻塞 MCP 正向 | 只验证必填、遮罩和失败诊断 |
| 余额不足 | 阻塞创建 | 保留预检证据，不重复提交产生计费风险 |

## 6. 自动化与人工验证

| 层级 | 时机 | 范围 |
| --- | --- | --- |
| 静态检查 | 候选 commit 固定后 | 全仓 typecheck、Web lint |
| 单元/API | 每次修复后 | Runtime provisioning、CLI-Hub、MCP、Skill installation、员工/任务相关最小测试 |
| 浏览器 E2E | 每日冒烟与周五全量 | K22 选择后的路由、双 Runtime 创建、能力配置、员工绑定和任务闭环 |
| 人工真实集成 | 本轮至少一次 | 两个 Runtime 的真实部署、CLI/MCP 调用、同题双跑和异常恢复 |

仓库测试必须遵守资源限制：根测试使用 `turbo run test --concurrency=2`；单个 API Jest 文件使用 `--runInBand`；不得运行无约束的根 `pnpm test`。

## 7. 缺陷优先级与回归

| 等级 | 本专项示例 | 处理 |
| --- | --- | --- |
| S0 | 跨 tenant 可见、Secret 泄漏、删除其他 tenant Runtime | 立即停止全部相关操作 |
| S1 | 任一 Provider 无法创建、任务完成但无结果、错误 Runtime 执行、重复计费 | 阻断专项准出 |
| S2 | CLI/MCP/Skill 单侧失败但有绕行、审计缺字段、状态刷新错误 | 修复或书面接受后回归 |
| S3 | 非关键文案、轻微布局或提示问题 | 可排期，但必须登记 |

修复后依次回归：原失败用例、同一能力域 P0、对应 Provider 主链路、Codex/Claude 同题双跑、跨 tenant 隔离。

## 8. 准入标准

- 候选 commit 固定并可追溯，目标为非生产环境。
- BASE-01 至 BASE-05、BASE-08 全部通过。
- K22 tenant、角色、工作区 slug、余额和在线节点已记录。
- 两类模型目录、低风险 CLI/MCP 和测试 Secret 已准备。
- 有安全清理方案，且未发现其他测试者正在操作同名批次。

## 9. 准出标准

全部满足才判定专项通过：

1. 所有适用 P0 执行率和通过率均为 `100%`，P1 全部有结果。
2. Codex 与 Claude Code Runtime 均在线，模型协议正确，且无重复 Runtime/部署/计费。
3. 两个 Runtime 的 CLI、MCP、Skill 均 ready；停用/恢复和跨 Runtime 隔离通过。
4. 两名员工的同题任务均成功，CLI/MCP/Skill 调用、最终报告、产物和审计可关联。
5. 未关闭 S0/S1 为 0；S2 有修复版本或书面风险接受。
6. 不存在跨 K22 数据泄漏、Secret 泄漏、未批准工具调用或错误 Provider 执行。
7. 测试业务资源与后台操作已按顺序清理，临时 Secret 已轮换/删除，审计按策略保留。
8. 最终报告包含环境、commit、tenant、资源 ID、执行统计、耗时、缺陷、阻塞和清理证明。

## 10. 工作站限制

本安排不包含 Jenkins 启动、配置、任务触发、push 或测试环境部署。若需要部署，必须由用户另行提供非 Jenkins 工作流；本地只执行授权范围内的文档、实现、验证和提交。
