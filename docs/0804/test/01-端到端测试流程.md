# 01. K22 Runtime 与 AI 员工端到端测试流程

## 1. 测试目标

以测试管理员身份验证以下闭环在 K22 tenant 内真实可用：

1. 账号能进入 K22，并且所有新增资源只落在 K22 映射的工作区。
2. Codex 与 Claude Code Runtime 都能通过预检、创建、部署、心跳和模型可用性检查。
3. 同一低风险 CLI 应用和同一低风险 MCP 能力可分别安装/连接到两个 Runtime，状态和授权互不串扰。
4. 一个跨 Runtime 兼容的 Skill 能完成发布、风险检查、安装、绑定和任务时能力快照。
5. 两名 AI 员工分别绑定 Codex/Claude Code Runtime 后，可以执行同一项任务并产生可比较、可追溯的结果。
6. 权限、Secret、失败恢复、幂等、审计、成本、性能和清理满足测试准出标准。

## 2. 关键原则

- **先 tenant，后写入**：没有确认 K22 前不得创建 Runtime、连接或员工。
- **共享目录，独立安装**：CLI/MCP/Skill 可来自同一目录项，但必须分别绑定两个 Runtime，逐一验证状态。
- **先能力就绪，后建员工**：Runtime、CLI、MCP、Skill 未 `ready` 时，不用创建员工来绕过门禁。
- **同题双跑**：两个员工使用完全相同的任务输入、附件和期望，避免用不同任务掩盖 Runtime 差异。
- **最小权限**：MCP 只批准任务所需工具；优先使用只读能力。高风险工具另走负向审批，不混入主闭环。
- **证据脱敏**：不读取、导出或记录 Cookie、Token、密码、Secret、完整内部 endpoint 查询参数。

## 3. 测试资源设计

所有资源使用唯一批次号 `<HHmm>`，例如 `0930`：

| 资源 | 建议名称 | 数量 | 说明 |
| --- | --- | ---: | --- |
| Codex Runtime | `QA-0804-K22-Codex-<HHmm>` | 1 | Provider=`Codex`，独立环境优先 |
| Claude Runtime | `QA-0804-K22-Claude-<HHmm>` | 1 | Provider=`Claude Code`，独立环境优先 |
| Codex 员工 | `QA-0804-K22-CodexAgent-<HHmm>` | 1 | 只绑定本轮 Codex Runtime |
| Claude 员工 | `QA-0804-K22-ClaudeAgent-<HHmm>` | 1 | 只绑定本轮 Claude Runtime |
| CLI 应用 | 执行时从 K22 CLI 市场选择 | 1 个目录项，2 个安装 | 要求低风险、可执行 `--version` 或等价只读命令 |
| MCP 服务 | 执行时从 K22 MCP 目录选择 | 1 个目录项，2 个连接 | 要求至少一个确定性只读工具，不依赖生产数据 |
| Skill | `QA-0804-K22-Capability-Probe-<HHmm>` | 1 个 Skill，2 个 Runtime 安装 | 声明所选 CLI/MCP 能力，输出结构化报告 |
| 任务 | `QA-0804-K22-DualRuntime-<HHmm>` | 每名员工至少 2 条 | 首轮成功任务 + 异常/恢复任务 |

执行前记录实际 CLI slug/version/入口、MCP catalog slug/release/工具名、模型 ID。目录不存在合适低风险项时记为环境阻塞，禁止临时连接未知公网服务。

## 4. 准入检查

### 4.1 环境与版本

1. 记录测试 URL、Git commit、构建时间、浏览器版本、时区和环境标识。
2. 检查 `/api/health`、SSO discovery、数据库、models 服务、MCP egress、Daemon/托管节点健康。
3. 确认至少一个在线托管节点可部署 Runtime；记录节点名称，不记录节点凭据。
4. 确认 K22 有足够测试余额，且 Codex/Claude Code 各至少一个兼容模型可选。
5. 确认账号具有 K22 workspace 管理员权限；若无权限，正向创建流程记为阻塞，并执行入口隐藏/服务端拒绝用例。

### 4.2 K22 tenant 确认

1. 无登录态打开 AgentSpace，使用统一 SSO 登录。
2. 在 SSO tenant 选择或登录后的组织信息中选择/确认 `K22`。
3. 记录 tenant 显示名、脱敏 tenant 标识、映射的工作区名称与 slug、当前角色。
4. 新标签页打开当前工作区深链，确认仍为 K22；切到其他 tenant 后深链必须拒绝或重新映射，不能继续显示 K22 私有资源。
5. 浏览器控制台与网络摘要不得出现密码、Token 或 Secret。

## 5. 主链路执行

### 阶段 A：建立基线

1. 在 Runtime、员工、CLI 市场、MCP 服务、Skills、任务看板分别搜索 `QA-0804-K22-`，记录测试前同名资源数量。
2. 记录 K22 当前 Runtime 数、员工数、CLI 安装数、MCP 连接数、Skill 数和进行中任务数。
3. 确认当前无后台安装/清理/部署操作，避免状态混入。

### 阶段 B：新增 Codex Runtime

1. 进入 K22 的“执行引擎/Runtime”页面，点击“配置执行能力”。
2. 供应商选择 `Codex`；名称使用本轮 Codex 名称。
3. 选择在线目标节点或“自动调度”；主验证建议开启“始终部署独立运行环境”，关闭共享。
4. 模型页确认只展示与 `openai_response` 兼容的模型；默认优先验证 `gpt-5.6-terra`。
5. 执行“检查并确认”，核对节点、模型、余额和分配方式摘要。
6. 点击“配置执行能力”；防重复点击，确认只产生一个部署任务。
7. 观察部署阶段直到 Runtime 在线，记录 Runtime ID、Provider、协议、模型、节点、最后心跳和耗时。
8. 刷新、前进后退并重新进入详情，状态必须保持。

### 阶段 C：新增 Claude Code Runtime

重复阶段 B，但供应商选择 `Claude Code`：

1. 模型必须来自 `anthropic` 兼容目录，不得沿用 Codex 的 Responses-only 模型。
2. 记录实际默认/选定模型，不预设 Claude Code 的固定默认模型。
3. 与 Codex 使用不同 Runtime 名称和 Runtime ID；独立部署时工作目录、凭据和心跳不得串用。
4. 完成后并排核对两个 Runtime 的 Provider、协议、模型、节点、状态和可复用策略。

### 阶段 D：为两个 Runtime 安装 CLI

1. 进入“应用市场” -> “CLI 市场”，选择一个满足测试数据要求的低风险应用。
2. 记录目录 source、slug、version、安装方式、入口命令、风险和依赖；不记录 Secret。
3. 目标先选 Codex Runtime，检查安装计划；若有风险项，逐项阅读并只批准必要项。
4. 提交一次并立即再次点击/刷新，验证幂等，不得生成重复安装。
5. 等待状态 `installed` 且 `enabled`；执行版本/只读探针，记录安全摘要。
6. 对 Claude Runtime 重复上述步骤，验证安装记录、路径、状态和错误互不覆盖。
7. 停用 Codex 上的安装，确认 Claude 不受影响；再启用 Codex，确认恢复。
8. 如果目录提供对应 Skill，同步后确认来源为 Runtime App，且只在目标 Runtime 安装就绪时可用。

### 阶段 E：为两个 Runtime 连接 MCP

1. 进入“应用市场” -> “MCP 服务”，选择一个低风险、确定性只读目录项。
2. 记录 transport、release、allowed hosts、data domains、声明工具和默认批准工具。
3. 为 Codex Runtime 创建连接：填写 endpoint/非敏感配置，通过凭据中心录入 Secret，仅批准任务必需工具。
4. 若 MCP 依赖 Runtime CLI 组件，先点击“安装 Runtime 组件”并等待完成，再提交连接。
5. 等待连接 `ready`，执行“重新验证”；检查上次验证时间、下次巡检、连续失败数。
6. 对 Claude Runtime 创建独立连接并达到 `ready`。
7. 比较两条连接：Runtime ID、批准工具、配置、活动和审计必须独立。
8. 停用 Codex MCP，确认 Claude 连接仍可验证；重新启用并恢复 `ready`。
9. 修改非敏感配置时，未填写的 Secret 必须保留且不回显；错误 endpoint 应失败且给出可恢复诊断。

### 阶段 F：新增、安装并绑定 Skill

1. 进入“Skills”，创建或从受信来源导入 `QA-0804-K22-Capability-Probe-<HHmm>`。
2. `SKILL.md` 描述必须明确：调用所选 CLI 的只读探针、调用 MCP 指定只读工具、生成 Markdown 结果；禁止任意 shell、越权网络和外部写入。
3. 如 Skill 声明 CLI/MCP 能力，catalog slug 和 required tools 必须与阶段 D/E 完全一致。
4. 保存草稿并发布；确认 artifact digest、版本、文件清单和风险摘要稳定。
5. 安装到 Codex Runtime：完成检查、逐项授权、创建安装计划，等待所有组件 `ready`。
6. 安装到 Claude Runtime并达到 `ready`；两条安装有独立 revision/operation 记录。
7. 刷新后确认两个安装仍为 ready；未解析能力不得被显示为 ready。
8. 记录 Skill Runner 入口、安装 digest 与审批审计，不记录配置值或 Secret。

### 阶段 G：新增两名 AI 员工

1. 进入“AI 员工”，选择“空白自定义”创建 Codex 员工。
2. 填写名称、备注名、简介和工作说明；说明中要求只使用批准能力、输出证据摘要、失败时停止而非猜测。
3. 执行引擎只选本轮 Codex Runtime；模型选择兼容模型。
4. 创建后进入详情，添加本轮 Skill；确认 Skill 显示需求已满足。
5. 重复创建 Claude 员工，绑定 Claude Runtime 和同一 Skill。
6. 刷新后核对两名员工的 Runtime、模型、Skill、状态和联系人入口。
7. 尝试给 Codex 员工切换到 Claude-only 模型或反向选择，系统必须过滤或拒绝。

### 阶段 H：同题双 Runtime 任务闭环

向两名员工分别发送完全相同的任务：

```text
任务：QA-0804-K22-DualRuntime-<HHmm>
请严格使用“QA-0804-K22-Capability-Probe-<HHmm>”完成以下工作：
1. 调用已批准 CLI 的只读版本/状态命令；
2. 调用已批准 MCP 只读工具，使用测试输入获取确定性结果；
3. 输出 Markdown 报告，包含 runtime_provider、model、cli_result_summary、mcp_result_summary、skill_name、PASS/FAIL；
4. 不得调用未批准工具，不得输出任何 Secret、Token、Cookie 或完整凭据。
```

每名员工分别验证：

1. 消息立即回显，只创建一条任务，状态按 `queued -> running -> completed/failed` 合法流转。
2. 执行时间线包含 Skill、CLI 与 MCP 调用；工具名和结果能按 ref 关联，无长期悬挂。
3. 高风险工具若未批准必须进入审批或被拒绝，不能静默执行。
4. 最终回复包含要求字段，且结果与实际 Provider/模型一致。
5. 任务详情、看板、会话、通知、成本、绩效和审计指向同一 task/employee/runtime。
6. MCP 工具审计包含 actor、runtime、tool、outcome、latency 和脱敏摘要。
7. Skill Runner 审计包含 installation/digest/entrypoint，不泄露输入 Secret。
8. 刷新、重新登录后任务、消息、产物和审计仍存在。

### 阶段 I：交叉与异常验证

1. 停用 Codex MCP 后重跑任务：应在执行前阻断或清楚失败；Claude 任务仍成功。
2. 恢复 Codex MCP 并重新验证后重试，成功且不重复原任务产物。
3. 停用 Claude CLI 后重跑：Skill readiness/任务应阻断；Codex 不受影响。
4. 将 Skill 从其中一个员工解绑，新任务不能再使用；已运行任务的能力快照与历史审计保持。
5. 断开 Runtime/等待心跳过期，任务保持排队或失败并给出恢复动作；不得误标 completed。
6. 快速重复发送相同消息和重复点击安装/创建，验证幂等和去重。
7. 用其他 tenant/工作区深链访问 K22 资源，UI 与服务端均拒绝且不泄露资源存在性。
8. 删除/禁用操作必须有确认；存在员工或安装引用时按设计阻断或明确级联影响。

## 6. 证据要求

每个阶段至少保存：

- commit、环境、时间、K22 脱敏 tenant 标识、工作区 slug、账号角色。
- 页面截图：两个 Runtime 列表/详情、CLI 安装、MCP 连接、Skill 安装、员工绑定、两次任务结果。
- 资源 ID 与状态时间线；Secret 字段只记录 `configured=true` 或脱敏指纹。
- 浏览器 console error、失败请求状态码/request ID、脱敏响应摘要。
- 任务调用审计、成本与产物的关联标识。

trace、HAR 或录屏若可能包含会话数据，必须先脱敏或不保留。

## 7. 清理顺序

按依赖反序清理，避免孤儿记录：

1. 停止/等待本轮任务结束，确认无 running/queued 操作。
2. 从两名员工解绑 Skill，删除本轮员工。
3. 卸载两个 Runtime 的 Skill 安装。
4. 停用并移除两个 Runtime 的 MCP 连接，轮换/删除测试 Secret。
5. 停用并卸载两个 Runtime 的 CLI 应用。
6. 删除两个 Runtime；等待托管环境清理完成，不只删除 UI 记录。
7. 删除本轮 Skill/目录测试项；保留系统公共目录项。
8. 搜索 `QA-0804-K22-`，确认任务、安装操作、连接和后台清理无活动残留。

审计记录按产品保留策略留存，不应为了“清零”直接删除；执行记录注明其 ID 和保留原因。

## 8. 暂停条件

出现以下任一情况立即停止对应写操作：跨 tenant 数据可见、Secret 回显、任务误用其他 Runtime、重复计费/重复部署、删除影响非本轮资源、数据库或外部依赖疑似生产、后台操作无法停止。先保留脱敏证据并确认隔离，再恢复测试。
