# CLI 与 MCP 市场产品优化

> 日期：2026-08-04
>
> 状态：产品设计提案，待评审
>
> 范围：应用市场中的 CLI 数据源、新增 CLI、CLI 安装及 MCP 发布/连接体验

## 结论

当前产品已经具备 CLI 目录同步、Runtime 私有安装、安装验证、Skill 同步，以及 MCP 目录发布、连接、工具授权和验证等后台能力，但前台信息架构没有完整表达这些能力。

本次审查的核心结论是：

1. **有必要支持新增 CLI**，优先提供“工作区私有 CLI”受控发布，不应开放任意 shell 命令安装。
2. **暂时没有必要继续增加新的公共聚合源**。应先补齐来源身份、同步健康、版本不可变、兼容性和审核状态，再开放来源适配器。
3. CLI 当前已有 `clihub_harness`、`clihub_public`、`skill_dependency` 三个底层来源。当前工作树虽已增加来源筛选，但直接展示底层 key；详情仍只映射为 `CLI-Anything harness` 或 `Public CLI`，会误标 `skill_dependency`，也无法区分平台固定条目与上游社区条目。
4. CLI 和 MCP 应继续保留不同操作语义：CLI 是“安装到 Runtime”，MCP 是“配置并连接”。对于 `managed_stdio` MCP，产品应把依赖 CLI 安装、密钥配置、工具授权和连接验证组织成一个有步骤的流程。
5. “添加到目录”“安装到 Runtime”“配置连接”“在任务中可用”是四个不同状态，必须在界面和数据模型中分开。

## 决策边界

本方案不改变以下基础边界：

- Runtime 安装仍使用受控 argv 计划，不执行浏览器提交的 shell 字符串；
- 工作区私有 MCP release 仍为高风险，并经过工具授权与连接验证；
- `streamable_http` MCP 不安装到 Runtime；
- `managed_stdio` MCP 只能引用已安装的受控 entrypoint；
- 凭据不回显，不进入 Provider 容器或 Runtime HOME；
- 不新增 PostgreSQL、Redis 或 RabbitMQ 部署服务。

## 研究限制

本次结论基于代码、既有产品文档、测试用例和 2026-08-04 对上游 CLI-Anything 目录的只读抽样，尚未完成真实用户访谈、卡片分类或可用性测试。因此本文给出了可验证假设与测试计划，不把推断描述成已验证用户事实。
