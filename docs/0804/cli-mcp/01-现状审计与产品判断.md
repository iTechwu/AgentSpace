# 现状审计与产品判断

## 1. 审查问题

本次审查回答四个问题：

1. CLI 市场的数据来自哪里，用户能否理解其来源和可信度？
2. 是否需要让管理员添加新的 CLI？
3. 当前如何添加 CLI/MCP，目标流程应如何设计？
4. CLI 安装和 MCP 连接的体验怎样统一，但又不混淆语义？

## 2. 当前信息架构

```text
应用与服务市场
+-- CLI 应用（默认 Tab）
|   +-- 搜索
|   +-- 类别 / 来源 / 安装状态 / 风险筛选
|   +-- CLI 目录列表
|   +-- 详情
|       +-- Source / Version / Entry point / Strategy / Skill / Requires
|       +-- 目标 Runtime
|       +-- 安装 / 更新 / 卸载 / 同步 Skill
|       +-- install_cmd 预览
|   +-- 按应用分组的 Runtime 安装记录
+-- MCP 服务
    +-- 搜索
    +-- 类别 / 来源 / 传输 / 风险 / 连接状态 / Runtime 筛选
    +-- MCP 目录列表与详情
    +-- 添加 MCP 服务
    +-- Runtime 组件安装（managed stdio）
    +-- Endpoint / 配置 / 密钥 / 工具授权
    +-- 配置并连接
    +-- 已连接服务管理
+-- Runtime 详情
    +-- CLI 与 MCP 能力概览
    +-- 针对当前 Runtime 的安装/连接入口
    +-- CLI/MCP 操作记录
```

CLI 与 MCP 已经被放在同一个能力市场中，Runtime 详情也开始提供按执行环境管理能力的入口，这是合理的双入口结构；主要问题发生在来源表达、动作层级、两个入口的一致性和安装进度反馈上。

## 3. CLI 数据源事实

### 3.1 底层来源

| 底层 source | 进入目录的方式 | 当前产品含义 | 当前 UI 呈现 |
| --- | --- | --- | --- |
| `clihub_harness` | 同步 CLI-Anything `registry.json` | CLI-Anything harness | `CLI-Anything harness` |
| `clihub_public` | 同步 CLI-Anything `public_registry.json`，并接收平台代码写入的固定条目 | 公共第三方 CLI 与平台固定 Runtime 组件混合 | `Public CLI` |
| `skill_dependency` | Skill 依赖审批后由服务层生成 | 某 Skill 的受控依赖，不是公共市场来源 | 被错误显示为 `Public CLI` |

证据：

- 同步目标固定在 [`packages/services/src/clihub/catalog.ts`](../../../packages/services/src/clihub/catalog.ts)；
- source 联合类型定义在 [`packages/db/src/types.ts`](../../../packages/db/src/types.ts)；
- `skill_dependency` 由 [`packages/services/src/skills/dependency-install.ts`](../../../packages/services/src/skills/dependency-install.ts) 生成；
- Chrome DevTools MCP、MiniMax Token Plan MCP 的 Runtime 组件由 [`packages/services/src/mcp-center/official-catalog.ts`](../../../packages/services/src/mcp-center/official-catalog.ts) 写入 `clihub_public`；
- CLI 详情中的二元来源映射位于 [`apps/web/features/market/market-page-client.tsx`](../../../apps/web/features/market/market-page-client.tsx)。

### 3.2 当前同步机制

- harness 目录只请求 GitHub Pages 地址，没有 raw GitHub fallback；
- public 目录先请求 GitHub Pages，失败后回退 raw GitHub；
- 两个来源并行请求，单个来源失败不会阻止另一个来源写入；
- 当页面加载且本地目录为空时自动同步，管理员也可以手动“刷新目录”；
- 页面收到 `catalogHealth`，但没有展示最后同步时间、陈旧状态或分来源错误；
- 数据库按 `source + name` upsert，目录条目不是不可变 release。
- 当前工作树已增加 CLI 来源、风险和安装状态筛选，但来源选项直接展示 `clihub_harness` 等内部 key，未提供用户可理解的来源标签、说明或可信度边界。

### 3.3 2026-08-04 上游抽样

只读抽样结果用于判断数据质量，不作为永久数量承诺：

| 目录 | 条目数 | 观察 |
| --- | ---: | --- |
| CLI-Anything harness registry | 79 | 31 个自由文本类别；5 个条目没有 `skill_md` |
| CLI-Anything public registry | 22 | 12 个自由文本类别；13 个版本为 `latest`；2 个没有 `install_cmd`；15 个声明账号、密钥、登录、本地应用或运行中服务依赖 |

上游来源：

- [CLI-Anything registry.json](https://raw.githubusercontent.com/HKUDS/CLI-Anything/main/registry.json)
- [CLI-Anything public_registry.json](https://raw.githubusercontent.com/HKUDS/CLI-Anything/main/public_registry.json)
- [CLI-Anything 贡献规范](https://github.com/HKUDS/CLI-Anything/blob/main/CONTRIBUTING.md)

这些数据说明目录“可发现”不等于“可在远程 Runtime 安装”。桌面应用、Homebrew、`curl | bash`、本机服务、`latest` 和需交互登录的条目都需要兼容性与安全 gate，不能只靠风险圆点表达。

## 4. MCP 来源事实

MCP 底层来源更清晰：

| source | 含义 | 创建方式 |
| --- | --- | --- |
| `official` | 平台维护并固定 release 的服务 | 服务端目录同步/种子 |
| `verified_partner` | 经过平台或合作方审核 | 数据模型已支持，当前页面没有发布入口 |
| `workspace_private` | 当前工作区管理员发布 | “添加 MCP 服务”表单 |

MCP UI 已提供来源筛选，但详情事实区没有直接展示来源；新增表单一次性要求管理员填写 release、transport、endpoint、工具、配置字段、密钥字段、数据域等信息，认知负担较大。

## 5. 主要体验问题

| 严重度 | 问题 | 用户影响 | 产品风险 |
| --- | --- | --- | --- |
| P0 | `skill_dependency` 被显示为 `Public CLI` | 管理员误判来源和可复用范围 | 审计信息不可信 |
| P0 | 公共目录条目出现 `latest`、缺少安装命令或需要本机依赖，但页面仍提供统一“安装”动作 | 用户把“目录存在”误解为“目标 Runtime 可安装” | 高频失败、供应链风险 |
| P1 | CLI 来源筛选直接展示底层 key，且没有来源说明、同步时间和陈旧状态 | 能筛选但仍无法判断数据是谁维护、是否最新 | 目录故障难定位 |
| P1 | CLI 没有“添加 CLI”入口 | 私有工具无法进入市场，只能改代码或上游提 PR | 企业/内部工具场景被阻断 |
| P1 | 市场和 Runtime 页能显示安装/操作状态，但后台步骤仍不可见 | 长操作缺乏反馈，失败后不知道重试哪一步 | 重复点击、运维工单增加 |
| P1 | 市场与 Runtime 详情各有一套 CLI/MCP 操作界面，字段、主动作和错误恢复尚未形成共享流程 | 用户从不同入口得到不同的信息密度 | 维护成本与行为分叉增加 |
| P1 | managed stdio MCP 的“安装 Runtime 组件”和“配置并连接”是两个按钮，但缺少步骤关系 | 用户不知道为什么连接按钮不可用 | CLI/MCP 依赖关系难理解 |
| P2 | CLI 类别直接使用上游自由文本，MCP 类别使用受控枚举 | 同一市场分类语言不一致 | 筛选不可扩展 |
| P2 | CLI 详情中 `Source`、`Version` 等字段未本地化 | 中英文体验不一致 | 降低完成效率 |
| P2 | install command 原样预览，但实际执行的是服务端受控计划 | 用户可能误以为会直接执行预览字符串 | 透明度表达失真 |

## 6. 当前用户旅程

| 阶段 | 用户动作 | 系统反馈 | 主要痛点 | 机会 |
| --- | --- | --- | --- | --- |
| 发现 | 进入市场，在 CLI/MCP Tab 间切换 | 显示目录和数量 | CLI 来源含义不清；类别碎片化 | 增加可信来源、兼容性与可用状态 |
| 判断 | 阅读详情，选择 Runtime | 展示风险、依赖和安装状态 | 目录元数据未转成可操作的兼容性结论 | 增加 Runtime 预检与阻断原因 |
| 安装 CLI | 点击安装 | 操作排队，轮询状态 | 看不到下载、安装、验证的阶段 | 统一步骤进度与失败恢复 |
| 连接 MCP | 安装依赖、填密钥、授权工具并连接 | 连接排队验证 | 多个前置条件同时出现在一个长详情面板 | 使用有状态步骤器和渐进披露 |
| 使用/维护 | 同步 Skill、更新/卸载、重新验证 MCP | Toast 和状态更新 | CLI 与 MCP 状态分散，缺少统一健康视图 | 按 Runtime 聚合能力健康和修复动作 |

## 7. 是否需要新增 CLI 能力

### 决策：需要，但分两层实施

**第一优先级：允许管理员添加工作区私有 CLI。** 这是内部开发工具、自建脚本、专有业务 CLI 和未进入公共市场的 MCP stdio server 的必要入口。

**第二优先级：开放新的目录来源适配器。** 只有在平台具备来源健康、签名/摘要、不可变版本、审核状态、下架和兼容性投影后，才接入新的公共聚合源。

### 不建议的方案

- 不提供“粘贴任意安装命令并执行”；
- 不把 npm、PyPI、GitHub 等简单等同于可信来源；
- 不让管理员用一个可变 URL 覆盖既有 release；
- 不把 Skill 依赖自动提升为全工作区公共 CLI；
- 不为每个 MCP 单独再造一套安装器。

### 产品问题陈述

工作区管理员需要把可信的公共或内部 CLI 安全地提供给特定 Runtime，并清楚知道来源、版本、依赖、权限、安装进度和任务可用状态；当前市场只能消费固定上游目录，来源表达和兼容性不足，导致管理员无法安全扩展，也难以理解 CLI 与 MCP 的依赖关系。
