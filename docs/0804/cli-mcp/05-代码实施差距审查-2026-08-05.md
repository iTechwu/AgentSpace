## 1. 结论

现有实现已经完成 CLI/MCP 统一市场入口、CLI 来源/风险/安装状态筛选、失败记录展示、Runtime 能力管理和员工继承提示，但还不能满足方案中的安全发布门槛。

应先完成 P0 的安装资格阻断和来源事实修复，再继续扩充目录。当前最严重的问题是：目录中的 `latest`、可变 Git `HEAD` 和不安全上游命令仍可能生成安装操作；高风险确认只是告知风险，不能替代服务端安全策略。

## 3. 规范符合性审查

### P0：必须先修复

| 差距 | 代码证据 | 风险 | 完成标准 |
| --- | --- | --- | --- |
| 未阻断可漂移 release | `packages/services/src/clihub/install-plan.ts` 在无 Git ref 时使用 `HEAD`；`packages/services/src/clihub/catalog-compatibility.ts` 存在无版本 npm override | 同名安装在不同时间得到不同产物，无法审计和复现 | `latest`、范围版本、无 Git commit/digest 的 release 不生成安装计划，服务端返回稳定错误码 |
| 不安全上游命令仍可能进入 CLI-Hub fallback | `packages/services/src/clihub/install-plan.ts` 仅将 shell 元字符标为高风险，确认后仍可排队 | 目录元数据可能间接触发任意 shell，违反“受控 argv”边界 | `curl | bash`、重定向、命令替换、链式命令等在服务端硬阻断；UI 同步禁用动作 |
| 缺少安装资格投影与 Runtime 预检 | `apps/web/features/market/market-page-loader.ts` 未返回 compatibility；服务端只检查在线、权限和风险确认 | 用户点击后才失败，无法保证所有可点击条目都通过预检 | 页面展示“可安装/需配置/不兼容”；服务端对版本、命令、桌面/交互依赖和 Runtime 工具链再次校验 |
| 来源事实错误 | CLI 详情使用二元映射，`skill_dependency` 被显示为 Public CLI；来源筛选显示内部 key | 管理员误判维护方、审核边界和复用范围 | 三类来源均使用稳定产品标签；`skill_dependency` 不再显示为公共 CLI |
| 目录健康未展示 | loader 返回 `catalogHealth`，客户端未渲染 | 用户无法判断目录是否陈旧；来源失败只存在于刷新反馈 | 页面显示最后成功同步时间、陈旧状态、条目数；后续补齐分来源错误持久化 |

## 4. 代码质量审查

本节只记录工程质量问题，不与规范缺失混算。

### 必须修复

- 用户可见行为已经增加，但本次实现提交没有同步更新产品文档；本审查文件补齐现状，后续每个阶段继续维护验收状态。
- Runtime 操作记录存在硬编码中文和固定中文日期，英文界面会出现混合语言。

### 建议重构

- `RuntimeCapabilitiesPanel` 同时承担完整市场数据、CLI 生命周期、MCP 配置、轮询、操作记录和渲染，职责过多。拆为 CLI、MCP、OperationHistory 三个能力组件，并只传当前 Runtime 的投影数据。
- active operation 状态在三个界面重复判断。应抽取共享谓词和状态标签，避免同一状态在不同入口产生分叉。
- provider Runtime 镜像为单一条目硬编码 Hacker Feeds，并为所有 provider 安装 Git，扩大镜像和攻击面。若无平台级使用证据，应改为按受管 release 安装或移除该特例。

## 5. 实施顺序

1. **P0-A 来源与健康事实**：修复来源标签、本地化详情、展示目录健康、补 harness raw fallback。
2. **P0-B 安装资格与服务端阻断**：禁止可漂移版本和不安全命令，输出结构化阻断原因，按 Runtime readiness 禁用安装。
3. **P1-A 共享状态与一致性**：统一 active 状态、日期/文案、筛选选择行为和错误恢复。
4. **P1-B MCP 单一主流程**：将 managed stdio 依赖安装与连接串成步骤器。
5. **P2 工作区私有 CLI**：先完成不可变数据模型和服务端校验，再开放管理员入口。
6. **P3 来源治理**：达到安装成功率、安全审查和来源健康可见性门槛后再实施。

## 7. 实施记录

### 2026-08-05：P0-A 来源与目录事实

- 已为 CLI 目录增加产品来源投影，平台固定 MCP Runtime 组件显示为“平台官方”，其他来源显示为“CLI-Anything 工具套件”“社区目录”或“Skill 依赖”；
- 已本地化 CLI 详情事实、风险和筛选标签，并让时间格式跟随当前语言；
- 已展示目录条目数、最后同步时间和陈旧状态；
- 已将原始命令明确标记为“上游安装声明”，说明服务端会生成受控执行计划；
- 已为 harness 目录增加 raw GitHub fallback；
- 待办：当前健康数据仍是聚合视图，分来源错误、最后成功时间和 revision 需要在 P3 数据模型中持久化。

### 2026-08-05：P0-B 安装资格与服务端阻断

- 已增加结构化安装资格：`installable`、`needs_configuration`、`unsupported`，并提供稳定错误码和所需 Runtime 工具链；
- 已在 loader、市场主动作和服务端排队接口复用同一组规则，前端禁用不能替代服务端校验；
- 已阻断 `latest`/范围版本、缺安装声明、缺入口、桌面或交互依赖、任意 shell 控制命令和未固定 artifact；
- CLI-Hub fallback 只接受完整白名单命令以及精确 npm/PyPI 版本或 40 位 Git commit，不再自动安装未固定版本的 `cli-anything-hub`；
- 已按目标 Runtime 的 npm、Python、pip、CLI-Hub readiness 禁用动作并展示修复原因；
- 已修正目录健康聚合，平台官方组件的刷新时间不再掩盖上游目录陈旧；
- 卸载不受新版目录资格影响，已安装的旧条目仍可安全移除。

### 2026-08-05：P1-A 状态与入口一致性

- 已提取共享 active operation 判断和 Runtime 安装资格投影，市场与 Runtime 详情使用相同状态与阻断原因；
- 已让 Runtime 安装记录的空状态、动作、状态和日期跟随当前语言；
- 已修复 MCP 筛选后列表与详情不一致，非编辑状态只展示当前筛选结果中的详情；
- 待办：CLI/MCP 服务端 operation 仍缺少可持久化阶段，managed stdio 仍需统一步骤器。

### 2026-08-05：P1-B managed stdio 单一主流程

- 市场页与 Runtime 详情页共用五步连接进度：Runtime、依赖 CLI、配置、工具权限、连接验证；
- managed stdio 只保留一个主动作，依赖未安装时继续安装固定版本 CLI，依赖就绪后继续验证并连接；
- 依赖 CLI 同步复用目录安装资格与 Runtime readiness，不能安装时直接展示稳定阻断原因；
- 已将 MiniMax API Key 与网络授权从 CLI 安装前置条件移回 MCP 连接配置，避免安全预检错误阻断官方组件安装；
- 待办：步骤状态目前由持久化 operation 汇总，后端仍需增加更细的下载、校验、安装和验证阶段。
