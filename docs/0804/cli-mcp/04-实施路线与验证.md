# 实施路线与验证

## 1. 实施原则

- 先修复来源事实和安装资格，再增加目录数量；
- 先复用现有 operation、Runtime 私有 HOME 和 MCP connection 能力，再改变界面组织；
- 每一阶段都可独立发布、回滚和测量；
- 工作区私有 CLI 首期只支持结构化 npm/PyPI release，不支持任意 shell；
- 目录同步与 Runtime 安装继续解耦。

## 2. 分阶段路线

### P0：修正事实与阻断误操作

目标：让当前目录不再误导用户。

- 修复 `skill_dependency` 的来源显示；
- 将平台固定 Runtime 组件显示为“平台官方”；
- CLI 详情字段本地化；
- 展示目录最后成功同步时间、陈旧状态和分来源错误；
- 对 `latest`、缺少安装命令、交互式/桌面依赖和当前 Runtime 不兼容条目禁用安装；
- 将 install command 预览改成“上游声明”，另行展示服务端规范化安装计划；
- managed stdio MCP 明确显示依赖 CLI 名称、固定版本和安装状态。

验收：管理员不会把 Skill 依赖误认为公共 CLI；所有可点击“安装”的条目都通过目标 Runtime 预检。

### P1：统一安装与连接步骤

目标：减少安装/连接中断和重复操作。

- 增加 `OperationStepper` 与 operation detail；
- CLI 安装显示预检、下载、安装、验证、记录阶段；
- managed stdio MCP 将依赖安装与连接配置串成一个流程；
- streamable HTTP MCP 跳过安装步骤；
- 列表、详情、Runtime 页复用同一状态投影；
- 失败提供修复动作、脱敏技术详情和幂等重试；
- 将当前来源/安装状态筛选改用统一产品标签，并补充兼容性筛选；
- 市场与 Runtime 详情复用同一套安装/连接流程组件和错误恢复规则。

验收：用户中途离开页面再返回，仍能恢复到正确 operation 和步骤；失败后不需要重新填写未受影响字段。

### P2：工作区私有 CLI

目标：让管理员无需改代码即可安全发布内部 CLI。

- 增加“添加 CLI”入口；
- 支持 npm/PyPI 精确版本和受管 manifest；
- 服务端解析 artifact、integrity、entrypoint 和依赖；
- 创建不可变工作区 release；
- 发布与安装分离；
- 记录 actor、来源、摘要、审批和下架状态；
- 支持从私有 CLI release 创建 managed stdio MCP release。

验收：管理员可在 5 分钟内发布并安装一个满足约束的内部 CLI；浏览器请求中不包含 shell 命令或 registry 凭据。

### P3：来源适配器与运营治理

目标：在可测量、可撤销的前提下扩展公共目录。

- 抽象来源适配器；
- package/release/source 分层；
- 引入来源级 revision、同步健康和变更审计；
- 支持 verified partner；
- 增加 yanked、replaced、deprecated 和 update available 状态；
- 建立来源准入与退出机制。

进入条件：P2 安装成功率、回滚率和安全审查结果达到目标，且来源健康 UI 已稳定运行至少一个发布周期。

## 5. 可用性测试

### 5.1 参与者

6 名目标用户：

- 3 名工作区管理员，日常管理 Runtime 或开发工具；
- 2 名开发者，了解 npm/PyPI 但不熟悉 MCP；
- 1 名安全/运维角色，关注来源和权限；
- 至少 2 名首次使用 AgentSpace 市场的用户。

### 5.2 任务

| 任务 | 成功标准 | 时间目标 |
| --- | --- | ---: |
| 找到一个平台官方 CLI，并说明其来源、版本和目标 Runtime 是否兼容 | 100% 完成，来源判断正确 | < 60 秒 |
| 添加一个固定版本的工作区私有 npm CLI | >= 85% 完成，无任意 shell 尝试 | < 5 分钟 |
| 安装 CLI 并定位一次 Node 版本不兼容错误 | >= 90% 找到失败步骤和修复动作 | < 2 分钟 |
| 连接 streamable HTTP MCP | >= 90% 完成，理解“连接”而非“安装” | < 4 分钟 |
| 连接依赖 CLI 的 managed stdio MCP | >= 85% 完成，不遗漏依赖安装 | < 6 分钟 |
| 对已连接 MCP 轮换密钥并重新验证 | >= 85% 完成，理解密钥不会回显 | < 3 分钟 |

记录任务完成率、耗时、错误次数、退回次数和术语理解；测试后填写 SUS。所有严重问题按以下等级记录：

- `Critical`：无法完成、可能执行错误/不安全操作；
- `Major`：需要帮助或多次试错；
- `Minor`：能完成但明显犹豫或效率低；
- `Cosmetic`：不影响完成。

进入开发前应至少完成 5 名用户的中保真原型测试。若无法立即招募，P0 可以作为事实修复先行，但 P2“添加 CLI”不应在未经任务测试的情况下全量开放。

## 6. 自动化验收矩阵

| 场景 | 必测结果 |
| --- | --- |
| `skill_dependency` 出现在 CLI 详情 | 显示“Skill 依赖”，不显示 Public CLI |
| 上游目录一个来源失败 | 另一个来源继续可用，失败来源标记陈旧并显示最后成功时间 |
| release 使用 `latest` | 禁止直接发布/安装，要求选择固定版本 |
| install command 包含 `curl | bash` | 不生成可执行计划，展示不可安装原因 |
| Runtime 不满足 Node/Python | 主动作禁用，提供更换 Runtime/修复入口 |
| 安装过程中刷新页面 | 恢复相同 operation 与步骤 |
| verifyCommands 失败 | 安装不进入“已就绪”，保留脱敏错误和重试动作 |
| streamable HTTP MCP | 不出现 Runtime 组件安装步骤 |
| managed stdio 依赖未安装 | 连接流程先进入依赖安装，连接按钮不绕过 |
| MCP 密钥保存后 | 不回显，不出现在日志、URL、Provider 环境或任务 bundle |
| 工作区成员访问添加入口 | 入口隐藏/只读，服务端继续拒绝越权 |
| 移动端 320px | 无水平溢出、底部动作不遮挡表单和错误摘要 |

## 7. 发布门槛

- P0、P1 相关单元、组件和最小 E2E 测试通过；
- 关键安装路径在受限 worker 配置下验证，不使用本地 Jenkins；
- 安装计划、日志、Toast 和埋点完成敏感信息检查；
- 工作区私有 release 可下架但不可静默覆盖；
- 至少完成 happy path、版本不存在、Runtime 不兼容、安装验证失败、MCP 认证失败五类真实流程验证；
- 产品、工程和安全共同确认 `source`、`risk`、`compatibility` 三者没有被合并成一个含糊标签。

## 8. 待确认决策

1. 工作区私有 CLI 首期是否允许私有 npm/PyPI registry，还是只允许平台公共 allowlist；
2. `skill_dependency` 是否应出现在 CLI 市场，还是仅在 Skill/Runtime 依赖视图中展示；
3. 平台固定 MCP Runtime 组件是否迁移为独立 `official` CLI source；
4. 工作区私有 CLI 是否需要双人审批，或仅 high risk 才需要；
5. 安装后“在任务中测试”使用现有任务队列还是增加专用 smoke operation。

建议默认决策：首期只允许平台 allowlist registry；`skill_dependency` 不进入公共 CLI 目录，只在依赖视图可见；官方组件迁移为 `official`；高风险 release 需要双人审批；smoke 复用受控 operation，不创建真实业务任务。
