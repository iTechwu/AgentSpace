## 1. 发布门禁

以下任一失败均不得开启 `TASK_QUEUE_BY_CONVERSATION=on`：

- 跨 Conversation 消息污染；
- 跨 Conversation Provider Session 复用；
- 同 Execution Lane 同时出现两个 running task；
- 旧会话因 `/new` 被取消、暂停或重排；
- `/new` 首条消息后回到旧 URL 或旧消息流；
- 无权限用户读取到其它 Conversation；
- active legacy task 在迁移中丢失完成结果。

## 3. 队列与并发测试

### 3.1 数据库单元测试

必须覆盖：

1. 相同 Lane：第一条 claimed/running 后，第二条不能 claim；
2. 相同 requester + employee、不同 Conversation：第二条可以 claim；
3. 相同 Runtime、不同 Lane：允许同时 claim；
4. 不同 employee、同 Conversation：不同 Lane 可并行；
5. 相同 Provider Session 不会出现在两个 active task；
6. legacy task 没有 Lane 时仍走兼容规则；
7. task 完成后同 Lane 下一条可 claim；
8. task failed/cancelled 后 Lane 解锁；
9. `preparing_commit` 仍占用 Lane；
10. 高优先级不会跳过同 Lane 更早的消息顺序。

### 3.2 并发 claim 竞态

使用两个独立数据库连接同时 claim 同一 Runtime：

- 同 Lane 两个 queued task，最终只能一个 claimed；
- 不同 Lane 两个 queued task，允许两个分别 claimed；
- 重试 claim 不重复创建 attempt；
- 事务回滚后 task 可被另一 claimant 正常领取。

### 3.3 Daemon 集成测试

- 同一 Runtime 启动两个不同 Lane 的 Provider 子进程；
- progress 事件分别回到正确 Conversation；
- 其中一条失败不终止另一条；
- Runtime maintenance 只能在 active task 清零后获得独占槽；
- capacity=1 时第二条显示 capacity wait，而不是跨会话逻辑排队；
- capacity=2 时两个 Conversation 并行。

## 4. Session 隔离测试

对每个支持的 Provider 执行：Codex、Claude、OpenCode、OpenClaw 及启用的其它 Provider。

| 检查 | A1 | A2 | 断言 |
| --- | --- | --- | --- |
| Router Session | R1 | R2 | `R1 != R2` |
| Provider Session | P1 | P2 | `P1 != P2` |
| WorkDir | W1 | W2 | 默认 `W1 != W2` |
| Inline history | H1 | H2 | 只含各自消息 |
| History path | HP1 | HP2 | 只指向各自历史 |
| Context snapshot | C1 | C2 | 不交叉引用 event |
| Token attribution | T1 | T2 | conversationId 正确 |

恢复 A1 后：Router Session 仍为 R1；若 P1 有效则 resume P1，失效时新建 P1b，但 Conversation 仍为 A1。

## 5. 消息一致性测试

- pending message 创建时带 conversationId；
- progress 只能更新相同 task + Conversation 的 pending；
- final replacement 不按员工名模糊匹配；
- 同一员工两个 Conversation 同时 pending 时不互换结果；
- replyToMessageId 必须属于当前 Conversation；
- attachment reference 必须属于用户可读 Conversation/channel；
- 实时事件乱序时按 task attempt 和 message revision 拒绝旧更新；
- reconnect 后通过 Conversation endpoint 补齐，不合并 channel 全量消息。

## 6. 迁移测试

### 6.1 Backfill

- 同一 legacy scope 只生成一个 deterministic Conversation；
- 回填重复运行不创建重复 Conversation/Lane；
- message 数量和顺序前后相同；
- task、execution event、token usage 保持可追溯；
- localStorage 内容不被当作权威消息上传。

### 6.2 活跃任务迁移

- running legacy task 在部署期间不中断；
- 其 Provider Session 不改变；
- 完成结果同时可在 legacy 页面和 Conversation V2 读取；
- 部署后创建的新 Conversation 可并行运行；
- 回滚 flag 后旧页面仍能看到完成结果。

## 7. 权限与安全

- 用户不能通过修改 conversationId 读取另一 workspace 数据；
- 用户不能向不属于所选 employee 的 Conversation 发消息；
- 浏览器提交的 employeeId/runtimeId/routerSessionId/providerSessionId 不可信；
- 服务端从 Conversation participant 和当前 runtime binding 重推导；
- 已失去 employee 使用权限时，历史可见性与继续发送权限分别判定；
- 管理员审计可查看 Conversation 元数据，但消息正文遵循现有权限；
- 删除/归档有审计事件；
- 日志不输出附件正文、Provider 凭据或不必要的消息全文。

## 8. 性能目标

| 指标 | 目标 |
| --- | --- |
| 创建 Conversation API p95 | < 300 ms |
| Conversation 历史首屏 p95 | < 500 ms |
| 消息分页 p95 | < 500 ms |
| send 到 queued/claimed projection p95 | < 500 ms |
| 无容量限制时跨 Conversation 额外等待 | < 1 个 poll interval |
| 同 Lane 顺序错误率 | 0 |
| 跨 Conversation 污染率 | 0 |
| 摘要 fallback 可见时间 | 消息持久化后立即 |
| 正式摘要更新时间 p95 | < 10 s，不阻塞聊天 |

压测至少覆盖：

- 单 workspace 10,000 Conversation；
- 单 employee 1,000 Conversation；
- 单 Conversation 10,000 message；
- 单 Runtime 20 个活跃 Lane；
- 历史分页与实时事件同时发生。

## 9. 可用性测试

### 9.1 参与者

- 6 名用户：3 名高频 AI 员工使用者、3 名新用户；
- 覆盖桌面宽屏和常见笔记本视口；
- 至少 2 名用户同时处理多个长任务。

### 9.2 任务

1. “让 Codex E2E 继续生成视频，同时新开会话排查脚本错误。”
2. “回到仍在运行的视频会话，查看进度。”
3. “通过 `/resume` 找到昨天的模型错误排查记录并继续。”
4. “判断当前看到的排队是本会话顺序还是 Runtime 资源等待。”
5. “把一个会话重命名后，在历史中重新找到它。”

### 9.3 成功标准

| 任务 | 完成率 | 时间 | 关键错误上限 |
| --- | --- | --- | --- |
| 新建并并行运行 | >= 95% | < 30 s | 0 次回到旧会话 |
| 切回后台会话 | >= 90% | < 20 s | <= 1 次误点 |
| `/resume` 找历史 | >= 90% | < 30 s | 0 次发送 `/resume` 给 AI |
| 理解等待状态 | >= 85% | < 20 s | <= 1 次误判 |
| 重命名并找回 | >= 90% | < 30 s | <= 1 次误点 |

整体 SUS 目标大于 80；若低于 68，不进入全面上线。

## 10. 观测与告警

### 10.1 业务指标

- 新 Conversation 创建成功率；
- `/new` 到首条消息转化率；
- 每 employee 活跃 Conversation 数；
- `/resume` 历史打开到选中率；
- 摘要生成成功率和用户重命名率；
- 空 draft 24 小时遗弃率。

### 10.2 正确性指标

以下指标非零立即 P0 告警：

- `conversation_session_crosslink_total`；
- `conversation_message_mismatch_total`；
- `conversation_result_wrong_thread_total`；
- `same_lane_concurrent_running_total`；
- `new_conversation_returned_to_previous_total`。

### 10.3 调度指标

- queue wait 按 Conversation/Lane 分布；
- capacity wait 按 Runtime 分布；
- active lanes per runtime；
- claim conflicts 和 retry；
- Lane starvation 超过阈值的数量；
- legacy fallback task 比例，目标逐步降到 0。

## 11. 上线顺序

1. 开启双写和 shadow claim；
2. 内部 workspace 开启 Conversation V2；
3. 检查 48 小时隔离指标；
4. 5% workspace 开启 Lane claim；
5. 25%、50%、100% 逐级扩大，每级至少观察一个高峰周期；
6. 完成 legacy backfill；
7. 开启服务端历史；
8. 收紧 NOT NULL 和移除 fallback。

任一 P0 指标非零，立即关闭相应 read/claim flag，保留双写数据用于复盘，不执行破坏性回滚。
