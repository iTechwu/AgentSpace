# AI员工 Runtime、模型与计费产品需求及交付规格

## 1. 问题与目标

### 1.1 已确认的业务约束

1. `DOFE_AGENT_RUNTIME_MODE` 是部署级配置，在实例启动时读取；未设置时默认为 `local`。`remote` 是服务器模式的正式值，不得使用 `server` 作为配置值，也不得在 Runtime 创建页让用户切换模式。
2. `local` 保持既有本地 Runtime、Provider 连接、模型、用量和错误处理行为，不要求用户重新配置或迁移。
3. `remote` 时，用户不允许手工进入服务器部署 Runtime、登录 Provider CLI、复制 API Key 或配置模型 Base URL。
4. 一个 Runtime 可以服务多个 AI员工；不同 AI员工可以选择不同的默认模型。
5. 模型必须与 Runtime 的实际协议兼容，不能在 Claude Code Runtime 中选择
   不支持 Anthropic 协议的模型，也不能在 Codex Runtime 中选择不支持 OpenAI
   协议的模型。
6. `remote` 成本由 `models.dofe.ai` 按 API Key、tenant、team 结算；AgentSpace 需要在
   AI员工、任务和会话层提供可解释的成本分配和审计。
7. 服务器 Runtime Key 应长期可用，但失效、撤销或认证异常时必须由系统自动申请替换并恢复
   Runtime，不能要求用户处理服务器。
8. 用户界面中原本代表数字员工的 “Agent” 文案统一改为 “AI员工”
   （英文为 “AI Employee”）。内部技术标识不在首期重命名范围。
9. 团队可见角色仅保留 `Owner`、`Admin`、`Member`；不引入按资源、动作或
   财务职责拆分的复杂角色体系。
10. `Owner` 与 `Admin` 都是团队管理员，均具备团队管理、财务/运营及全部
   AI员工操作能力；当前版本的 AI员工不对 `Member` 开放操作权限。
11. 平台超管是平台运维身份，不是 team/tenant 成员。超管继承全部 team/tenant
   管理员能力，但不得出现在成员列表、转移目标、分配对象或邀请选择器中。

### 1.2 产品问题陈述

在 `remote` 部署中，团队管理员目前需要理解 Provider、Docker、CLI 登录、Base URL、模型协议和
计费密钥，才能让一个 AI员工开始工作。这既降低交付速度，也让团队隔离、
费用归属和审计无法稳定执行。

本方案仅在 `remote` 部署中让管理员选择 Runtime 类型和模型策略；系统负责安装、凭据、
协议校验、健康检查、轮换与账单关联。`local` 部署继续使用现有产品路径。

### 1.3 成功定义

1. `remote` 部署中的管理员可以在界面发起 Runtime 创建，看到完整进度和失败原因，而不是等待
   一个长期阻塞的请求。
2. Runtime 就绪前，用户不会看到可被错误调度的 AI员工或模型。
3. `remote` 的模型选择来自 models 的兼容目录，并在执行前再次校验。
4. `remote` 团队能查看余额、Runtime 实际用量、AI员工预估/已对账成本和未分配成本。
5. `remote` Key 失效后，系统能在受控重试下自动恢复或明确告警。

### 1.4 待验证的产品假设

当前结论来自已确认的业务约束，尚未完成真实用户访谈。进入开发前需至少验证：

| 假设 | 验证方法 | 通过标准 |
| --- | --- | --- |
| 管理员更需要“进度和下一步”而非底层安装日志 | 访谈 3 名管理员，观察现有安装流程 | 3/3 认为步骤状态足够判断是否需要介入 |
| AI员工默认模型与会话 `/model` 的分层可被理解 | 5 名目标用户完成模型选择原型任务 | 80% 能正确说明哪个范围会受影响 |
| “预估 / 已对账 / 未分配”成本状态可建立信任 | 财务或运营角色访谈 3 人 | 80% 能判断哪个数值可用于正式结算 |

## 2. 领域术语与责任边界

| 产品术语 | 含义 | 责任方 |
| --- | --- | --- |
| AI员工 | 用户可配置、可执行任务的数字员工 | AgentSpace |
| 运行模式 | 实例启动时决定保持既有本地路径，或启用受管服务器和 models | AgentSpace 部署配置 |
| Runtime | 服务器模式中安装有 Provider CLI 的受管执行环境 | AgentSpace |
| 本地服务连接 | 既有本机服务及其模型能力 | AgentSpace 既有本地模式实现 |
| Runtime Key | 仅属于一个 Runtime 的 models 网关 API Key | models 创建，AgentSpace 编排 |
| 模型网关 | `model.local.dofe.ai/api` 数据平面，负责协议代理、路由与实际计费 | models |
| 模型目录 | 可见性、协议、健康状态和价格信息的权威集合 | models |
| 成本分配 | 将 Runtime 用量按任务归因给 AI员工的业务视图 | AgentSpace |
| 实际计费 | tenant/team/Key 在网关的真实扣费与余额 | models |

服务器模式（`DOFE_AGENT_RUNTIME_MODE=remote`）的 Runtime Key、模型网关、模型目录与实际计费只适用于 `remote`。本地模式保持既有产品与数据行为，不因本设计新增 Runtime Key、models 管理调用、状态或成本文案；两种模式不会自动切换。

产品文案统一使用 “AI员工”。下列技术名首期保留：`AgentRouter`、`agentId`、
数据库表名、SDK 名称、第三方协议中的 Agent。

## 3. 用户与核心旅程

### 3.1 角色

| 可见角色 | 产品定位 | 核心能力 |
| --- | --- | --- |
| Owner | 团队管理员与归属主体 | 拥有 Admin 的全部能力，并可执行 team/tenant 所有权转移；不另设“财务”“运营”“AI员工负责人”等角色。 |
| Admin | 团队管理员 | 管理团队、Runtime、模型、成本、审计和全部 AI员工；不能执行 team/tenant 所有权转移。 |
| Member | 普通团队成员 | 不管理团队、Runtime、模型、成本或审计；当前版本不可创建、配置、执行、启停或删除任何 AI员工。 |

除所有权转移外，`Owner` 与 `Admin` 的日常业务权限保持一致，目的是让团队管理
足够简单；产品不应为财务、运营、AI员工负责人、会话成员等概念创建额外角色或
权限包。所有权转移仅可在 Owner 发起的既有生命周期流程中执行，且最后一位 Owner
不得离开团队或被降级。

### 3.2 平台超管与成员隐身规则

平台超管仅在平台运维控制台中出现，并在执行平台运维、故障恢复、合规处置时
继承任意 tenant/team 的 `Owner`、`Admin` 管理能力。超管不是该 tenant/team 的
成员记录，因此必须遵守以下边界：

1. team/tenant 的成员列表、角色筛选、邀请、所有权转移、资源转移和 AI员工
   分配选择器均不得返回或展示超管账号。
2. 超管不可成为用户可选择的资源负责人、AI员工负责人或团队成员；平台授权
   不通过向 team/tenant 写入成员关系来实现。
3. 团队侧审计若必须展示平台介入，应显示为“平台运维”，不展示个人超管身份或
   将其误显示为团队成员；平台侧审计保留实际超管身份、原因、目标范围和时间。
4. 超管访问遵循最小必要范围和可追溯原则。它不改变团队成员对“谁属于本团队”
   的可见认知，也不参与团队内的转移与分配流程。

> 当前实现状态（2026-07-28 核实）：团队侧权限校验依据 `workspace_membership` 的
> `Owner/Admin/Member` 角色，不引入平台超管作为成员记录——**已实现**：SSO
> `authoritativeUser.isAdmin` 持久化到 `users.is_admin`；超管登录不写入成员关系，
> 访问团队时由 `server-workspace-resolver` 合成内存中的 Admin 权限（跨 tenant/team
> 覆盖已具备）；成员列表/计数/所有权转移均排除超管；团队侧审计以“平台运维”匿名化，
> 平台侧 `platform-audit` 账本保留真实操作者；`/platform/audit` 路由已存在。**导航与
> 控制台**（2026-07-28 已闭环）：侧栏新增仅超管可见的“平台运维”入口，并新增 `/platform`
> 跨团队只读运维看板（工作区 / 受管 Runtime 数·在线·需关注·周期成本 / 最近平台审计），
> 仍遵循上述边界。

### 3.3 旅程 A：管理员在服务器模式创建 Runtime

| 阶段 | 管理员行为 | 系统反馈 | 风险与设计机会 |
| --- | --- | --- | --- |
| 进入 | 打开“执行环境” | 显示可用 Runtime、容量、状态、创建入口 | 不把 Provider 配置暴露给用户 |
| 选择 | 选择 Provider/协议、目标服务器、Runtime 名称和默认模型 | 只显示兼容模型与价格摘要 | 先解释“此 Runtime 可服务多个 AI员工” |
| 确认 | 提交创建 | 创建异步安装任务 | 明确“系统将自动配置模型网关凭据” |
| 安装 | 查看状态和日志摘要 | 显示安装阶段、耗时、可取消性、重试条件 | 不展示 Key、命令或敏感路径 |
| 就绪 | 绑定 AI员工或创建 AI员工 | 展示协议、默认模型、健康状态与可用模型数 | 防止未健康 Runtime 被选择 |

### 3.4 旅程 B：为 AI员工选择模型并在会话中临时切换

| 阶段 | 用户行为 | 系统行为 |
| --- | --- | --- |
| 配置 AI员工 | 选择已就绪 Runtime，可选“AI员工默认模型” | 默认继承 Runtime；仅显示该 Runtime 可用模型 |
| 发起会话 | AI员工接收任务 | 解析有效模型：会话覆盖 > AI员工默认 > Runtime 默认 > 团队策略 > 协议兜底 |
| 临时切换 | 输入 `/model <modelId>`（群聊需 @AI员工）或点击聊天顶部模型菜单 | `/model` 与顶部模型菜单已落地：仅更新当前会话，Owner/Admin 可用；直接私聊顶部显示当前生效模型与来源，并支持选择/清除覆盖 |
| 执行与查看 | 发送任务 | 在任务详情记录请求模型、实际模型、token、预估成本与状态 |
| 会话结束 | 结束或归档会话 | 覆盖自然失效，下一会话回到 AI员工/Runtime 默认 |

### 3.5 旅程 C：Key 失效与自动恢复

| 阶段 | 触发 | 用户体验 |
| --- | --- | --- |
| 发现异常 | 网关 401、Key 失效、健康检查失败 | Runtime 标为“凭据恢复中”，不把错误归咎于用户 |
| 自动处理 | AgentSpace 创建轮换任务并向 models 请求替换 Key | 页面展示“正在更新模型凭据”，保留可查看的脱敏原因 |
| 验证 | 新 Key 健康检查成功 | Runtime 恢复可用；旧 Key 由系统撤销 |
| 失败升级 | 多次失败、余额不足、模型无可用端点 | 状态改为“需要处理”，给出具体动作：充值、检查模型、联系运维 |

### 3.6 本地兼容边界

`local` 是默认部署模式，不新增创建向导、受管任务、凭据恢复、模型目录、费用状态或
故障旅程。既有本地服务不可用时，继续沿用当前产品的提示和恢复方式；不得自动创建
服务器 Runtime、申请 Runtime Key 或要求用户切换模式。

## 5. 关键页面与交互规格

### 5.1 Runtime 列表

每个 Runtime 行/卡片必须固定展示：

```text
名称 | Provider/协议 | 状态 | 默认模型 | 已服务 AI员工数 | 最近心跳 | 本周期实际成本
```

状态使用语义色和文字，不能仅依赖颜色：

| 状态 | 含义 | 可用操作 |
| --- | --- | --- |
| 准备中 | 安装任务未完成 | 查看任务、取消（允许时） |
| 可用 | 已验活且可执行 | 查看、编辑默认模型、轮换 Key、停用 |
| 凭据恢复中 | 正在轮换 Key | 查看恢复任务；不可手工编辑 Key |
| 需要处理 | 自动恢复失败或余额/兼容性阻断 | 查看原因、重试、联系运维 |
| 已停用 | 不再接受新任务 | 查看审计、删除（满足保留策略后） |

列表支持按 Provider、状态、团队、模型和“是否存在未分配成本”筛选。

### 5.2 服务器模式创建 Runtime 向导

向导采用三步，而不是在一个长表单中暴露基础设施字段：

```text
步骤 1：选择执行类型
  Provider Runtime、协议、目标服务器、名称

步骤 2：选择模型策略
  Runtime 默认模型、模型能力、价格摘要、可选模型范围

步骤 3：确认与创建
  自动配置项摘要、成本/余额预检、创建后行为
```

低保真布局：

```text
┌ 创建执行环境 ─────────────────────────────────────────────┐
│  1 执行类型  ━━━  2 模型策略  ━━━  3 确认                 │
│                                                            │
│  Runtime 名称  [________________________]                 │
│  执行类型      [Claude Code Runtime v]                     │
│  目标服务器    [受管服务器 A              v]               │
│                                                            │
│  系统会自动：安装批准的 CLI、创建 Runtime Key、配置网关。 │
│                                                            │
│                                      [取消] [下一步 →]     │
└────────────────────────────────────────────────────────────┘
```

模型选择器每项显示模型名、协议标签、上下文长度、工具调用/视觉能力、健康状态和价格
摘要；不可选项可以显示但必须解释原因。

提交前调用 models 余额/预算预检。预检失败时禁止创建，但允许用户返回调整模型或查看
余额；不能将失败伪装成安装失败。

### 5.3 Runtime 创建任务详情

```text
┌ Runtime：研究 Claude Runtime                         准备中 ┐
│ 请求时间 10:24   已耗时 02:14   可安全取消：否              │
│                                                                │
│ ✓ 校验目标服务器                                                │
│ ✓ 分配模型网关凭据                                              │
│ ● 安装 Claude Code                                  进行中     │
│ ○ 配置运行环境                                                  │
│ ○ 健康检查                                                       │
│ ○ 注册执行环境                                                   │
│                                                                │
│ 日志摘要：正在拉取批准的运行镜像。敏感内容已隐藏。             │
│                                    [关闭] [取消任务]            │
└────────────────────────────────────────────────────────────────┘
```

交互要求：

- 任务状态可轮询或订阅刷新；刷新不改变用户当前位置。
- 日志只显示结构化、脱敏摘要；Key、Bearer、完整环境变量、主机私密路径必须隐藏。
- 失败状态显示错误分类、受影响步骤、是否可重试、推荐操作和关联审计 ID。
- 用户可取消时显示取消后果；已创建 Key 的取消必须等待撤销/清理完成。

### 5.4 AI员工模型设置

AI员工表单中的模型字段名称为“AI员工默认模型”，并标注继承关系：

```text
执行环境：研究 Claude Runtime
Runtime 默认模型：claude-compatible-coding
AI员工默认模型：[继承执行环境默认模型 v]
```

选择不同模型时，只展示该 Runtime 的协议兼容模型。若管理员之后修改 Runtime
默认模型，仅继承 Runtime 的 AI员工受影响；已有 AI员工显式设置的默认模型不变。
该表单及 AI员工的创建、执行、启停、删除仅对 Owner 和 Admin 开放。

### 5.5 会话 `/model`

会话顶部显示紧凑、可扫描的模型状态，而不是在输入框旁长期展示复杂配置：

```text
当前：coding-pro · 会话覆盖
[切换模型] [恢复 AI员工默认]
```

`/model` 建议交互：

```text
/model              打开当前会话的可选模型列表
/model <alias>      选择兼容模型并确认
/model reset        清除会话覆盖，恢复 AI员工或 Runtime 默认
```

变更确认文案必须说明范围：“仅影响当前会话之后的新任务，不影响其他 AI员工、
会话或执行环境。”执行中的任务不被中断。当前版本仅 Owner 和 Admin 可以发起
AI员工会话与使用 `/model`；Member 不显示 AI员工操作入口。

## 6. 产品规则与异常处理

| 场景 | 前端表现 | 服务端规则 |
| --- | --- | --- |
| 无兼容模型 | 禁用继续创建，显示协议/可见性原因 | 不创建 Runtime Key |
| 余额不足 | 显示余额不足与余额入口 | 预检拒绝，不开始安装 |
| 目标服务器离线 | 显示“等待服务器上线”或失败 | 可重试；不重复创建 Key |
| CLI 安装失败 | 显示失败步骤和脱敏摘要 | 清理安装资源并撤销未使用 Key |
| Runtime 验活失败 | 状态为“需要处理” | 不注册为可调度 Runtime |
| `/model` 不兼容 | 保持原模型并在聊天顶部显示不可用原因与可选项 | 拒绝创建新任务覆盖，返回结构化错误码 |
| Runtime Key 失效 | 显示“凭据恢复中” | 创建幂等轮换任务，成功后撤销旧 Key |
| 网关用量无法关联任务 | 在成本页列为未分配 | 不把费用猜测性归属 AI员工 |

## 7. 成本与审计体验

### 7.1 成本展示层级

| 页面 | 数值 | 标记 |
| --- | --- | --- |
| 团队余额 | models 余额和可用余额 | 实际余额，仅 Owner/Admin 可见 |
| Runtime 详情 | 当前 Runtime Key 的网关用量 | 实际成本，仅 Owner/Admin 可见 |
| AI员工详情 | 该 AI员工任务成本分配 | 预估 / 已对账，仅 Owner/Admin 可见 |
| 成本中心 | 未关联到 AI员工的 Runtime 用量 | 未分配，需关注，仅 Owner/Admin 可见 |

不能将“预估成本”与“models 实际成本”放在同一无标签数字中。金额、币种、时间范围、
数据更新时间和对账状态必须同时显示。

### 7.2 审计可读性

审计列表应可按 AI员工、Runtime、会话、任务、模型、操作者、时间和事件类型筛选，
且仅 Owner 与 Admin 可见。平台超管执行的必要介入在团队侧以“平台运维”显示，
实际超管身份仅保留在平台侧审计。
事件人类可读标题示例：

- “李明将研究助手的默认模型从 A 调整为 B”
- “系统为研究 Claude Runtime 轮换了模型网关凭据”
- “会话 #研发讨论 将模型切换为 B，仅影响后续任务”
- “研究 Runtime 因余额不足未启动任务”

审计详情展示关联 ID 与脱敏 Key 前缀，绝不展示明文 Key。

## 8. 服务器模式对 models.dofe.ai 的产品与接口要求

### 8.1 当前可复用能力

models 已经具备：按 API Key/tenant 的模型可见性、`/v1/models` 协议过滤、
OpenAI/Anthropic/Gemini 协议入口、team/tenant 余额、按 API Key 查询用量、
模型路由和现有 AI员工 Key。

### 8.2 必须新增或增强的能力

| 能力 | 目的 | 首期要求 |
| --- | --- | --- |
| Runtime Credential | 每个 Runtime 一把可管理网关 Key | 创建、状态、轮换、撤销、幂等性（已实施） |
| 内部兼容模型目录 | Runtime 创建页不复制协议过滤逻辑 | 按团队可见性、健康、协议、允许模型返回（已实施） |
| 用量关联字段 | 让 AI员工成本从预估进入已对账 | Runtime Key ID、实际模型、网关请求 ID、token 明细、实际金额（已实施） |
| 机器可读错误 | AgentSpace 能正确恢复或提示 | Key 失效、模型不可用、协议不兼容、余额不足、限流 |
| Key 轮换审计 | 安全与故障追踪 | 前后 Key ID、发起者、原因、结果，均不含明文 |

models 的内部管理 API 只由服务器模式的 AgentSpace 控制面使用。服务器 Runtime 进程
只能持有 Runtime Key，调用模型数据平面；不能拿到 models 的内部服务密钥，也不能创建、
轮换或撤销自己的 Key。本地模式不调用这些接口，也不持有 Runtime Key。

## 10. 可用性与无障碍验证计划

### 10.1 原型范围

中保真原型至少覆盖：

1. 创建 Claude Runtime 的完整成功路径。
2. 因模型协议不兼容被阻止的路径。
3. 安装失败并重试的路径。
4. AI员工选择默认模型、会话 `/model` 覆盖和 reset。
5. 成本页区分实际、预估、已对账和未分配成本。

### 10.2 测试参与者与任务

招募 5 至 8 名目标用户：3 至 5 名 Owner/Admin，以及 2 至 3 名 Member。Owner 与
Admin 覆盖团队管理、财务/运营和 AI员工操作任务；Member 验证不可操作 AI员工且
不会被引导进入无权限页面。

| 任务 | 成功标准 | 目标时长 |
| --- | --- | --- |
| 创建可用 Runtime | 90% 完成，且不尝试查找/填写 Provider Key | 3 分钟内 |
| 为 AI员工设置独立默认模型 | 85% 正确理解继承关系 | 90 秒内 |
| 在当前会话用 `/model` 切换并恢复 | 85% 正确说明影响范围 | 60 秒内 |
| 判断一项成本是否可用于正式结算 | 80% 正确区分预估、已对账、未分配 | 60 秒内 |
| 处理 Runtime 凭据恢复失败 | 80% 能找到推荐动作 | 90 秒内 |
| Member 尝试访问 AI员工操作 | 100% 被正确阻止且理解原因 | 30 秒内 |

记录完成率、完成时间、错误次数、严重性和 SUS。首个版本目标：核心任务完成率
大于 85%，SUS 大于 80，且无严重级别 1 的可用性问题。

### 10.3 无障碍要求

- 状态必须同时使用文字、图标和颜色，颜色对比度达到 WCAG AA。
- Runtime 进度使用语义化进度/状态区域，屏幕阅读器可获知步骤变化。
- 模型选择器支持键盘导航、搜索、选中状态和不可选原因。
- 任务日志摘要可复制，敏感内容被脱敏后仍保留错误上下文。
- 所有取消、轮换、删除操作在键盘和触屏场景下具有清晰确认与焦点管理。
