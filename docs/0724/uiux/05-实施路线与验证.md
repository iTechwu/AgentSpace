## 分期实施

### Phase 0：验证与基线（2--3 天）

1. 与 3 名内部用户进行 30 分钟上下文访谈：负责人、运营管理员、协作成员各至少 1 人。
2. 记录当前基线任务：定位离线引擎、更新 Runtime、找到待审批、创建任务、查看某个员工的执行状态。
3. 对现有导航进行闭合卡片分类，使用本方案的五个任务域，验证入口归属。
4. 在 1920、1440、1024、768、390px 对关键页截屏，记录溢出、折行和对比度缺陷。

### Phase 1：基础系统与外壳（3--5 天）

1. 在 `globals.css` 建立 token 层与 reduced-motion 规则。
2. 重构 `WorkspaceFrame`：248px 侧栏、64px chrome、任务域导航、移动抽屉。
3. 建立 `PageHeader`、`Toolbar`、`StatusBadge`、`MetricStrip`、`EmptyState`。
4. 通过视觉截图比对和既有导航测试，确保模块路由、权限和缓存预取不回归。

### Phase 2：执行引擎垂直切片（3--4 天）

1. 将容器页面改为实体页模板，先保留所有现有数据读取与 actions。
2. 从列表中移走删除和更新，落实详情主行动与更多菜单。
3. 构建活动时间线、诊断折叠区和空/错/离线状态。
4. 实现 [在线执行引擎接入向导](./06-引导与可点击性规范.md)，覆盖连接成功与认证失败恢复。
5. 对真实长名称、多个 Provider、0/1/N 工作区和认证失败进行验收。

### Phase 3：推广与收口（按模块迭代）

推广顺序：数字员工 -> 审批 -> 任务 -> 知识 -> 设置 -> 成本/绩效。每完成一个模块，必须复用既有骨架与 token；若需要新增模式，先在组件文档中补充契约。

## 原型与可用性测试

在 Phase 2 后，以中保真可点击原型或 staging 环境测试 5--8 名用户，其中至少 3 名为当前工作区用户。每位参与者完成以下任务：

| 任务 | 成功条件 | 目标 |
| --- | --- | --- |
| 找到需要处理的执行引擎 | 正确识别离线/认证异常并进入详情 | 完成率 >= 90%，中位时间 < 20 秒 |
| 更新一个指定 Runtime | 找到主要动作、理解确认信息并完成 | 完成率 >= 85%，中位时间 < 45 秒 |
| 找到待审批事项 | 从任一模块进入审批并识别风险 | 完成率 >= 90%，中位时间 < 25 秒 |
| 定位某数字员工的绑定引擎 | 通过团队域进入员工详情并看到绑定 | 完成率 >= 85%，中位时间 < 45 秒 |
| 接入在线执行引擎 | 选择接入方式、运行命令、校验心跳并完成命名 | 完成率 >= 85%，中位时间 < 3 分钟 |

记录完成率、耗时、错误数、主观难度和 SUS。若 SUS < 68，或任何核心任务完成率 < 85%，优先修复阻塞项再扩展到其他模块。

## 设计 QA 清单

- [ ] 1920px 下实体页列表至少 304px、详情至少 720px；没有折成多列的运行时名称。
- [ ] 1440px 下侧栏、列表和详情均可独立扫描，主内容没有横向滚动。
- [ ] 1024px 下侧栏收起或抽屉化，详情不与列表并排挤压。
- [ ] 768px 与 390px 下可从详情安全返回列表，所有文本和按钮完整可见。
- [ ] 状态不只靠颜色；离线、错误、待审批具有文字、图标和明确动作。
- [ ] 每页最多一个显性主要行动；删除等破坏性操作具有确认步骤。
- [ ] 组件没有直写色值、随意圆角或渐变；视觉 token 统一来源。
- [ ] 键盘可到达所有导航、筛选、列表和更多菜单；焦点始终可见。
- [ ] 空、加载、成功、失败、无权限和离线状态均有可验证表现。
- [ ] 新用户能从空状态或页面标题进入接入引擎向导；已接入用户不会被重复教学打断。
- [ ] 所有可点击行、卡片、链接和图标按钮有一致的 hover、focus 与点击反馈；非交互文字不伪装成控件。

## 发布门槛

1. 现有单元测试、导航 E2E 与权限相关测试均通过。
2. 在上述五个视口完成视觉回归截图并人工核验。
3. 自动化无障碍检查无严重问题，人工核验文字对比度和键盘焦点。
4. 5--8 人测试达标，所有 P0 和 P1 可用性问题有处理结论。
5. 工程确认不改变既有路由、权限、daemon action 与缓存语义。
