# 01. 体验审计与设计目标

## 观察来源

- 已审阅现有工作台外壳 `apps/web/features/dashboard/workspace-frame.tsx`、执行引擎页面 `apps/web/features/agents/components/container-overview.tsx` 及通用样式 `apps/web/app/globals.css`。
- 已审阅用户提供的 2048px 宽度截图，其中同时出现 3 个纵向区域：全局侧栏、执行引擎列表、运行时详情。
- 已查看参考项目首页的已加载页面结构：其基础 UI 使用中性背景、细边框、`rounded-md`、紧凑按钮与明确的主次行动层级。

这些是启发式评估证据，而非用户访谈结论。

## 问题清单

| 优先级 | 问题 | 截图/代码证据 | 用户影响 | 改造原则 |
| --- | --- | --- | --- | --- |
| P0 | 三栏同时竞争注意力 | 左导航、列表、详情都使用强边框、卡片、阴影和相近字号 | 长名称在列表中被迫折行；用户难以定位主工作区 | 固定壳层级，主从详情只在需要时出现 |
| P0 | 列表行承载过多列 | 执行引擎行同时放名称、连接状态、更新按钮、删除、Provider、设备与备注 | 列表无法快速比较，危险动作接近选择动作 | 行内只保留名称、健康、摘要、最近活动；操作收进溢出菜单 |
| P0 | 状态信息重复且没有处置优先级 | 连接状态在列表、详情头部、指标卡重复；多个 `0` 统计卡同权 | 异常容易被淹没，正常状态占据注意力 | 顶部只呈现需要行动的异常；正常状态降为紧凑标签 |
| P1 | 视觉系统有两次叠加痕迹 | `globals.css` 前段与末尾都定义工作台样式；后段又覆盖 `workspace-layout` 和侧栏 | 页面很难形成稳定的色彩、圆角、阴影和间距节奏 | 建立单一 token 层，删除按页面附加的主题覆盖 |
| P1 | 装饰性风格超过运营语义 | 全局含多处径向/线性渐变、18--36px 圆角和明显投影 | 工作台更像展示页，信息密度反而下降 | 以平面层级、细边框和 8px 圆角表达分组 |
| P1 | 导航把频次、实体和管理项混排 | 侧栏同时出现快捷统计、消息、联系人、员工、引擎、技能等 | 用户无法预判入口归属，且侧栏比内容区更醒目 | 基于任务域分组，计数只出现于需要处理的项目 |
| P2 | 信息语言混杂 | 当前截图中中文标签、英文系统描述、运行时名称和按钮混在同一密度层 | 扫描路径中断，国际化显得不完整 | UI 文案一层语言，原始技术字段放到复制/详情区 |

## 设计问题陈述

作为需要持续调度数字员工、处理审批和排查运行时异常的工作区成员，我需要在一个稳定、可预期的工作台中快速判断「什么需要我现在处理」，再进入实体详情完成操作；而不是在每个页面重新解析导航、统计卡和技术字段。

## 设计目标

| 目标 | 设计结果 | 可衡量信号 |
| --- | --- | --- |
| 让异常可见 | 危险和待处理项在页面标题右侧以动作队列出现 | 受试者能在 10 秒内找到离线引擎 |
| 让列表可比 | 一行仅保留 3--4 个可比字段，长文本单行截断 | 在 1440px 时不出现四列折行 |
| 让详情可行动 | 标题区只保留最高频的 1 个主要动作和次级菜单 | 受试者可在 30 秒内完成「更新 Runtime」 |
| 让系统一致 | 每个页面使用同一外壳、标题、工具栏、列表、状态标签和空状态 | 关键模块中 token 直写颜色降至 0 |
| 让页面安静 | 正常态信息不使用饱和色、重阴影或大卡片 | 首屏中高饱和色仅用于主行动、状态和告警 |

## 设计原则

1. **先行动，后说明。** 顶部回答“是否需要处理”，详情再解释技术原因。
2. **一屏一个主任务。** 页面不再为所有模块保留同等醒目的入口和数据。
3. **实体拥有稳定身份。** 引擎、员工、任务、审批均使用相同的列表行与详情头部骨架。
4. **渐进披露。** 默认给出可决策的摘要；日志、版本、原始 ID 与安装项进入二级区或可展开面板。
5. **弱装饰，强反馈。** 平面化表面承载信息；加载、保存、失败、权限不足必须具有清楚反馈。
6. **可访问优先。** 文本对比度至少 WCAG AA；颜色不作为唯一状态信号；所有图标按钮有名称和焦点态。

## 非目标

- 不将协作工作台改造成营销首页或仪表盘画廊。
- 不通过隐藏权限、日志或审计信息来换取“简洁”；这些信息应被移到合适层级。
- 不改变既有任务、daemon、审批或运行时的服务端行为。
