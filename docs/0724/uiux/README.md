# agent.dofe UI/UX 重构方案

日期：2026-07-24  
范围：桌面优先的 Agent-native 协作工作台；已从「执行引擎管理」延伸到任务、审批、知识与共享工作台框架。

## 结论

当前界面的问题不是功能不足，而是页面同时把全局导航、模块入口、列表、详情、状态和操作都以同一视觉强度呈现。在 1920px 及以上宽度下，用户需要在窄列表中阅读长名称，同时在详情页反复确认相同状态，导致扫描成本高、信息层级失效。

目标是把产品重构为安静、可扫描、任务导向的运营工作台：

- 用稳定的三层布局承载全局、模块、详情信息。
- 以「当前任务和异常」替代常驻的装饰性统计卡。
- 用统一的实体列表和详情头部，减少每页独立拼装的视觉语言。
- 以中性背景、低阴影、8px 圆角和单一蓝色行动色建立克制的系统感。

本方案参考 `https://model.local.dofe.ai` 的克制中性基底、清晰边界、紧凑按钮和一致的文字层级；不复用其面向产品介绍页的营销排版。agent.dofe 的目标用户是需要反复执行、监控和处置工作的运营成员，页面应优先服务扫描、比对和决策。

## 约束与假设

- 本目录同时记录产品方案与分阶段实施结果；界面代码已开始落地，但不改变业务数据模型、权限判断和 daemon action 契约。
- 用户提供的执行引擎管理截图和现有代码是问题证据；尚未进行真实用户访谈。因此文档把访谈、树测试和可用性测试列为首个实施阶段的验证门槛，而非将假设写成事实。
- 保留当前的 Next.js 路由、权限控制、模块预取和业务动作；重构应以页面框架、视觉 token、组件复用和信息密度为主。

## 采用顺序

1. 先统一 token 与 `WorkspaceFrame` 外壳，消除全局风格冲突。
2. 用「执行引擎管理」验证主从详情模板、运行状态和异常处置。
3. 将同一模板推广到员工、技能、知识、审批、任务和设置模块。
4. 在真实运行数据下完成 5--8 人可用性测试，再进入视觉收口。
