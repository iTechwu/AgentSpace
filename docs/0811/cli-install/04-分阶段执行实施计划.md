# 分阶段执行实施计划

## 1. 执行原则

- 每个阶段都有可独立验证的交付物；
- 先解决页面“无出口”问题，再扩大部署能力；
- 先建立 release 和状态模型，再接 Docker 编排；
- 默认采用 feature flag，失败可回退到现有 CLI/MCP 流程；
- 每个阶段完成聚焦测试后立即提交独立 git commit；
- 不在本机启动 Jenkins，不做未经请求的部署。

## 2. 阶段总览

| 阶段 | 目标 | 主要产物 | 依赖 |
| --- | --- | --- | --- |
| Phase 0 | 目录与问题基线 | 目录治理报告、原因统计、能力分类 | 无 |
| Phase 1 | 页面不再出现无出口按钮 | `nextAction`、角色化文案、请求入口 | Phase 0 |
| Phase 2 | Runtime 基线标准化 | baseline image、readiness、rollout | Phase 0 |
| Phase 3 | release 治理 | immutable release、artifact lock、审核队列 | Phase 1 |
| Phase 4 | 管理员部署请求 | request/approval/operation 状态机 | Phase 1、2 |
| Phase 5 | managed service 生命周期 | 镜像缓存、创建、健康、回收、回滚 | Phase 3、4 |
| Phase 6 | CLI/MCP 一键启用 | 统一可用性投影、依赖链和连接向导 | Phase 4、5 |
| Phase 7 | 灰度与全面上线 | 运行指标、可用性测试、迁移和回滚演练 | Phase 6 |

## 3. Phase 0：目录与问题基线

### 工作内容

- 导出当前 CLI/MCP catalog 的 deployment mode、version、install strategy、requires、transport 和 risk；
- 按 `release_unpinned`、`install_command_unsafe`、`runtime_dependency_unsupported`、`configuration_required`、`runtime_*_unavailable` 分类统计；
- 标记每个条目适合 `runtime_package`、`managed_service` 或 `external_service`；
- 区分 `daemonMode` 与 execution profile，不按 local/remote 直接推导 CLI/MCP；
- 审核官方条目：Chrome DevTools、MiniMax、OpenMontage；
- 输出可直接开放、需管理员部署、待维护者修复的清单。

### 验收

- 每个目录条目有唯一责任人和处置分类；
- 普通用户目录不再显示无法解释的“不可安装”长尾条目，或它们有明确的“暂未开放”状态；
- 统计报表能在同步后重复生成。

## 4. Phase 1：页面状态和管理员请求

### 代码范围

- `apps/web/features/market/market-page-loader.ts`：生成 availability projection；
- `apps/web/features/market/capability-presentation.ts`：统一 `nextAction` 和角色化 reason；
- `apps/web/features/market/market-page-client.tsx`：替换禁用安装按钮和技术错误文案；
- `apps/web/features/runtimes/runtime-capabilities-panel.tsx`：复用同一投影；
- `apps/web/features/market/`：新增“申请管理员部署”弹窗和请求进度；
- `packages/db`：新增 capability request 与 operation 表和读写函数；
- `packages/services`：权限、幂等、审计和状态机。

### 产品交付

- 普通用户看到 `安装/连接/配置/申请/处理中/暂未开放` 之一；
- 管理员看到技术诊断和处理动作；
- 申请创建后可在“我的请求”中查看，不需要重复创建。

### 验收

- 任意 catalog 条目都有非空 `nextAction`；
- 长期状态不使用禁用主按钮表达；
- 请求重复提交保持同一个 idempotency key 和 operation。

## 5. Phase 2：Runtime 基线标准化

### Docker 工作

- 在 `deploy/daemon/Dockerfile.provider-runtime` 中明确安装和版本锁定 Node/npm、Python/pip、Chromium、CLI-Hub；
- 为 CLI-Hub 增加固定来源和验证步骤；
- 增加启动/heartbeat readiness 探针；
- 为不同 Provider image 建立兼容矩阵；
- 构建 SBOM、签名并保存 digest；
- 只预装基础工具，不预装所有业务 CLI 或 MCP 服务。

### 运行时工作

- `packages/daemon/src/runtime-apps.ts`：扩展 readiness 到 writable/persistent HOME、runtime package executor、MCP Gateway、managed service reachability、node、npm、python、pip、cliHub、chromium；
- `packages/services/src/clihub/runtime-apps.ts`：把 readiness 映射为可操作原因；
- `packages/services`：增加 Runtime execution profile 与 capability implementation 协商；
- Runtime 详情页显示“基础环境准备度”和最后检查时间。

### 验收

- 新建 Runtime 后 60 秒内完成 readiness；
- 不同 Provider Runtime 的结果不会误用宿主机 readiness；
- Remote 受管 Docker Runtime 在 profile 满足时同时提供 CLI 与 MCP，不会被错误降级为 MCP-only；
- Remote 只读 Runtime 不会出现 CLI 安装入口；Local Runtime 没有 Gateway 时不会误报 MCP 可用；
- 缺工具时页面可提供“一键更新 Runtime”或“申请管理员处理”，而不是显示不可解释的安装失败。

## 6. Phase 3：release 治理

### 工作内容

- package 与 release 分离；
- 同步公共目录时解析 `latest` 为精确版本；
- 记录 artifact integrity 和 manifest digest；
- 对 unsafe shell、桌面依赖、交互登录等条目标记治理原因；
- 管理员审核并发布 immutable release；
- release 支持 yanked、rollback 和升级候选。

### 兼容策略

- 保留现有 catalog item 作为迁移读模型；
- 没有 release 的旧条目只进入管理员治理列表；
- 已安装应用补写 release 引用时，先保存未知来源快照，不强行伪造 digest；
- 新安装必须只接受 release ID。

### 验收

- `latest` 不再直接进入普通用户安装路径；
- release digest、artifact digest 和 entrypoint 验证可追溯；
- yanked release 阻止新安装，但不破坏历史审计和正在运行任务的收尾策略。

## 7. Phase 4：管理员部署请求

### 工作内容

- capability request CRUD、审批、拒绝、补充信息和取消；
- 普通成员/管理员权限分离；
- 申请与 operation 绑定；
- 站内通知和页面进度；
- 审计事件和敏感字段脱敏。

### 验收

- 普通成员点击“申请管理员部署”后，不需要手动复制命令；
- 管理员批准时可以选择节点、scope、暖实例策略和资源档位；
- 拒绝必须提供用户可理解的原因；
- 请求、部署、连接三者状态可回溯。

## 8. Phase 5：managed service 生命周期

### 工作内容

- 复用现有 managed service container runtime；
- 增加 release cache、pull、signature verify、provision、health、suspend、retire；
- 以 workspace/runtime 维度隔离实例；
- 实现空闲 TTL、资源配额、重试和回滚；
- 通过 connection reference 连接 MCP Gateway；
- 不把容器 endpoint 或 token 返回浏览器。

### 验收

- 镜像签名验证失败时容器不会启动；
- 重复批准不会创建重复容器；
- 健康失败自动将连接降级，任务能力目录移除该服务；
- 回收前检查 task/job/pending operation；
- 外部 PostgreSQL/Redis/RabbitMQ 依赖通过配置连接，不在应用部署中创建。

## 9. Phase 6：一键启用体验

### CLI

- 选择 Runtime 后统一展示 readiness、release 和下一步动作；
- 不按 `daemonMode` 分流；根据 execution profile 自动选择 CLI/MCP 实现；
- `runtime_package` 直接安装；
- 基础工具缺失时走 Runtime baseline 更新；
- 高风险 CLI 保留管理员确认，但不让普通用户面对技术 gate；
- 安装成功后可同步 Skill。

### MCP

- `managed_stdio`：先确保依赖 CLI release，再启动 worker/broker；
- `managed_service`：部署/复用 service instance，再执行连接验证；
- `streamable_http`：只执行配置、网络和握手验证；
- 工具范围、凭据和连接健康纳入同一向导；
- 连接成功后只暴露 approved tools。

### 验收

- 用户从一个主按钮开始，系统自动跨越依赖步骤；
- 普通用户无需选择 local/remote；两种实现都可用时显示系统推荐，管理员可在高级设置切换；
- 依赖步骤失败时可以重试，不需要重新填写凭据和工具范围；
- CLI 安装和 MCP 连接的状态词不混用；
- 完成页面显示实际可用能力数和最近健康时间。

## 10. Phase 7：灰度上线

### 灰度顺序

1. 仅官方、低风险、固定 release 的 CLI；
2. 官方 managed service OpenMontage；
3. Chrome DevTools managed stdio；
4. MiniMax 等需要凭据的 MCP；
5. 经过治理的社区目录。

### 回滚开关

```text
CAPABILITY_AVAILABILITY_PROJECTION_V2=0
CAPABILITY_REQUESTS_ENABLED=0
MANAGED_SERVICE_PROVISIONING_ENABLED=0
RUNTIME_BASELINE_ROLLOUT_ENABLED=0
```

关闭开关只停止新操作，不删除已存在的审计、实例或连接。正在运行的服务按安全停机策略收尾。

## 11. 代码提交拆分

推荐每个独立交付物单独提交，中文 commit message：

1. `增加能力可用性投影与管理员请求模型`
2. `优化CLI与MCP安装状态和错误恢复界面`
3. `增加Runtime基础环境就绪检查`
4. `增加不可变能力release治理`
5. `接入受管服务镜像缓存与部署生命周期`
6. `统一CLI安装与MCP连接向导`

每个提交都必须包含对应单元测试或集成测试，不把未验证的部署改动合并到应用代码。
