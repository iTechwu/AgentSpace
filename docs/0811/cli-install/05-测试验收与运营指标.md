# 测试验收与运营指标

## 1. 验收原则

验收必须同时覆盖：

- 能否安装/部署；
- 用户是否知道下一步；
- 安全门禁是否仍然有效；
- Docker 生命周期是否可恢复；
- 状态在刷新、重启和网络抖动后是否一致；
- 外部集中依赖是否未被应用部署重复创建。

## 2. 功能验收矩阵

| 场景 | 前置条件 | 预期结果 |
| --- | --- | --- |
| 固定 npm CLI | Runtime npm ready，release approved | 点击安装，验证 entrypoint，状态 installed |
| 固定 PyPI CLI | Python/pip ready，release approved | 受控 pip 计划成功，状态 installed |
| Remote 受管 Docker Runtime | persistent HOME、executor、MCP Gateway ready | 同时允许 CLI 与 MCP，不因 remote 标签禁用 CLI |
| Remote 只读 Runtime | 无 writable HOME/executor，MCP Gateway ready | 不显示 CLI 安装，推荐 MCP |
| Local Runtime 无 MCP Gateway | CLI readiness ready | 允许 CLI，不声称 MCP 可用 |
| Local Runtime 同时支持两种实现 | CLI/MCP 均通过预检 | 普通用户看到推荐路径，管理员可在高级设置切换 |
| Runtime 缺 npm | release approved，npm unavailable | 显示准备 Runtime 或申请管理员，不创建失败安装 |
| `latest` 条目 | 无 immutable release | 普通用户显示暂未开放，管理员进入 release 治理 |
| unsafe install command | 包含 shell 控制/下载执行 | 发布被拒绝，永不下发 Runtime |
| managed service 镜像已缓存 | digest/signature valid | 启用时快速创建实例并连接 |
| managed service 未缓存 | release approved | 管理员批准后先 pull，再 provision |
| 签名错误 | image digest 不匹配签名 | 容器不启动，记录失败原因 |
| 外部 MCP | endpoint/schema/secret valid | 完成握手、工具发现和 approved tools 保存 |
| MCP 需要 CLI 依赖 | dependency release approved | 一键安装依赖后继续连接 |
| 普通用户未授权 | service not deployed | 创建管理员 request，不暴露内部 endpoint |
| 管理员拒绝申请 | request pending | 状态 rejected，显示原因，可重新申请 |
| Runtime 离线 | operation pending | 保留意图，恢复后可继续或切换 Runtime |
| 健康检查失败 | service ready | connection degraded，不向新任务暴露 |
| 服务空闲回收 | 无运行 task/job | 实例回收，connection 显示下次启用会启动 |
| 重复点击/重试 | 相同 idempotency key | 不产生重复 operation、容器或安装记录 |

## 3. 安全验收

- 浏览器不能提交任意 image、endpoint、command、mount 或 capability；
- 所有 release、镜像和 artifact 都有固定引用；
- 镜像 signature required 时缺 key 或验证失败必须 fail closed；
- managed service 不挂载 Docker socket、Provider HOME、SSH agent；
- worker 使用非 root、read-only rootfs、cap drop 和资源限制；
- egress 只允许 catalog policy 声明的目标；
- secret 不进入页面 JSON、操作快照、日志或 MCP tool arguments；
- task 只能调用 ready connection 的 approved tools；
- disable、release yank、成员移除后不再发放新 lease；
- PostgreSQL、Redis、RabbitMQ 未出现在应用 Dockerfile/Compose 服务定义中。

## 4. 状态恢复验收

### 4.1 Web 重载

在每个阶段刷新页面，状态必须由数据库/服务端读模型恢复，不依赖浏览器内存。

### 4.2 Daemon 重启

执行中重启 daemon 后：

- lease 过期并可重新 claim；
- 不重复安装已完成 release；
- 不创建重复容器；
- operation 可以继续、失败或安全回滚；
- 用户看到稳定阶段和下一步。

### 4.3 节点断电/网络中断

- 镜像已缓存的实例可以重新 reconcile；
- 正在 pull/provision 的操作不会被误标记为成功；
- 连接降级后任务能力目录及时移除；
- 人工重试使用幂等键。

## 5. 自动化测试分层

### 单元测试

- deployment mode 分类决策树；
- `daemonMode` 与 execution profile 解耦；
- CLI/MCP 多实现推荐和管理员可选集合；
- release immutable/完整性/签名校验；
- readiness 到 `nextAction` 的映射；
- 权限、幂等键、状态迁移；
- 面向角色的 reason 文案；
- 资源、网络和容器 argv 构建。

### 服务集成测试

- capability request 审批与 operation claim；
- Runtime baseline readiness 上报；
- managed service provision/health/retire；
- MCP Gateway 与 connection 状态联动；
- secrets 不落日志和响应；
- 外部依赖配置只引用集中管理地址。

### Web 测试

- CLI 可安装、需配置、申请管理员、暂未开放四种状态；
- MCP 已部署连接、未部署申请、凭据配置、部署失败重试；
- 普通成员和管理员视图差异；
- 进度刷新和通知；
- 不再渲染长期禁用的无出口主按钮。

### E2E

- 真实 Docker Runtime 安装一个固定 npm CLI；
- 真实 Docker Runtime 安装一个固定 PyPI CLI；
- 受管节点拉取并启动一个 digest-pinned MCP service；
- 服务故障后自动降级、重试和恢复；
- 管理员批准普通用户申请后自动完成部署和连接。

测试资源受仓库 AGENTS 约束：单文件 API Jest 使用 `--runInBand`，完整测试限制并发，不执行无约束的 `pnpm test`。

## 6. 可用性测试计划

### 参与者

5 至 8 名：

- 2 名普通工作区成员；
- 2 名工作区管理员；
- 1 至 2 名 Runtime/平台运维人员；
- 可选 1 至 2 名首次使用者。

### 任务

1. 将一个固定版本 CLI 安装到在线 Runtime；
2. 发现一个未部署 MCP，并申请管理员部署；
3. 管理员批准并启用 OpenMontage；
4. 处理一个需要凭据的服务；
5. 在部署失败后找到原因并重试；
6. 判断一个 `latest` 条目为什么暂未开放。

### 成功指标

| 指标 | 目标 |
| --- | ---: |
| 用户判断下一步的成功率 | >= 90% |
| 完成安装或部署申请 | >= 85% |
| 无需复制命令/进入服务器 | 100% |
| 因禁用主按钮产生的困惑 | 0 个关键问题 |
| 普通用户理解 Docker/release 技术细节 | 不要求 |
| 管理员从批准到状态 ready | <= 5 分钟（缓存镜像） |

## 7. 运营指标

### 漏斗

```text
目录曝光 -> 查看详情 -> 选择 Runtime -> 点击主动作
-> operation/request 创建 -> ready/installed/connected
```

记录每一阶段的数量、耗时和失败原因。不要把 secret、完整 URL、用户输入或工具 payload 作为埋点字段。

### 核心指标

- 可获取目录覆盖率：普通用户条目中有明确 `nextAction` 的比例，目标 100%；
- 一键完成率：点击主动作后无需人工复制命令即可 ready 的比例；
- 管理员介入率：需要申请部署的比例；
- 首次 ready 时间：按缓存/未缓存、CLI/service 分组；
- operation 重试率和最终成功率；
- release 治理积压量和平均处理时间；
- Runtime baseline readiness 通过率；
- 服务实例资源利用率、空闲回收率和启动失败率；
- degraded connection 恢复时间；
- 用户因“不可安装”离开详情页的比例。

## 8. 上线门禁

只有同时满足以下条件才允许扩大目录范围：

- 普通用户核心任务完成率 >= 85%；
- 高风险和不合格 release 不会进入普通用户安装路径；
- managed service 的签名、网络、资源、回滚测试通过；
- 至少一个 Docker Runtime 和一个独立 managed node 完成真实 E2E；
- operation 在 daemon 重启、网络中断和页面刷新后可恢复；
- 审计、通知和脱敏检查通过；
- 没有新增 PostgreSQL、Redis、RabbitMQ 应用服务定义；
- 已准备回滚 feature flag 和旧流程兼容窗口。
