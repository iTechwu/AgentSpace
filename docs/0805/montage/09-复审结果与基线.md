## 4. 为什么“修改后”仍会出现相同审计结果

当前证据只能支持以下解释之一：

1. 修改发生在未切换到当前 checkout 的其他工作树或分支；
2. 修改尚未 commit，因此没有进入当前审计基线；
3. 只修改了文档、镜像或部署配置，没有修改审计所检查的运行时代码和数据库迁移；
4. 修改只覆盖了 models 单服务状态机，没有把 purge guard、Worker durable invocation 和 AgentSpace usage projection 接入跨服务生命周期。

因此不能用“models 单测通过”关闭 P0，也不能用“Job 已完成”关闭统一账单；必须以三仓同一 Job 的数据库和聊天页证据为准。

## 5. 重新关闭审计项的最小证据

在提交下一轮实现前，每个 P0/P1 至少需要：

- 代码 commit SHA、迁移版本和部署镜像 digest；
- 同一个 `delegationId + modelInvocationId` 的 models invocation、usage、charge、ledger 查询结果；
- 删除 MCP/Runtime 时接口返回的状态和 purge guard 拒绝证据；
- Worker 在 models 成功后被杀死，重启后只出现一条结算事实的日志/数据库快照；
- AgentSpace `token_usage`、聊天阶段卡片、最终 MP4 Artifact 和账单状态的同一 trace；
- 重复 webhook、重复请求和重复 cron 执行后的 exactly-once 计数；
- fake clock 或相对时间测试夹具，避免固定日期让 delegation 测试按日失效。

在这些证据出现前，准确状态仍是：**delegation 核心代码部分完成；跨服务清理、异常恢复和统一账单生产门禁未关闭。**
