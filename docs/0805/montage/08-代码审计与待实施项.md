# OpenMontage / models delegation 代码审计与待实施项

审计日期：2026-08-06  
审计范围：`agentspace.dofe.ai`、`models.dofe.ai`、`OpenMontage` 的 Job、Runtime、MCP、delegation、usage、charge、ledger、Artifact 和异常恢复链路。

## 1. 审计结论

本轮实现已经把 models delegation 的核心数据库和服务端状态机搭起来了，以下能力有代码证据：

- delegation 创建、`active -> draining -> revoked` 状态约束；
- invocation 预留、结算、释放和 `reconciliation_required` 状态；
- `delegationId + modelInvocationId` 幂等索引；
- models 在代理上游前执行预算预留，终态后由 models 服务端写 usage 并结算；
- OpenMontage Job Link、阶段 checkpoint、Artifact Bridge、事件回放和终态 delegation drain；
- API Key、Team、Runtime Credential 删除不会通过 `GatewayUsageLog` 的外键级联删除历史 usage。

但是，“代码具备能力”还没有等价为“清理、故障注入和统一账单在三仓部署中闭环”。当前不能把本能力标记为 production-ready。最重要的未闭环是：

1. AgentSpace 的 MCP remove / Runtime delete 尚未统一调用 models delegation 的最终 purge 门禁。
2. OpenMontage 代理生成 `modelInvocationId` 后只在内存中转发，缺少调用前的本地 durable invocation/outbox 记录。
3. AgentSpace 的 `token_usage` 依赖后台同步才出现；最近一次真实 Claude/GLM-5.2 任务虽然完成，但实时查询没有对应 `token_usage` 行，统一账单 E2E 仍未通过。
4. 用户要求的删除 MCP、杀 Worker、删除 Runtime、撤销 delegation、异步生成取消、调用重放等故障注入 E2E 尚未形成三仓真实环境的强断言矩阵。

## 3. 必须修复的高风险项

### F-001 [P0] Runtime/MCP 清理没有跨服务最终 purge 门禁

**现状证据**

- AgentSpace `deleteManagedRuntimeAsync` 在调用 `safeRevokeCredential` 后，如果没有 daemon 连接，会直接执行 `deleteAgentRuntimeSync`：`packages/services/src/runtime-provisioning/runtime-provisioning.ts:1404-1452`。
- `deleteAgentRuntimeSync` 只是直接 `DELETE FROM agent_runtime`，没有检查 OpenMontage Job 的运行状态、models delegation 的 `reserved`/`reconciliation_required` 或 runtime credential reconciliation target：`packages/db/src/daemons.ts:662-685`。
- MCP remove 在 operation 成功后直接删除连接：`packages/services/src/mcp-center/connections.ts:275-280`、`packages/db/src/mcp-center.ts:890-895`。该路径没有先调用 delegation drain/reconcile，也没有检查关联 Job 是否仍在执行。

**风险**

撤销请求与实际在途请求之间存在竞态。Runtime/MCP 记录可能已经消失，但 models 仍有预留或尚未归属的 usage；操作结果可能表现为“资源删除成功”，而财务事实只能依赖后台扫描，无法保证删除接口本身是安全门禁。

**待实施**

- 增加统一的 `assertPurgeable(workspaceId, runtimeId|connectionId|jobId)`，在 API、cron、daemon completion 三个入口都调用。
- 门禁必须同时检查：OpenMontage Job 是否 `QUEUED/RUNNING/WAITING_APPROVAL`、本地 delegation 是否 `active/drain_pending`、models delegation 是否有 `reserved/reconciliation_required`、usage retry/reconciliation 是否未完成。
- 只有 `DRAINING -> all terminal -> budget released/settled -> usage/charge/ledger reconciled -> REVOKED` 后，才允许清理 secret、MCP、容器和 Runtime 记录。
- 将“删除 Runtime”改成默认 `stop + drain`；最终 purge 由后台任务在门禁通过后完成，接口返回 `202/pending` 而不是立即成功。

**验收**

同一 Job 在模型请求中途删除 MCP、删除 Runtime、撤销 delegation 三种操作都必须返回“禁止最终 purge/正在 drain”，新请求立即被拒绝，历史 usage/charge/ledger 仍可查询。

### F-002 [P0] OpenMontage 没有持久化调用前的 modelInvocationId

**现状证据**

- `DelegatedModelCredential.signed_headers()` 在调用时生成 UUID：`OpenMontage/tools/dofe/delegation.py:27-61`。
- loopback proxy 根据 `X-Request-Id` 或随机 UUID 计算 invocation ID，然后直接调用 models：`OpenMontage/openmontage/delegation_proxy.py:79-105`。
- Worker 只在每个阶段领取 credential，没有 invocation outbox 或本地调用表：`OpenMontage/openmontage/job_worker.py:254-283`。

**风险**

Worker 在上游已成功、响应尚未回到本地时崩溃，重试若没有稳定的 `X-Request-Id` 会产生新的 invocation ID。models 的幂等约束只能保证“相同 ID”幂等，不能把两个不同 ID 判断为同一次业务调用，可能导致重复消费或无法自动归因。

**待实施**

- 在 OpenMontage Job SQLite/持久存储中增加 `model_invocation` 表，至少保存 `jobId/stage/attempt/modelInvocationId/requestId/status/createdAt/lastSentAt`。
- 每次发送上游前在同一事务中 `insert ... on conflict`，重试必须复用同一个 ID；只有明确的新业务 attempt 才生成新 ID。
- Worker 启动和 lease 恢复时扫描 `sent/unknown` 记录，调用 models 内部 reconciliation 查询恢复 Usage Link，再决定 settle/release。
- 将 proxy 生成 ID 的逻辑下沉为可注入的 durable `InvocationStore`，禁止无 `X-Request-Id` 时使用不可恢复的随机 ID。

**验收**

杀死 Worker 于 models 返回成功之后、Job 状态提交之前，重启后必须只出现一条 models invocation、一条 usage、一条 charge、一条 ledger，且 Job/employee/stage 归因不丢。

### F-003 [P0] AgentSpace token_usage 投影不是实时闭环，实际账单证据缺失

**现状证据**

- `recordTokenUsageSync` 明确把本地 cost 固定为 `0`，并等待 models reconciliation：`agentspace.dofe.ai/packages/db/src/token-usage.ts:161-207`。
- 同步依赖 `reconcileAllManagedRuntimeUsageAsync` 扫描 Runtime Credential，再分页拉取 models usage：`packages/services/src/models/usage-sync.ts:58-127`、`197-287`。
- 最近一次真实 Claude/GLM-5.2 任务已完成并能从 provider JSONL 看到 token usage，但按该 Job 查询 AgentSpace `token_usage` 没有行；这说明“任务成功”尚未证明“统一账单成功”。

**风险**

后台同步未运行、分页游标错误、Runtime 被提前删除或 models 暂时不可达时，消费可能只存在 models，AgentSpace 聊天/成本页没有可见账单。若同步按 request ID 之外的字段回填，可能形成 unallocated 或错误员工归因。

**待实施**

- Job 创建时写入 `token_usage` 的 pending 占位行或 durable reconciliation target，不能等首次 cron 才发现消费。
- 同步接口必须按 `gatewayUsageId`、`gatewayRequestId`、`delegationId + modelInvocationId` 三重键匹配，并保存 `employeeId/runtimeId/jobId/stage/sourceInvocationId` 快照。
- 增加 models usage -> AgentSpace 的 push/outbox 或短轮询 SLA；超过 SLA 必须在聊天页显示“账单对账中”，而不是无记录。
- 账单状态只能由 models 的 terminal charge 推进；AgentSpace 不得把 `estimated` 当最终费用。

**验收**

真实付费模型任务完成后 30 秒内，聊天页能看到阶段消费、最终金额、models usage/charge/ledger ID；重复同步 10 次仍只有一条 `token_usage` 和一条 billing event。

### F-004 [P1] usage 归因快照字段仍可为空，数据库没有 delegation 条件约束

**现状证据**

`GatewayUsageLog` 的 `runtimeId/employeeId/rootTaskId/sourceInvocationId/externalJobId/pipelineStage/modelInvocationId/tenantId` 全部是 nullable：`models.dofe.ai/apps/api/prisma/schema.prisma:1264-1283`。Proxy 在 delegation 路径会传值，但 schema 没有 `CHECK (delegation_id IS NULL OR ...)`，也没有服务层统一 DTO 验证所有快照都非空。

**风险**

未来新增模型入口、异步 generation 入口或内部调用若遗漏任一字段，usage 仍可成功落库，查询时只能依赖已删除的 delegation/Runtime/Job，违背“不可变财务事实”的要求。

**待实施**

- 为 delegation usage 增加专用写入 DTO 和 service guard，五个强制快照缺一即拒绝。
- PostgreSQL 增加条件 `CHECK`，并为 `runtimeCredentialDelegationId + modelInvocationId` 建立 usage 唯一约束（当前已有 nullable unique，需确认数据库迁移已生效）。
- 异步 generation 复用同一套 DTO，禁止从旧的 `GatewayGenerationTask` 反查归因。

### F-005 [P1] charge/ledger 关联是裸 UUID，没有数据库级完整性

**现状证据**

`GatewayUsageLog.billingChargeId/billingAccountId/billingLedgerEntryId` 只有 scalar 字段，没有 Prisma relation 或外键：`models.dofe.ai/apps/api/prisma/schema.prisma:1280-1283`、`1317-1323`。BillingCharge/BillingLedgerEntry 本身也主要依靠 service 逻辑和索引关联 usage。

**风险**

usage 可能指向不存在的 charge/ledger，或者 charge 已写入但 usage link 未回填。清理时无法依赖数据库拒绝破坏性操作，对账只能靠定期扫描。

**待实施**

- 对可 nullable 的 billing FK 使用 `ON DELETE SET NULL`，对 charge/ledger 的财务事实删除使用 `RESTRICT`；同时保留不可变 tenant/employee/runtime/job 快照。
- 增加 `usage -> charge -> ledger` 的一对一/一对多关系约束和唯一键，禁止一个 model invocation 产生多个 settled charge。
- 每次 settlement 在同一数据库事务写入 usage、charge、ledger link；失败进入 reconciliation queue，不返回“已结算”。

### F-006 [P1] MCP 删除策略没有按需求显式区分“禁止新 Job”和“取消运行中 Job”

**现状证据**

当前只有 `disableMcpConnectionSync` 和 `removeMcpConnectionSync`。disable 会取消未完成的 MCP operation，但不会取消 OpenMontage Job：`agentspace.dofe.ai/packages/services/src/mcp-center/connections.ts:243-263`。remove 在 operation 完成后删除连接：`packages/services/src/mcp-center/connections.ts:275-280`、`packages/db/src/mcp-center.ts:890-895`。

**风险**

产品层无法告诉用户本次操作是“只阻止新 Job”还是“同时取消运行中 Job”。连接删除后，运行中的 Job 可能继续使用已签发的 delegation；如果只依赖终态事件触发 drain，事件丢失时会长期占用预算。

**待实施**

- API 增加 `mode: prohibit_new_jobs | cancel_running_jobs`，默认前者并明确返回状态。
- `cancel_running_jobs` 先为所有关联 Job 写入 cancel intent，再等待 Job 终态和 models reconciliation；两种模式都禁止删除历史账单。
- remove 只做 archive/disabled 标记；物理删除连接和 secret 必须走统一 purge worker，并保留 `mcpConnectionId` 快照。
- OpenMontage cron 必须并入 runtime maintenance 或由部署平台提供必达调度；当前它是独立 route：`apps/web/app/api/cron/openmontage-reconcile/route.ts:19-25`。

### F-007 [P1] reconciliation watermark 以时间为主，缺少稳定 provider cursor

**现状证据**

models 使用 `providerReconciledThrough` 时间戳并以 invocation `createdAt` 判断覆盖：`models.dofe.ai/apps/api/libs/domain/runtime-credential-delegation/delegation-reconciliation.service.ts:68-80`、`139-157`、`220-225`。

**风险**

同一时间戳、时钟回拨、provider 延迟写入或分页排序不稳定时，单纯时间 watermark 可能提前释放 reservation，或重复扫描但无法确认完整性。

**待实施**

- 优先使用 models usage provider 的稳定 `(updatedAt,id)` cursor；时间只能作为兼容字段。
- 保存 `reconciliationAttemptId/providerCursor/observedRemoteCount/settledAmount/releasedAmount`，形成可审计对账快照。
- 对“usage 成功但价格缺失”设置人工/自动重试上限，不能无限停留在 `reconciliation_required`。

### F-008 [P1] 失败注入 E2E 未覆盖用户要求的完整矩阵

代码测试目前覆盖了状态机、代理签名、事件重放和本地 checkpoint，但没有发现三仓真实环境中同时断言“只结算一次、历史可查、归因不丢、不再产生新消费”的以下场景：

| 场景 | 当前状态 | 必须增加的断言 |
| --- | --- | --- |
| 模型请求中途删除 MCP | 缺失 | 新调用 401/403；在途调用最终 settle/release；MCP 历史保留 |
| models 成功后立即杀 Worker | 缺失 | orphan reconcile；一条 usage/charge/ledger；Job 恢复 |
| 删除 Runtime | 只有常规删除测试 | reserved/in-flight 时 purge 被拒绝；drain 完成后才删除 |
| 撤销 delegation | 只有 service 单测 | 新调用拒绝；旧调用完成；预算预留全部释放或结算 |
| 异步视频生成中取消 | 缺失 | generation task 终态、provider 终态和 delegation 结算一致 |
| 重放同一调用 | 只有局部 invocation 单测 | 相同 `modelInvocationId`、requestId、eventId 多次重放均不重复收费 |
| 两个 AI 员工并发 | 文档列为待执行 | employee/runtime/job/stage 快照严格隔离 |
| 大文件/长视频 | 文档列为待执行 | Artifact 可回收，超时/重试不重复产生模型消费 |

## 4. 发布前实施顺序

1. **先修清理门禁**：统一 Job/Runtime/MCP purge guard 和 `202 pending` 生命周期；补数据库迁移与状态审计。
2. **再修调用 durable 记录**：OpenMontage invocation store、重试复用 ID、Worker 启动 orphan reconciliation。
3. **补齐账单投影**：models settlement outbox 或 AgentSpace pending usage 占位、三重幂等键、SLA 和聊天页对账状态。
4. **补强数据约束**：delegation 条件快照约束、usage/charge/ledger 外键和 settlement 唯一性。
5. **最后做部署 E2E**：真实付费模型、真实 Remotion/HyperFrames、最终 MP4 回收、删除/崩溃/取消/重放矩阵全部通过后，才开放默认入口。

## 6. 关闭标准

在下列证据全部归档前，状态保持“代码部分完成，生产验收中”：

- 三仓相同 `delegationId/modelInvocationId` 的 usage、charge、ledger 只出现一次；
- 删除 MCP、Runtime、CLI、容器、secret 后，历史账单和 Job 归因仍可查询；
- Worker 崩溃、网络超时、provider 异步延迟、重复 webhook 都能自动恢复；
- Job 聊天页显示七阶段状态、预算/实际消费、最终 MP4 Artifact 和对账状态；
- models、AgentSpace、OpenMontage 的部署版本、配置、迁移和测试报告可按 Job trace 复现。
