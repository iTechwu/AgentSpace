# MCP 扩展实施审查与推进

> 审查日期：2026-08-02
>
> 范围：`docs/0801/mcp-extension` 的目标方案，以及当前工作区中 MCP 中心、控制面、Runtime daemon 和 CLI bridge 的实现。
>
> 结论：MCP 市场的目录、连接、验证和审计数据面已具备可继续开发的骨架；但“模型在任务中调用 MCP 工具”尚未安全实现，不能将连接状态对外承诺为任务可调用。

## 1. 已实现且与方案一致的部分

| 能力 | 当前实现 | 审查结论 |
| --- | --- | --- |
| 应用市场双 Tab | `apps/web/features/market/market-page-client.tsx` 与 loader 提供 CLI/MCP 切换 | 符合产品信息架构 |
| MCP 目录和连接 | `mcp_catalog_item`、`runtime_mcp_connection` 及对应服务 | 符合 Runtime x MCP 的连接模型 |
| 密钥静态存储 | AES-256-GCM 加密的 `runtime_mcp_secret` | 控制面静态加密已落地；密钥不回显到浏览器 |
| 远程 MCP 验证 | daemon 使用 Streamable HTTP client 执行 initialize 和 tools/list | MVP 传输已收敛为 `streamable_http` |
| 工具白名单 | 连接记录保留 `approvedTools`，调用端再次检查 | 符合最小工具授权方向 |
| 基础安全控制 | HTTPS、目录 host allow-list、私网/metadata 地址、URL 凭据、重定向、超时和请求头校验 | 本次审查补齐端口限制、重定向拒绝与请求头结构校验 |

## 2. 本次已推进的修复

1. **修复启用状态机。** `enable` 操作完成后也持久化验证结果，使成功连接可由 `queued_verification` 正确进入 `ready`，而不是永久停留在等待状态。
2. **收紧密钥流向。** 一次性 daemon operation claim 由控制面解密并直接交付该次认证请求；daemon 不再需要控制面加密主密钥来执行远程验证。
3. **收紧外连和日志。** 拒绝 HTTP 重定向及非 443 HTTPS 端口、URL 凭据/query/fragment；每次 MCP 请求重新解析 DNS，拒绝任一私网/metadata 答案并将 TLS socket 固定到校验后的地址；拒绝危险/多行请求头；已连接服务的市场 payload 不再包含 endpoint；daemon 错误会结合当前连接真实密钥做二次脱敏，完成/失败回调也会在服务端脱敏。
4. **收敛 UI 真实能力。** 非 `streamable_http` 目录项不能建立连接；数据库 `ready` 在 UI 中显示为“已验证”，不再显示为“已就绪”；CLI/MCP Tab 使用 URL history 导航并随浏览器返回同步状态。
5. **栅栏化连接操作。** 配置、密钥、停用和删除会取消未完成 operation；只有 `queued_verification` 连接可以被 claim，只有 `running` operation 可以写入完成/失败结果，过期验证无法恢复被停用或更新后的连接。
6. **限制不受信任的目录和响应。** workspace 私有目录一律按高风险处理；非密钥配置必须匹配审核 schema 且拒绝额外字段；应用市场仅渲染 schema 中声明的固定字段，不提供自由 header 输入；operation claim 与完成回调都会对历史连接重新校验 endpoint、schema、header 与工具范围，不合规记录安全失败并等待管理员整改；daemon 限制 MCP 响应、发现工具数量、重复名称、描述和 schema 总大小。
7. **阻止可变目录覆写。** 当前表仅能按 `(workspace, slug)` 保存一个条目，工作区目录发布改为数据库原子 insert-only，同 slug 的并发发布也会失败，避免已有连接在不重新验证的情况下被静默改写 host、schema 或工具范围。
8. **补齐工具缺失诊断。** 控制面仍以当前 approved tools 重算验证状态；若 discovery 缺少任一已获准工具，会持久化 `degraded`、`mcp.approved_tool_missing` 和有限的工具名摘要，同时保留本次 discovery 快照，连接不会进入任务能力清单。
9. **补齐已连接服务的安全诊断与配置更新。** 列表显示上次验证、脱敏失败摘要和可展开的获准工具；“管理配置”进入显式替换模式，不回显 endpoint、非密钥配置或密钥，填写的密钥才会轮换。服务端更新工具范围时若新增高风险工具，必须再次提供高风险确认，不能通过配置更新绕过新建连接的授权要求。

## 2.5 本次推进的修复（2026-08-02）

针对审查发现的 Standards/Spec 问题，本次推进完成以下修复；未完成的项保留在第 3、4 节。

1. **任务清单 freshness check。** `listReadyMcpConnectionsForTaskSync` 现在与 daemon claim 路径共用同一套 freshness 校验：重新读取当前 `runtime_mcp_connection` 状态行、确认仍为 `ready`、确认每个 approved tool 仍存在于最新 discovery snapshot。任一条件失败即排除该连接，并在 approved tool 缺失时将其置为 `degraded`。见 `packages/services/src/mcp-center/connections.ts`。
2. **配置编辑脏态保护。** `mcp-market-panel.tsx` 新增 `dirtyEndpoint` / `dirtyNonSecretParams` 状态。进入“管理配置”时所有字段视为未触碰；只有用户实际修改的 endpoint / 非密钥配置才会传给 `replaceMcpConnectionConfigAction`，未编辑字段以 `undefined` 传递，服务端保持原值。留空的密钥不参与轮换。
3. **原子替换已验证。** `replaceMcpConnectionConfigSync` / `replaceMcpConnectionConfigAction` 已在单一事务内完成配置更新、多密钥轮换、一次 reverify 和一次审计；测试覆盖回滚场景。
4. **Runtime Provider 兼容性预检。** `market-page-loader.ts` 将 `mcpEligible` 收紧为仅 `claude`，因为当前只有 Claude adapter 实现了 `--mcp-config` + `--strict-mcp-config` 的一次性 task-scoped MCP 注入。市场页 Runtime 选择器现在显示“支持 MCP / 不支持 MCP”。Codex 等 Provider 在等价临时配置验证通过前不会获得 MCP 会话。
5. **Gateway 逐调用状态复核。** `McpGateway` 现在接受可选的 `validateConnection` 回调；`executeRemoteTask` 通过 `HttpDaemonClient` 在每次工具调用前请求 `POST /api/daemon/tasks/:taskId/mcp-connections/:connectionId/validate`。该端点重新读取连接状态并校验工具仍在 approved 与 discovery snapshot 中；连接被停用、改配或工具失效后，正在运行的 task session 会立即拒绝后续调用。实现见 `packages/daemon/src/mcp/gateway.ts`、`packages/daemon/src/remote-daemon.ts`、`apps/web/app/api/daemon/tasks/[taskId]/mcp-connections/[connectionId]/validate/route.ts` 与 `packages/services/src/mcp-center/connections.ts` 的 `validateMcpConnectionForGatewaySync`。
6. **任务授权再校验 catalog 声明工具。** `resolveReadyMcpConnectionForTask` 在 freshness check 中新增 approved tools ⊆ catalog declaredTools 的校验：若目录降级导致已批准工具不再被声明，连接会被排除并置为 `degraded`，防止运行中任务获得目录已移除的工具。见 `packages/services/src/mcp-center/connections.ts`。
7. **一次性 session claim 标记。** `agent_task_queue` 新增 `mcp_session_claimed_at`；`claimMcpTaskSessionSync` 在首次 claim 时原子设置标记并返回 resolved bundle，重复调用返回空连接列表，避免同一 task 被多次授予 MCP 能力。实现见 `packages/db/src/task-queue.ts`、`packages/services/src/mcp-center/connections.ts`。
8. **审计逐调用持久化。** `McpGateway.onAudit` 改为支持异步回调；`executeRemoteTask` 不再使用内存 sink 批量上报，而是在每次工具调用后通过 `HttpDaemonClient.reportMcpToolAudits` 立即写入一条审计。daemon 崩溃时最多丢失正在进行的调用审计，而非整个 task 的审计链。控制面 `POST /api/daemon/tasks/:taskId/mcp-tool-audits` 已校验 daemon 身份与 task 归属，并持久化 connectionId、toolName、outcome、latencyMs 与 redacted summary。实现见 `packages/daemon/src/mcp/gateway.ts`、`packages/daemon/src/remote-daemon.ts`、`apps/web/app/api/daemon/tasks/[taskId]/mcp-tool-audits/route.ts`。

## 2.6 本次推进的修复（2026-08-02，二次审查）

针对二次审查发现的问题，本轮完成以下修复：

1. **Codex MCP 注入（尽力隔离）。** `buildCodexMcpGatewayArgs` 从“追加单 server”改为**整表替换 `mcp_servers`**（`--config 'mcp_servers={ "dofe-mcp-gateway" = { url = "…" } }'`），并在 codex adapter 注入 `--ignore-user-config`（清空 `$CODEX_HOME/config.toml` 层，auth 仍用 CODEX_HOME，登录状态保留；首执行与 `exec resume` 共用 baseArgs）。codex 没有 flag 能禁用 project/cloud 配置层，因此隔离是尽力而为——真正的 gate 是第 5 条的可选开关。
2. **Codex 市场资格回退 + 实验开关。** `market-page-loader.ts` 的 `mcpEligible` 恢复为仅 `claude`，Codex 需显式 `MCP_CODEX_EXPERIMENTAL_ENABLED=1` 才可选。“能拼出启动参数”不再等于“已支持”。
3. **一次性 claim 与 HTTP 重试解耦。** `claimMcpTaskSession` 携带 `attemptId`；服务端首次 claim 缓存 resolved bundle，同一 attemptId 的重试返回缓存结果（响应丢失不再把任务降级为“无 MCP”），不同 attemptId（真正的重复执行）返回空列表拒绝。缓存为进程内存，控制面重启后重试降级为空。
4. **Gateway MCP session 与任务 token 强绑定。** `McpSessionEntry` 记录所属 task token；每次请求用 `mcp-session-id` 取 session 时校验 `entry.token === token`，跨任务复用 session header 返回 403。测试覆盖“复用另一任务 session header 必须被拒绝”。
5. **审计归属与幂等。** `POST /mcp-tool-audits` 固定使用 URL 中的 taskId（请求体 `taskId` 不再生效），校验 connection 属于该 workspace，并以客户端生成的 `event_id` 做幂等去重（`UNIQUE(workspace_id, event_id)`，重放返回原行）。gateway 每次工具调用生成 `event_id`。
6. **健康巡检与活动页落地。** `scheduleMcpHealthChecksSync` 已接入 runtime-maintenance cron 阶段；`next_health_check_at`、失败指数退避（1h→1d 上限）、连续失败计数、`degraded` 降级、operation `source` 分类（`user_verify|config_change|secret_rotation|health_check|enable|remove`）均已实现。连接详情页 `/market/mcp-connections/:id` 提供“概览/工具/配置/活动”四 Tab，活动聚合 operations 与 tool audits。

## 3. P0：任务调用路径——Claude Gateway 已实现，Codex 注入已实现但未验证

`packages/daemon/src/mcp/gateway.ts` 已实现 daemon 常驻 loopback Streamable HTTP gateway，并具备以下能力：

- daemon 通过已认证的 `POST /api/daemon/tasks/:taskId/mcp-session` 认领一次性 resolved connection bundle（endpoint + 密钥），结果仅保存在 daemon 内存。
- `executeRemoteTask` 为运行中 task 创建 gateway session，并把随机 session URL 通过 `mcpGatewayUrl` 传给 `runProviderTask`；task 结束、取消、超时或失败时撤销 session 并上报审计。
- gateway 校验 `taskId + connectionId + toolName` 白名单，拒绝跨 task、跨连接、未获准工具和越权调用；`mcp-session-id` 强绑定到任务 token，跨任务复用被拒绝。
- Claude adapter 使用 `--mcp-config '{"dofe-mcp-gateway":{"type":"http","url":...}}' --strict-mcp-config`；Codex adapter 使用 `--ignore-user-config` + `--config 'mcp_servers={ "dofe-mcp-gateway" = { url = "…" } }'`。Provider 仅获得 loopback URL，不获得远端 endpoint 或密钥。
- gateway 测试已覆盖：工具列表不泄露 endpoint/密钥、Approved 工具调用与审计、非白名单工具拒绝、session 撤销后拒绝访问、复用另一任务 session header 被拒绝。

**仍不满足“任务可调用 MCP”承诺的缺口：**

1. **Codex 注入已实现但未验证。** Codex adapter 已消费 `mcpGatewayUrl` 并整表替换 `mcp_servers` + `--ignore-user-config`；但 codex 无 flag 可禁用 project/cloud 配置层，隔离是尽力而为，且尚未在真实 codex 版本上完成端到端验证。因此市场页默认不将 Codex 标记为 MCP 可用（需 `MCP_CODEX_EXPERIMENTAL_ENABLED=1`）。
2. **缺乏真实 Claude / Codex CLI 端到端验证。** gateway 单元测试通过，但尚未在真实 Runtime 任务中验证工具调用、审计落库、撤销中断和 session 生命周期。验收清单见 `08-claude-e2e-验收清单.md`。
3. **egress 策略未落地。** daemon 已完成 DNS 解析、socket pinning 和私网/metadata 拒绝，但容器二层出网仍依赖 Compose/受管 node 的网络策略，尚未以容器集成测试验证 Provider 不能绕过 gateway 直连 MCP。

因此，当前**仅可宣称 Claude Runtime 具备任务调用 MCP 的实验能力**，在通过真实 CLI 端到端验证前不得对外承诺“任务可调用 MCP”。Codex 注入已实现但保持默认不可选，直到隔离与 E2E 验证通过；其他 Provider 不暴露 MCP。

## 5. 发布判定

当前版本**必须作为“目录配置与远端连通性验证”内测能力发布**：

- 界面继续使用“已验证”措辞，`ready` 仅表示远端连接和凭据已被 daemon 验证成功，不等于已向任务暴露工具。
- **Claude Runtime 可进入“任务调用 MCP”内部验证**：gateway、一次性凭据 claim（attemptId 幂等重试）、白名单、session 与任务 token 强绑定、调用审计逐调用持久化（event_id 幂等）均已实现，但需通过真实 Claude CLI 端到端验证（见 `08-claude-e2e-验收清单.md`）后才能升级承诺。
- **Codex 注入已实现但默认不可选**：整表替换 `mcp_servers` + `--ignore-user-config` 为尽力隔离，project/cloud 配置层尚无 codex flag 可禁用；需 `MCP_CODEX_EXPERIMENTAL_ENABLED=1` 显式开启，并在指定 CI 环境通过隔离与端到端验证后才可正式开放。
- 健康巡检与连接详情活动页已实现；完整“MCP 中心”能力仍待：真实 CLI 端到端验证、Codex 隔离与 E2E 验证、二层 egress 约束、目录 release 版本、市场分类筛选、受管 stdio/OAuth。
