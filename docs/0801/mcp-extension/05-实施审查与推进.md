# MCP 扩展实施审查与推进

> 审查日期：2026-08-02
>
> 范围：`docs/0801/mcp-extension` 的目标方案，以及当前工作区中 MCP 中心、控制面、Runtime daemon 和 CLI bridge 的实现。
>
> 结论：MCP 市场的目录、连接、验证和审计数据面已具备可继续开发的骨架；但“模型在任务中调用 MCP 工具”尚未安全实现，不能将连接状态对外承诺为任务可调用。

## 1. 已实现且与方案一致的部分

| 能力 | 当前实现 | 审查结论 |
| --- | --- | --- |

## 2. 本次已推进的修复

1. **修复启用状态机。** `enable` 操作完成后也持久化验证结果，使成功连接可由 `queued_verification` 正确进入 `ready`，而不是永久停留在等待状态。
2. **收紧密钥流向。** 一次性 daemon operation claim 由控制面解密并直接交付该次认证请求；daemon 不再需要控制面加密主密钥来执行远程验证。
3. **收紧外连和日志。** 拒绝 HTTP 重定向及非 443 HTTPS 端口、URL 凭据/query/fragment；每次 MCP 请求重新解析 DNS，拒绝任一私网/metadata 答案并将 TLS socket 固定到校验后的地址；拒绝危险/多行请求头；已连接服务的市场 payload 不再包含 endpoint；daemon 错误会结合当前连接真实密钥做二次脱敏，完成/失败回调也会在服务端脱敏。
4. **收敛 UI 真实能力。** 非 `streamable_http` 目录项不能建立连接；数据库 `ready` 在 UI 中显示为“已验证”，不再显示为“已就绪”；CLI/MCP Tab 使用 URL history 导航并随浏览器返回同步状态。
5. **栅栏化连接操作。** 配置、密钥、停用和删除会取消未完成 operation；只有 `queued_verification` 连接可以被 claim，只有 `running` operation 可以写入完成/失败结果，过期验证无法恢复被停用或更新后的连接。
6. **限制不受信任的目录和响应。** workspace 私有目录一律按高风险处理；非密钥配置必须匹配审核 schema 且拒绝额外字段；应用市场仅渲染 schema 中声明的固定字段，不提供自由 header 输入；operation claim 与完成回调都会对历史连接重新校验 endpoint、schema、header 与工具范围，不合规记录安全失败并等待管理员整改；daemon 限制 MCP 响应、发现工具数量、重复名称、描述和 schema 总大小。
7. **阻止可变目录覆写。** 当前表仅能按 `(workspace, slug)` 保存一个条目，工作区目录发布改为数据库原子 insert-only，同 slug 的并发发布也会失败，避免已有连接在不重新验证的情况下被静默改写 host、schema 或工具范围。
8. **补齐工具缺失诊断。** 控制面仍以当前 approved tools 重算验证状态；若 discovery 缺少任一已获准工具，会持久化 `degraded`、`mcp.approved_tool_missing` 和有限的工具名摘要，同时保留本次 discovery 快照，连接不会进入任务能力清单。

## 3. P0：任务调用路径尚未安全落地

当前代码已将无密钥的 `RuntimeMcpConnectionContextEntry` 注入 task input bundle，供 Runtime 为未来 gateway 建立 task-scoped allow-list；但 `runProviderTask` 尚未通过 `codex mcp` 或 `claude --mcp-config` 注册 MCP server。因此 Provider 任务仍没有可调用 MCP 工具，`runtime_mcp_tool_audit` 也不会产生真实调用审计。

更关键的是，现有 bridge 设计将 task registry 写入与 Provider 同一 Runtime 用户可读的文件。即使权限是 `0600`，同 UID 的 Provider 进程仍可读取其中的 endpoint 和密钥。这不满足架构文档中“Provider 不获得 MCP 凭据”的要求，不能通过简单接入 CLI 参数来完成。

为避免未完成能力被误接入，公开的 `dofe-agent mcp-bridge` 子命令已显式禁用，基于 Provider 可读 registry 的 bridge 实现已删除。它不是当前可用的 Provider 配置方式。

### 必须的替代实现

在宣称任务可调用前，实施一个 **daemon 常驻本地 MCP gateway 或独立凭据进程**：

1. gateway 以不同于 Provider 的受限身份运行，保存连接密钥于内存或仅其可读的短期凭据文件；Provider 不拥有控制面主密钥，也不能读取 registry。
2. Provider 的 Codex/Claude MCP 配置只注册本地 gateway 地址和 task-scoped connection/tool allow-list，不含远端 endpoint 或密钥。
3. gateway 根据 `taskId + connectionId + toolName` 强制校验工作区、Runtime、连接状态和 approved tools，并在调用前后写入 `runtime_mcp_tool_audit`。
4. gateway 仅能通过 Runtime 的 allow-listed egress 出网；对 DNS 解析后的 IP 再做私网/metadata 拒绝，并拒绝重定向。
5. task 结束、取消或超时时注销 session；后续请求一律拒绝。测试必须证明 Provider 进程不能读取远端密钥且不能越权调用其他连接。

在上述 gateway 完成前，`ready` 仅表示“远端连接已验证”，不是“已向任务暴露工具”。

### Gateway 落地顺序与 Provider 约束

现有 Runtime 可安全传递无密钥 manifest，但不能从 task bundle 取得远端连接凭据。因此 gateway 必须由 daemon 在 task 已 claim 且开始执行后向控制面认领，不能通过 Provider 可读文件、环境变量或启动参数携带远端 endpoint/密钥。

1. 新增 daemon-only 的 task MCP session claim：仅匹配 `workspaceId + runtimeId + taskId` 的运行中 task 可获取一次性 resolved connection bundle；控制面再次确认连接为 `ready`、工具仍在 `approved ∩ discovered`，并执行 freshness check。结果只交给 daemon 内存。
2. daemon 为该 task 启动 loopback Streamable HTTP gateway。Provider 只得到随机 task session URL；gateway 将 URL session 映射到内存中的 connection/tool allow-list，并拒绝过期、跨 task、跨 Runtime、未获准工具和超限参数。
3. gateway 通过现有 Runtime MCP client 发起远端调用，并写入 `runtime_mcp_tool_audit`；任务完成、取消、超时或 daemon 重启立即撤销 session。远端 endpoint、header、非密钥配置和密钥均不得出现在 Provider 的 MCP 配置中。
4. Provider 分阶段启用。当前本机 Claude CLI 支持一次性 `--mcp-config` 与 `--strict-mcp-config`，可作为首个受支持 Provider；当前 Codex `exec` 帮助未提供等价的一次性 MCP 配置参数，不能使用会写入长期用户配置的 `codex mcp add` 作为替代。Codex 的 task-scoped config 注入方式必须先在目标版本上验证，再进入发布范围。

这意味着 P0 的最小可发布面应先限定为“Claude Runtime + 远程 streamable_http MCP”；其他 Provider 保持不暴露 MCP，直到其等价的临时配置与会话清理测试通过。

## 4. 仍需完成的 P1/P2

| 优先级 | 项目 | 完成标准 |
| --- | --- | --- |
| P1 | 健康巡检与降级 | 需由在线 Runtime daemon 执行验证，不能由控制面 cron 直连 MCP；先为 operation 增加 `user_verify`、`config_change`、`health_check` 来源，并引入 `next_health_check_at`、claim lease、退避和低优先级调度。健康失败置为 `degraded`，保留快照且新 task 不再获得该连接 |
| P1 | 目录配置 UI | 已按 schema 渲染固定非密钥字段、区分密钥字段且阻止缺失必填项的提交；目录现已支持来源、传输、风险、连接健康筛选，历史宽松连接在 claim 时会被阻断并显示安全错误。仍缺目录类别字段、Runtime Provider 兼容性和 egress 策略预检，以及目录条目的批量迁移/重新发布工作流 |
| P1 | 目录不可变版本与迁移 | 当前服务拒绝同 slug 覆写；批量迁移前需将 catalog 从 `(workspace, slug)` 可变 upsert 改为不可变 `(workspace, slug, version)` release，连接固定引用 release。扩大 host、工具或密钥 schema 的发布不得自动迁移既有连接 |
| P1 | 网络 egress 策略 | daemon 已执行 DNS 解析和 socket pinning；Compose 网络名称本身不能按域名实行 allow-list。受管 node 或独立 egress gateway 必须按 `Runtime + catalog allow-list` 执行二层出网约束，Runtime 不获得 Docker socket、iptables 或代理管理权限，并以容器集成测试验证 |
| P1 | 调用审计 | gateway 写入 task、actor、工具、结果、延迟与安全错误码；不持久化参数和返回内容 |
| P2 | 受管 stdio MCP | 按 `04-运行环境隔离决策.md` 在独立受管服务容器中运行，固定 digest、私网和短期密钥，不在宿主机或 Provider Runtime 中安装 |

## 5. 发布判定

当前版本可作为“目录配置与远端连通性验证”内测能力发布，前提是界面继续使用“已验证”措辞，且不把 MCP 工具注入 Provider task。只有第 3 节 gateway 和 P1 调用审计、DNS/egress 约束通过安全与集成测试后，才能发布“任务可调用 MCP”的承诺。
