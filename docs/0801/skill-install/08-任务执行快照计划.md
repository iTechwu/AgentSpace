# 任务执行快照 + 多 revision readiness 实现计划

## 背景（为什么做）

Skill 安装的 Remote 执行面（materializer/verifier/worker）已落地，但**任务还没绑定到 installation revision**。`docs/0801/skill-install/07-实施差距审查.md` P0-4 列出两个 bug + 一个缺失机制：

1. **Bug — revision 写死 `v1`**：`assertSkillInstallationReadyForTaskSync`（`packages/services/src/skills/installations.ts:356-361`）调用 `readSkillInstallationByLockSync` 时硬编码 `revision: "v1"`。升级产生 v2/v3 后，任务门禁查错行、误判未就绪。
2. **Bug — 门禁与物化的 digest 不一致**：门禁 `collectSkillReadinessBlockers` 用 `assignment pin ?? skill.active_artifact_digest`（`task-context.ts:1180`），但物化 `tryMaterializeFromArtifact` 只读 `skill.active_artifact_digest`（`injection.ts:95`）。升级/回滚翻转 digest 时，门禁校验 A、物化写入 B。
3. **缺失 — 无任务级快照**：`agent_task_queue` 只有 `input_json`/`result_json`，没有 `{runtimeId, installationId, artifactDigest, revision}` 的不可变记录。运行中的任务会被中途升级/回滚漂移，也无在途 revision 审计。

设计意图（02-架构设计 §4.2/§6、06 §5.4/§7.2）：同一任务只读 assignment 固定的 artifact digest；运行中任务固定在创建时 revision；执行前 freshness check（fail-closed）；降级只阻止新任务，在途任务继续按已固定快照执行（不中途终止）。

## 目标

1. 门禁按 `(workspace, runtime, artifactDigest)` 解析**最高 revision 的 installation**（不再写死 v1），返回真实 status。
2. 物化使用与门禁**同一个 digest**（任务级 pin），消除漂移。
3. 任务在 prep 时生成**不可变 Skill 执行快照**并持久化；重试复用；在途任务用快照 digest 物化，不随升级漂移。
4. 执行前 **freshness check**：快照里的 installation 仍 `ready` 且 `installationId` 不变（捕获回滚把快照分支降级）；否则 fail-closed（409）。
5. 快照即审计：持久化在途任务所用 revision。

## 本轮不实现

- 中途终止运行任务（按设计不做；物化文件已进 bundle，任务按快照跑完）。
- `rollout_pin` / canary 百分比灰度（Phase 4）。
- 真实 release lock / 升级并发锁（Phase 4）。
- service catalog、managed node（Phase 3/6）。

## 关键决策（已定）

- **快照存储**：`agent_task_queue.skill_execution_snapshot_json JSONB DEFAULT NULL`（与 `input_json`/`result_json` 一致；nullable，旧任务无快照即空，无需 backfill）。不建独立副表。
- **重试时的 freshness**：每次 `getInputBundle`（含重试）都重校快照 installation 仍 ready；若被回滚降级 → fail-closed 409，**不**静默 re-resolve 到新 revision（保审计可重现）。这是"重试可重现 + fail-closed"的组合；若产品希望降级后重试自动改用新 ready revision，需另行确认。

## Slice A — 两个 bug 修复（无 schema 迁移）

### A1. 多 revision 门禁 — `packages/services/src/skills/installations.ts`
- 重写 `assertSkillInstallationReadyForTaskSync`：去掉 `revision: "v1"`。复用现有 `listSkillInstallationsSync({workspaceId, runtimeId, artifactDigest})`（`packages/db/src/skill-installations.ts:181`，不加 status 过滤），客户端按 `^v(\d+)$` 选最高 revision。
- 返回 `{ok:true, installationId, revision}` 或 `{ok:false, status, reason}`（status 取该候选真实状态，错误信息才诚实）。
- `readSkillInstallationByLockSync` 仍被 `createSkillInstallationSync`/`rollbackSkillInstallationSync` 用，import 保留。

### A2. 物化 digest 覆盖 — `packages/services/src/skills/injection.ts`
- `materializeWorkspaceSkillsForProvider` 增可选 `digestBySkillId?: Map<string,string>`，透传到两处 `writeSkillsToRoot`。
- `writeSkillsToRoot` 增 `digestBySkillId?`，按 `skill.id` 取 `overrideDigest` 传给 `tryMaterializeFromArtifact`。
- `tryMaterializeFromArtifact` 增 `overrideDigest?`：`const digest = overrideDigest ?? readActiveArtifactDigestForSkillSync(...)`。
- 全部可选参数，旧行为不变（无快照时回落原逻辑）。

### A3. `packages/daemon/src/task-context.ts`
- `materializeAgentSkills`（1024）增可选 `digestBySkillId?`，转发给 `materializeWorkspaceSkillsForProvider`。

## Slice B — 任务执行快照（schema 迁移）

### B1. 领域类型 — `packages/domain/src/skill-package.ts`
- `TaskSkillExecutionSnapshotEntry { skillId, skillName, artifactDigest, installationId, revision, status }`
- `TaskSkillExecutionSnapshot { workspaceId, runtimeId, resolvedAt, entries: Entry[] }`

### B2. Schema — `packages/db/src/postgres-schema.ts`
- `POSTGRES_SCHEMA_VERSION` `"63"` → `"64"`。
- 追加 `ALTER TABLE agent_task_queue ADD COLUMN IF NOT EXISTS skill_execution_snapshot_json JSONB`（**必须 ALTER**，既有库不会重跑 `CREATE TABLE`）。
- **不**加进 `JsonColumnName`/`TABLE_MIGRATION_PLANS.agent_task_queue.jsonColumns`（SQLite 无此列、字段不 backfill）。`ensurePostgresSchema` 启动时重放全部语句，bump 常量即可，无需迁移表/backfill。

### B3. DB 读写 — `packages/db/src/task-queue.ts`（+ `index.ts` 导出）
- `readTaskSkillExecutionSnapshotSync(taskId): TaskSkillExecutionSnapshot | null`（单列 SELECT，不动 `readQueuedTaskSync`/`mapQueuedTaskRecord`，避免改全表 SELECT）。
- `writeTaskSkillExecutionSnapshotSync(taskId, snapshot): boolean`（UPDATE 单列）。

### B4. Services 解析器 — `packages/services/src/skills/installations.ts`
- `resolveTaskSkillExecutionSnapshotSync({workspaceId, runtimeId, agentName, agentSkills})`：每个非 builtin skill，digest = `listStoredAgentSkillAssignmentsSync` 的 pin `?? readStoredSkillActiveArtifactDigestSync`（与现门禁同序，`task-context.ts:1180-1181`）；用 A1 解析器查最高 revision installation；`ready` → 入 entry，否则省略（blocker 由门禁报）。`resolvedAt` 用 `new Date().toISOString()`。
- `resolveOrLoadTaskSkillExecutionSnapshotSync(taskId, {...})`：读持久快照；存在且 `runtimeId` 匹配 → 复用；否则 resolve + write + 返回。

### B5. Daemon 接线 — `packages/daemon/src/task-context.ts`
- `prepareDaemonTaskContext`（421）：`filterRuntimeAppSkillsByRuntimeAvailability`（462）之后、`materializeAgentSkills`（464）之前，调 `resolveOrLoadTaskSkillExecutionSnapshotSync(input.task.id, {workspaceId, runtimeId, agentName, agentSkills})`。
- 由 `snapshot.entries` 构造 `digestBySkillId`，传给 `materializeAgentSkills(... , digestBySkillId)`。
- `collectSkillReadinessBlockers`（1142）增 `snapshot` 入参：**保留** `readAgentSkillRequirementSummarySync` 的配置/密钥/能力检查（1169-1178）；**只替换** installation 段（1180-1189）——每个非 builtin skill 需 (a) 快照有 entry；(b) freshness 重校 `assertSkillInstallationReadyForTaskSync(...entry.artifactDigest)` 为 ok **且** `installationId === entry.installationId`；缺 entry / 不匹配 → blocker。
- `PreparedDaemonTaskContext`（125）增 `skillExecutionSnapshot` 字段（审计可见）。两条调用方（`apps/web/.../input-bundle/route.ts:84`、`apps/cli/src/commands/daemon.ts:1065`）都传 task+runtime，按 `task.id` 持久化/复用，无需改路由。

## 测试 — 扩 `packages/daemon/src/task-context-skill-env.test.ts`（单文件，保持 workspace 隔离）

复用现有 `prepareSkillInstallationForTaskGate`（56-89）建 v1 ready；用 `createSkillUpgradePlanSync` 构造 v2。新增：
1. **多 revision 门禁**：v1 ready + v2 preparing → v2-digest 返回 `{ok:false,status:"preparing"}`、v1-digest 返回 `{ok:true,revision:"v1"}`；v2 ready 后 → `{ok:true,revision:"v2"}`。
2. **快照跨升级固定 digest**：resolve 快照后翻转 `active_artifact_digest`；`resolveOrLoad...` 同 taskId 返回原快照；`materializeAgentSkills` 仍写原 artifact 文件。
3. **回滚 freshness fail-closed**：快照 ready 后把该 installation 置 `degraded`/`rolled_back`；`collectSkillReadinessBlockers(快照)` 报 blocker。
4. **持久化 round-trip**：`readTaskSkillExecutionSnapshotSync(taskId)` 与写入一致（installationId/revision/digest）。
5. **digest 覆盖单元**：`materializeWorkspaceSkillsForProvider({...digestBySkillId})` 在 `active_artifact_digest` 不同时仍写覆盖 digest 的文件。

**共享 PG 测试库脆弱性**：`agent_task_queue`/`skill_installation`/`skill_artifact` 是全局表，node:test 并发跑会撞 ID。新测试用 `randomLikeId()` 风格唯一 ID（或复用 `enqueueNativeTaskSync`/`createSkillInstallationPlanSync`），`beforeEach` 按 workspace 清理 `DELETE FROM agent_task_queue WHERE workspace_id=?` + `DELETE FROM skill_installation WHERE workspace_id=?`。单文件扩展，不加并发第二文件。

## 已确认决策

1. **多 revision 解析**：复用 `listSkillInstallationsSync`，按 `^v(\d+)$` 最高 revision，返回真实 status。
2. **快照存储**：`agent_task_queue.skill_execution_snapshot_json` JSONB + schema 版本 bump，无 backfill。
3. **重试 freshness**：每次 prep 重校，降级即 409，不静默 re-resolve。
4. **物化 digest 覆盖**：可选参数全链透传，无快照时行为不变。
