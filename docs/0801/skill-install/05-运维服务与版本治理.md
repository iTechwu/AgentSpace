# 运维手册：Skill 支撑服务与版本治理

## 1. 适用范围与职责

本手册适用于“一个 Skill 不能仅靠包文件、依赖和现有 CLI/MCP 完成任务，且确实需要常驻服务”的场景，例如受管 stdio MCP、内部 HTTP connector、浏览器/渲染器、索引器或特定 SDK gateway。它不授权运维或 Skill 作者在宿主机安装软件，也不允许 Skill 包附带 `docker-compose.yml`、`docker run`、任意 shell 或数据库初始化命令。

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| Skill 作者 | 定义业务需要、包版本、兼容性和服务 catalog 引用 | 选择任意镜像或直接创建服务 |
| 工作区管理员 | 选择 Runtime/员工、输入业务配置、批准风险、发起安装/升级 | 查看服务密钥、修改底层网络或镜像 |
| 平台运维 | 审核服务模板、发布 image digest、设置资源/网络/告警、执行受管服务变更 | 读取业务数据或 Provider 凭据 |
| managed node | 唯一创建/停止受管服务的执行面 | 执行未经模板允许的容器、宿主机命令 |

## 2. 服务目录准入

每项服务先进入 `Skill Service Catalog`，再允许被任何 Skill 引用。目录条目必须版本化且不可变，至少包含：

```yaml
slug: document-renderer
templateVersion: 2.1.0
deploymentType: managed_service # external_connection | platform_shared
imageDigest: ghcr.io/dofe-ai/document-renderer@sha256:...
sbomDigest: sha256:...
signatureRequired: true
signatureKeyPem: <cosign public key PEM>
protocol: http # mcp_streamable_http | mcp_stdio_proxy
scope: workspace_runtime
resources: { cpu: "1", memory: "1Gi", ephemeralStorage: "2Gi" }
health: { readinessPath: "/ready", timeoutSeconds: 5 }
network: { ingress: runtime_private, egressAllowlist: ["fonts.example.com:443"] }
configSchemaVersion: 3
secrets: [RENDER_LICENSE]
externalDependencies: ["postgres:central-render-db"]
rollbackClass: backward_compatible
runAsNonRoot: true
readOnlyRootfs: true
capDrop: [ALL]
```

准入检查：镜像必须是批准 registry 的完整 `repo@sha256`；SBOM digest、cosign 公钥和 `signatureRequired=true` 必填；非 root、只读 rootfs、`cap_drop` 包含 `ALL` 为硬门槛；无 Docker socket、宿主机目录、Provider HOME 或 credential 挂载；端口仅在私网暴露；所有外部依赖是既有集中服务。模板不得创建 PostgreSQL、Redis、RabbitMQ 服务、镜像、volume 或初始化 job。

批准 registry 由控制面环境变量配置：

```bash
DOFE_AGENT_SKILL_SERVICE_ALLOWED_REGISTRIES=docker.io,ghcr.io,registry.internal.example.com
```

未设置时仅允许 `docker.io` 和 `ghcr.io`。本地 E2E registry 必须显式加入，不得把 `localhost` 或任意 registry 加入生产默认值。

`external_connection` 不部署任何容器，只保存经验证的受控连接。`platform_shared` 必须另有租户隔离、容量、数据域和 threat-model 批准，不能因一个 Skill 的需求自动创建。

### 2.1 managed node 前置条件

image-based service 只允许在满足以下条件的 Linux managed node 上启用：

1. Docker 使用可管理的 `DOCKER-USER` chain；节点安装 `iptables` 和 `ip6tables`，daemon 对规则创建、查询和删除有最小所需权限。
2. 节点安装 cosign；`COSIGN_BIN` 指向受管二进制。签名验证必须发生在 `docker pull` 前。
3. daemon state dir 位于本地持久磁盘，权限仅 daemon 用户可读写；secret generation、egress policy state 和 dependency env metadata 均在该目录下。
4. `MANAGED_RUNTIME_DOCKER_NETWORK` 只承载 Runtime 私有入站；出站仍由 per-service L3/L4 policy 强制，不能把 bridge 配置当安全边界。
5. 节点时钟、DNS resolver 和 CA bundle受运维管理；策略固定解析时的全部 A/AAAA，DNS 变化需要重新 provision/刷新策略。

任一前置条件缺失时，daemon 必须在容器启动前返回失败。不得回退到 `/etc/hosts`、不可达 DNS 或“仅记录告警”。

### 2.2 secret 注入与轮换

- 控制面只传 secret 字段名；值通过 daemon 认证通道在 claim 后获取。
- daemon 为每个 service operation 创建 generation scoped `0700` 目录和 `0400` 文件，以只读 bind mount 注入 `/run/secrets/<NAME>`；容器配置只含 `<NAME>_FILE=/run/secrets/<NAME>`。
- 非 root 模板的文件 owner 使用受管容器 UID/GID；禁止在 argv、`--env NAME=value`、日志、operation evidence 或 `docker inspect` 中出现值。
- 轮换创建新 generation 和新容器；新实例健康后再切换 binding 并删除旧 generation。失败时删除失败容器和新 generation，旧实例继续服务。
- retire 删除容器、egress policy 和全部 secret generation；清理失败进入可重试 maintenance，不静默忽略。

### 2.3 Skill Runner 镜像

含 `0755` Node.js、Python 或 Bash entrypoint 的 Skill 只允许经短生命周期 Runner 容器执行。每台 managed node 必须配置三类经过审核、与该节点 CPU 架构匹配的不可变镜像：

```bash
DOFE_SKILL_RUNNER_NODE_IMAGE=registry.example.com/dofe/skill-node@sha256:<64-hex>
DOFE_SKILL_RUNNER_PYTHON_IMAGE=registry.example.com/dofe/skill-python@sha256:<64-hex>
DOFE_SKILL_RUNNER_BASH_IMAGE=registry.example.com/dofe/skill-bash@sha256:<64-hex>
DOFE_SKILL_RUNNER_TIMEOUT_MS=60000
```

daemon 在安装验证和任务 broker 启动时都会执行 `docker image inspect <repo@sha256>`；仅配置字符串但节点本地没有该 digest 时，脚本组件不会进入 ready。Runner 使用 `--pull never`，因此镜像预拉取/分发必须在运维变更窗口完成，不能依赖任务首次执行联网拉取。broker 启动后会冻结本任务使用的 digest 与 timeout；修改环境变量只对后续新 broker 生效。

镜像变量为空、使用 tag 或 digest 格式无效时，对应脚本组件在安装验证阶段进入 `blocked`，不得显示 ready。CI managed-node reconciler 要求三者均配置并在重建节点前执行 `docker pull`；本地节点可留空以保持 fail-closed。

运维发布顺序：先扫描并批准新镜像 digest，在代表性节点预拉取；更新受保护的 CI 变量并重建 managed node；执行 Node/Python/Bash smoke；观察 `skill_runner.image_not_configured`、cache/env 校验失败、timeout 和非零退出率；稳定后才回收旧 digest。回退时恢复上一组 digest 并重建节点，不修改 Skill artifact 或 installation revision。

Runner 固定使用非 root UID/GID、只读 rootfs、`network=none`、`cap-drop=ALL`、`no-new-privileges`、PID/CPU/内存/输出/超时上限。artifact、workspace、dependency env 均只读，只有任务的 `runtime-output/skill-runs` 子目录可写；不得向 Runner 注入 Provider HOME、Provider credential、Docker socket或 daemon 全量环境变量。

## 3. 创建与绑定操作步骤

1. **提出需求**：作者提供 service catalog slug、目标 Skill artifact digest、需要的协议/工具、最小资源、数据域、网络和预期兼容版本。没有 catalog 模板则先完成准入，不创建实例。
2. **运维预检**：确认目标 Runtime 在线、Runtime/服务版本兼容、私网与 egress 规则可用、外部依赖已由集中基础设施提供、配额足够、所需 secret 已在 credential store 配置。
3. **审批**：管理员确认服务会被创建在何处、能访问哪些数据/网络、影响哪些 Skill。高风险工具、网络或写入能力逐项确认。
4. **创建**：控制面写入 `managed_skill_service` 和 operation；managed node 按模板和 image digest 创建 workspace + runtime scoped 服务。禁止人工 SSH 进入节点执行 Docker 命令。
5. **验证**：执行 readiness、协议握手、最小权限调用和网络拒绝测试。MCP 服务还要完成 initialize、tools/list 与 approved-tools 交集检查。
6. **绑定**：通过验证后写入 `skill_service_binding`，重新评估依赖该服务的 installation；全部组件 ready 才允许激活员工。
7. **观测**：记录服务版本、健康、延迟、错误码、资源、operation 和脱敏审计。日志不得包含密钥、原始业务 payload 或 Provider token。

失败时，operation 标记失败并保留安全诊断；Skill installation 为 `blocked`。不得用“临时把 endpoint 写进环境变量”绕过绑定。

## 4. 版本模型

| 层 | 人类版本 | 强制锁定值 | 何时变化 |
| --- | --- | --- | --- |
| Skill 内容 | SemVer/tag | artifact SHA-256 | 任一文件变动 |
| 格式 | DSP schema version | schema digest | manifest 语义变化 |
| 依赖 | package version | lock/integrity digest | 依赖或解析器变动 |
| 服务模板 | template version | template digest | 资源、网络、schema、策略变动 |
| 服务镜像 | image tag | image digest | 服务代码/基础镜像变动 |
| 服务配置 | schema version | normalized config revision | 字段或默认行为变动 |
| MCP | protocol/version | discovered-tools fingerprint | 协议或工具 schema 变动 |
| 安装 | release label | installation revision | 任一上述 lock 变动 |

任务、审计和回滚一律使用不可变锁定值。tag、branch、`latest` 与手工输入镜像名只能用于发现候选，不能作为执行依据。

### 4.1 来源更新冻结

GitHub/GitLab 来源的“检查更新”只解析远端 ref 到 commit SHA，不下载内容、不创建 artifact；管理员另行执行“获取候选版本”后才重新导入。发生上游供应链事件、凭证异常或来源 API 大面积故障时，平台运维设置：

内容寻址去重可能让本地导入与 Git 导入共享同一个 artifact，而 artifact provenance 只保留首次落库来源。检查器优先读取 active artifact 的 `resolvedRef`；仅当该 Skill 只有一个绑定 artifact 且制品缺少 ref 时，才回退到 Skill 自身导入配置。只要已经存在候选绑定就禁止该回退，避免把候选 ref 误判为当前激活版本。

```bash
DOFE_SKILL_SOURCE_UPDATE_CHECKS_ENABLED=false
```

该开关同时禁止按需检查和候选重新导入，不影响已锁定 artifact 的现有安装与任务。解除冻结前先验证来源 API、组织公告和候选 diff；恢复变量后重启 Web 控制面。当前没有定时扫描 worker，运维不应把按需检查误认为自动更新。

## 5. 升级、blue-green 与回滚

### 5.1 变更分类

| 变更 | 策略 |
| --- | --- |
| 文档/资产，且无 executable/capability/依赖变化 | 新 artifact inspection 后可按工作区策略自动创建候选 |
| 脚本、依赖、网络、CLI、MCP 工具或权限变化 | 必须展示 diff 并由管理员重新批准 |
| 服务 image、资源、配置 schema 或健康协议变化 | 运维变更；先在代表性 Runtime 验证，再按 blue-green 或明确批次推广 |
| 可逆数据迁移 | 采用 expand -> deploy -> verify -> contract，回滚前保留旧兼容路径 |
| 不可逆数据迁移 | 维护窗口和显式变更单；禁止自动回滚，必须有恢复演练 |

### 5.2 操作顺序

1. 发布新模板和 image digest，不修改现有模板版本。
2. 解析受影响 Skill release，生成 content/dependency/service/config/MCP capability diff。
3. 在代表性 Runtime 创建新 installation 和 blue 服务实例，运行健康、隔离、任务级 smoke test。
4. 管理员批准后以分批 assignment rollout 切换新 revision；每批观察错误率、延迟、runner 拒绝和 MCP 工具失败率。
5. 达到退出阈值立即停止推广，将未切换 assignment 保持在旧 revision；对 `stateless` 或 `backward_compatible` 服务显式回绑 green。
6. 稳定后才回收旧服务实例、旧 cache 与旧密钥版本，保留 digest、operation 和审计记录到既定保留期。

## 6. 日常运行与事件处理

| 信号 | 处理 |
| --- | --- |
| readiness 失败或 MCP 验证失败 | 标记服务与依赖 installation degraded；新任务不注入能力；运行复验或回滚 |
| 镜像 digest/SBOM 出现高危告警 | 暂停新安装，评估影响，发布修复 digest，走 blue-green；必要时停用 binding |
| 运行时资源超限 | 限流或停止实例，保留诊断；不要扩大权限或在宿主机临时运行 |
| 外部数据库/缓存故障 | 使用集中基础设施的既有事件流程；Skill 服务不自行拉起替代 PostgreSQL/Redis/RabbitMQ |
| 密钥轮换 | 在 credential store 新增版本，逐实例重载/重建、验证后废弃旧版本；不将旧值回显给管理员 |
| 退役 | 停止新 assignment -> 清空/迁移业务状态按模板策略 -> 删除 service instance/binding -> 回收专属 state volume -> 保留审计 |

## 7. 变更验收与应急门槛

每次服务模板或 production-like rollout 必须证明：镜像 digest 与 catalog 一致；容器身份/只读文件系统/无 socket/无 Provider credential；网络仅能到 allow-list；`docker inspect`/进程列表/日志无 secret；服务健康与协议检查通过；新旧 Skill revision 可独立运行；停用服务后新任务不再获得相应能力；回滚演练在目标 RTO 内完成。

### 7.1 Linux 负面验证清单

在指定测试环境以真实容器执行并保存审计证据：

```text
[ ] allow-list 目标 IPv4/IPv6 + 精确端口成功
[ ] 非允许域名、raw IPv4、raw IPv6、其他端口失败
[ ] DNS 与 DoH 旁路失败
[ ] 空 allow-list 所有出站失败，Runtime 私有健康探针仍成功
[ ] docker inspect / ps / daemon log / operation evidence 无 secret 值
[ ] secret 轮换后旧 generation 删除，失败轮换不影响 green
[ ] daemon crash/restart 后规则重建或容器保持 fail-closed
[ ] retire 后容器、iptables/ip6tables chain、secret generation 全部清理
```

上线门禁脚本必须返回明确成功/失败，并由发布流水线保存结果。当前工作站禁止 Jenkins，因此本地只实现和验证代码，不代替指定环境的门禁执行。

本工作站不启动 Jenkins、Docker 中的 Jenkins 或远程 Jenkins job。这里的运维步骤描述的是平台控制面与 managed node 的目标行为；本地工作仅完成实现、测试以及用户明确授权的提交或推送。
