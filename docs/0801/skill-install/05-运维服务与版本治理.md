# 运维手册：Skill 支撑服务与版本治理

## 1. 适用范围与职责

本手册适用于“一个 Skill 不能仅靠包文件、依赖和现有 CLI/MCP 完成任务，且确实需要常驻服务”的场景，例如受管 stdio MCP、内部 HTTP connector、浏览器/渲染器、索引器或特定 SDK gateway。它不授权运维或 Skill 作者在宿主机安装软件，也不允许 Skill 包附带 `docker-compose.yml`、`docker run`、任意 shell 或数据库初始化命令。

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| Skill 作者 | 定义业务需要、包版本、兼容性和服务 catalog 引用 | 选择任意镜像或直接创建服务 |
| 工作区管理员 | 选择 Runtime/员工、输入业务配置、批准风险、发起安装/升级 | 查看服务密钥、修改底层网络或镜像 |
| 平台运维 | 审核服务模板、发布 image digest、设置资源/网络/告警、执行受管服务变更 | 读取业务数据或 Provider 凭据 |
| managed node | 唯一创建/停止受管服务的执行面 | 执行未经模板允许的容器、宿主机命令 |

## 2. 服务目录准入

每项服务先进入 `Skill Service Catalog`，再允许被任何 Skill 引用。目录条目必须版本化且不可变，至少包含：

```yaml
slug: document-renderer
templateVersion: 2.1.0
deploymentType: managed_service # external_connection | platform_shared
imageDigest: sha256:...
protocol: http # mcp_streamable_http | mcp_stdio_proxy
scope: workspace_runtime
resources: { cpu: "1", memory: "1Gi", ephemeralStorage: "2Gi" }
health: { readinessPath: "/ready", timeoutSeconds: 5 }
network: { ingress: runtime_private, egressAllowlist: ["fonts.example.com:443"] }
configSchemaVersion: 3
secrets: [RENDER_LICENSE]
externalDependencies: ["postgres:central-render-db"]
rollbackClass: backward_compatible
```

准入检查：镜像必须来自批准 registry 并锁定 digest；SBOM、漏洞与许可证检查通过；非 root/只读 rootfs/`no-new-privileges`/`cap_drop: ALL` 生效；无 Docker socket、宿主机目录、Provider HOME 或 credential 挂载；端口仅在私网暴露；所有外部依赖是既有集中服务。模板不得创建 PostgreSQL、Redis、RabbitMQ 服务、镜像、volume 或初始化 job。

`external_connection` 不部署任何容器，只保存经验证的受控连接。`platform_shared` 必须另有租户隔离、容量、数据域和 threat-model 批准，不能因一个 Skill 的需求自动创建。

## 3. 创建与绑定操作步骤

1. **提出需求**：作者提供 service catalog slug、目标 Skill artifact digest、需要的协议/工具、最小资源、数据域、网络和预期兼容版本。没有 catalog 模板则先完成准入，不创建实例。
2. **运维预检**：确认目标 Runtime 在线、Runtime/服务版本兼容、私网与 egress 规则可用、外部依赖已由集中基础设施提供、配额足够、所需 secret 已在 credential store 配置。
3. **审批**：管理员确认服务会被创建在何处、能访问哪些数据/网络、影响哪些 Skill。高风险工具、网络或写入能力逐项确认。
4. **创建**：控制面写入 `managed_skill_service` 和 operation；managed node 按模板和 image digest 创建 workspace + runtime scoped 服务。禁止人工 SSH 进入节点执行 Docker 命令。
5. **验证**：执行 readiness、协议握手、最小权限调用和网络拒绝测试。MCP 服务还要完成 initialize、tools/list 与 approved-tools 交集检查。
6. **绑定**：通过验证后写入 `skill_service_binding`，重新评估依赖该服务的 installation；全部组件 ready 才允许激活员工。
7. **观测**：记录服务版本、健康、延迟、错误码、资源、operation 和脱敏审计。日志不得包含密钥、原始业务 payload 或 Provider token。

失败时，operation 标记失败并保留安全诊断；Skill installation 为 `blocked`。不得用“临时把 endpoint 写进环境变量”绕过绑定。

## 4. 版本模型

| 层 | 人类版本 | 强制锁定值 | 何时变化 |
| --- | --- | --- | --- |
| Skill 内容 | SemVer/tag | artifact SHA-256 | 任一文件变动 |
| 格式 | DSP schema version | schema digest | manifest 语义变化 |
| 依赖 | package version | lock/integrity digest | 依赖或解析器变动 |
| 服务模板 | template version | template digest | 资源、网络、schema、策略变动 |
| 服务镜像 | image tag | image digest | 服务代码/基础镜像变动 |
| 服务配置 | schema version | normalized config revision | 字段或默认行为变动 |
| MCP | protocol/version | discovered-tools fingerprint | 协议或工具 schema 变动 |
| 安装 | release label | installation revision | 任一上述 lock 变动 |

任务、审计和回滚一律使用不可变锁定值。tag、branch、`latest` 与手工输入镜像名只能用于发现候选，不能作为执行依据。

## 5. 升级、灰度与回滚

### 5.1 变更分类

| 变更 | 策略 |
| --- | --- |
| 文档/资产，且无 executable/capability/依赖变化 | 新 artifact inspection 后可按工作区策略自动创建候选 |
| 脚本、依赖、网络、CLI、MCP 工具或权限变化 | 必须展示 diff 并由管理员重新批准 |
| 服务 image、资源、配置 schema 或健康协议变化 | 运维变更；先在 canary Runtime 验证，再逐批推广 |
| 可逆数据迁移 | 采用 expand -> deploy -> verify -> contract，回滚前保留旧兼容路径 |
| 不可逆数据迁移 | 维护窗口和显式变更单；禁止自动回滚，必须有恢复演练 |

### 5.2 操作顺序

1. 发布新模板和 image digest，不修改现有模板版本。
2. 解析受影响 Skill release，生成 content/dependency/service/config/MCP capability diff。
3. 在代表性 canary Runtime 创建新 installation 和服务实例，运行健康、隔离、任务级 smoke test。
4. 管理员批准后以分批 assignment rollout 切换新 revision；每批观察错误率、延迟、runner 拒绝和 MCP 工具失败率。
5. 达到退出阈值立即停止推广，将未切换 assignment 保持在旧 revision；对 `stateless` 或 `backward_compatible` 服务回滚 image/binding。
6. 稳定后才回收旧服务实例、旧 cache 与旧密钥版本，保留 digest、operation 和审计记录到既定保留期。

## 6. 日常运行与事件处理

| 信号 | 处理 |
| --- | --- |
| readiness 失败或 MCP 验证失败 | 标记服务与依赖 installation degraded；新任务不注入能力；运行复验或回滚 |
| 镜像 digest/SBOM 出现高危告警 | 暂停新安装，评估影响，发布修复 digest，走 canary；必要时停用 binding |
| 运行时资源超限 | 限流或停止实例，保留诊断；不要扩大权限或在宿主机临时运行 |
| 外部数据库/缓存故障 | 使用集中基础设施的既有事件流程；Skill 服务不自行拉起替代 PostgreSQL/Redis/RabbitMQ |
| 密钥轮换 | 在 credential store 新增版本，逐实例重载/重建、验证后废弃旧版本；不将旧值回显给管理员 |
| 退役 | 停止新 assignment -> 清空/迁移业务状态按模板策略 -> 删除 service instance/binding -> 回收专属 state volume -> 保留审计 |

## 7. 变更验收与应急门槛

每次服务模板或 production-like rollout 必须证明：镜像 digest 与 catalog 一致；容器身份/只读文件系统/无 socket/无 Provider credential；网络仅能到 allow-list；服务健康与协议检查通过；新旧 Skill revision 可独立运行；停用服务后新任务不再获得相应能力；回滚演练在目标 RTO 内完成。

本工作站不启动 Jenkins、Docker 中的 Jenkins 或远程 Jenkins job。这里的运维步骤描述的是平台控制面与 managed node 的目标行为；本地工作仅完成实现、测试以及用户明确授权的提交或推送。
