# Skill 安装实施差距复审（第四轮）

> 复审日期：2026-08-03
>
> 审查范围：`docs/0801/skill-install`、当前提交历史，以及 domain / db / services / daemon / web 的生产调用链和定向测试。
>
> 结论：**当前实现已经超过“控制面原型”，具备 Remote artifact、依赖安装、任务快照、版本审批、managed service 和卸载/退役的完整骨架；但仍存在“安装验证成功、任务实际不可用”、网络与 secret 隔离失真、跨层事务不原子等问题。系统尚不能对不受信任 Skill 宣称生产可用。**

## 1. 本轮重新确认的完成项

以下旧问题已有生产调用链和测试，不再作为独立阻断项：

1. **安装 operation 协议已 fail-closed。** complete/fail 共享 parser、冻结组件集合、artifact evidence、组件与 operation 原子更新均已实现。
2. **任务 revision snapshot 已实现。** 任务固定 `runtimeId + installationId + artifactDigest + revision`，重试复用，并在执行前做 freshness check。
3. **安装组件已去重。** entrypoint 与同一 `0755` 文件只生成一个 script component；service declaration 也会生成 service component。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L144)。
4. **任务 bundle 已保留 mode。** Web 传递 executable mode，Daemon materialize 后 chmod；旧的“0755 变 0644”问题已关闭。见 [bundle.ts](../../../packages/daemon/src/bundle.ts#L13)。
5. **cache 已增加逐文件 SHA、额外文件和 root digest 检查。** 同尺寸文件篡改不再直接命中。
6. **operation 已有 lease、heartbeat 和过期重排。** skill installation 与 managed service 都会续租，并由 maintenance requeue 过期 operation。
7. **依赖安装不再只看声明。** npm/pip/uv 使用精确版本、受控 registry、隔离目录和独立产物验证。
8. **managed service 执行骨架已落地。** 包含 catalog admission、Docker 生命周期、健康检查、cosign 可选验证、secret 获取、binding、卸载、退役扫描、蓝绿切换和门控 real-Docker E2E。
9. **版本治理后端明显完善。** release lock、unresolved required、持久 approval、diff hash、same-runtime/ready/lineage 检查和一次性消费均已实现。

这些进展是真实的，但部分实现只完成了“准备/验证”，没有完成任务期消费；部分安全测试只断言生成了参数，没有验证策略真的不可绕过。

## 2. 仍然阻断上线的问题

### P0-1：依赖安装目录没有进入任务执行环境

[operation-worker.ts](../../../packages/daemon/src/skill-install/operation-worker.ts#L103) 把依赖安装到 installation 专属 `skill-install-envs/...`，并在 complete evidence 中记录 `installedDependencies`。但该目录只有 installer 使用；任务准备、input bundle 和 Provider 启动均没有读取它，也没有注入 `NODE_PATH`、`PYTHONPATH`、venv `PATH` 或等价只读 mount。

因此 dependency component 可以 ready，但实际 Skill 脚本在任务中仍无法 `require`/`import` 已安装包。这是当前最直接的“假 ready”。

必须完成：

- task snapshot 固定 dependency env digest/path，并与 installation/release lock 一起校验 freshness。
- Remote Daemon 启动 Provider/脚本时只读挂载对应 env，按 manager 注入最小 `PATH/NODE_PATH/PYTHONPATH`。
- 安装、任务运行和重试使用同一个 Runtime 上的同一 env，不从控制面重新构造。
- 增加真实端到端测试：安装依赖后，在 Remote task 中执行脚本并成功 import/require；删除或篡改 env 后任务必须 fail-closed。

### P0-2：managed service 的 egress allow-list 实际可绕过

[buildManagedServiceNetworkArgs](../../../packages/daemon/src/skill-service/managed-service-runtime.ts#L286) 对空 allow-list 同时添加 internal network 和共享 network。只要共享 bridge 有默认路由，容器仍可通过它出站，“空列表 = 零 egress”并不成立。

非空 allow-list 只使用不可达 DNS 加只读 `/etc/hosts`；源码已经承认 raw-IP egress 是残余风险。第三方服务可直接连接任意 IP，也可经允许主机访问代理/DoH，现有测试只检查 Docker args，不实际探测禁止目标。

必须完成：

- 使用 CNI/eBPF/nftables/受管 egress proxy 在 L3/L4 强制目的 IP/port；DNS 与 hosts 只能用于解析，不能作为边界。
- 零 egress 容器不得连接任何具有默认外网路由的网络；私有入站应通过无外网的专用网络或 sidecar/proxy 提供。
- allow-list 解析必须固定 scheme/host/port、处理 DNS rebind 和多 A/AAAA，并持续刷新策略。
- real-Docker E2E 必须从容器内验证：允许目标成功，域名旁路、任意 raw IP、IPv6 和 DNS/DoH 绕过失败。

### P0-3：service secret 通过 Docker argv/env 暴露

[buildManagedServiceContainerCreateArgs](../../../packages/daemon/src/skill-service/managed-service-runtime.ts#L143) 把 secret 拼成 `docker create --env NAME=value` 参数。即使 claim payload 和错误消息做了脱敏，secret 仍会进入 daemon 子进程 argv、Docker API/container config，并能被有 Docker 访问权的进程或 `docker inspect` 读取。

必须改为 Runtime secret store、Docker secret/file mount 或短期 broker 注入；argv、审计、container inspect 和持久 config 中不得出现明文。还需定义轮换、撤销、容器重建和 retire 后清理流程，并增加进程列表/inspect/日志负面测试。

### P0-4：安装计划、approval 和 service 完成跨层不原子

当前存在三条部分提交路径：

1. [createSkillInstallationPlanSync](../../../packages/services/src/skills/installations.ts#L80) 依次创建 installation、prepare operation，再逐个排 service operation，没有外层事务。任一 catalog/queue 失败会让 action 报错但留下部分状态。
2. [createSkillUpgradePlanSync](../../../packages/services/src/skills/release.ts#L486) 先在一个独立事务消费 approval，随后才创建 installation 和 operation；后续失败会永久消费 approval，却没有升级计划。
3. [completeManagedSkillServiceProvisionOperationSync](../../../packages/services/src/skill-services/bindings.ts#L125) 依次完成 operation、标记 service ready、创建 binding 和重算 readiness，没有统一事务。binding 失败后 operation 已 succeeded，无法正常重试。

本轮 release 测试已经暴露这一问题：required/optional 缺 catalog 均在 plan 已开始写入后抛错，release 测试 `15/18`。

必须让 plan/upgrade/service complete 各自在一个数据库事务内提交；外部 Docker 操作保留在事务外，但其控制面结果必须通过幂等、可重试的单次状态转换落库。approval 消费必须与 candidate installation、operation 和 service queue 同事务。

### P0-5：Skill upgrade 不会准备新版本声明的 service

初始安装会遍历 manifest services 调用 `queueManagedSkillServiceForInstallationSync`，但 [createSkillUpgradePlanSync](../../../packages/services/src/skills/release.ts#L486) 只创建 candidate installation 和 prepare operation，没有为 candidate 创建或复用 service binding，也没有排 service provision/upgrade。

带 service 的 v2 candidate 会在 service component 上长期 blocked；独立的 `upgradeManagedSkillServiceSync` 也没有与 Skill release diff/approval/lock 自动编排。

必须建立 release orchestrator：根据 from/to lock 计算 service keep/provision/upgrade/remove，准备完成后再激活 Skill revision；失败时保持旧 revision 和旧 binding。升级测试需覆盖新增 service、模板升级、移除 service、optional service、不可逆迁移和回滚。

### P0-6：cache 仍信任可改写 meta，未绑定当前 operation

cache hit 已重算文件 SHA 和 root digest，但 [verifyCachedFiles](../../../packages/daemon/src/skill-install/operation-worker.ts#L267) 只使用 cache 内的 `meta.files`、`meta.manifestJson` 和 `meta.expectedDigest`，没有把它们与当前 claim 的 `operation.artifactDigest/manifestJson/files` 比较。

攻击者若能同时改写 cache 文件与 meta，可构造另一套自洽 artifact 放在旧 digest 目录中并通过检查。cache 发布后也没有递归只读或不可变权限。

必须让 verifier 接收 operation，逐字段比较冻结 manifest/file set/expected digest；cache 路径名必须等于当前 artifact digest；发布后设置只读并以原子 replacement 修复坏 cache。增加 meta+file 联合篡改、manifest 替换、mode 变化和旧 cache schema 测试。

### P0-7：lease 有过期时间，但没有真正的 fencing token

skill/service operation 续租和 complete 只使用 operationId。过期 operation 被 requeue 后仍复用同一个 ID；新 worker claim 后，旧 worker可能续上新 lease并提交结果，因为请求中没有 claim generation/token。当前实现属于 timeout/requeue，不是 fencing。

必须在每次 claim 生成不可复用的 lease token 或 attempt generation，start/renew/complete/fail 全部 compare-and-set；同时增加 attempt count、指数退避、最大重试和 poison operation 状态。测试必须覆盖旧 worker 在新 claim 后迟到 renew/complete 被拒绝。

### P0-8：artifact binding 表已存在，但导入和 UI 没接通

`skill_artifact_binding` 与 upsert/resolve helper 已新增，但导入的 `prepareSkillArtifact` 仍不传 `skillId`，`setActiveArtifactDigestForSkillSync` 也不创建 binding。[listSkillArtifactsForSkillSync](../../../packages/db/src/skill-artifacts.ts#L163) 仍只按 legacy `skill_artifact.skill_id` 查询，安装历史 UI 继续调用它。

结果是导入 Skill 仍可能没有历史、lineage 和 rollback owner；两个都未绑定的 artifact 还会绕过 `assertSameSkillLineage`。

必须在导入事务中 upsert binding，所有 history/rollback/upgrade 查询改用 binding，补 migration/backfill 和唯一性约束，并测试同 digest 多 Skill、导入后 history、跨 Skill upgrade 拒绝和 rollback。

## 3. 高优先级优化项

### P1-1：artifact 下载仍缺 SSRF 和流式硬上限

[artifact-materializer.ts](../../../packages/daemon/src/skill-install/artifact-materializer.ts#L145) 仍直接 fetch claim URL，允许默认 redirect，没有 scheme/origin/private-IP 限制；无 Content-Length 时 `arrayBuffer()` 无界读入内存，小文件的 guard 也放宽到 64MB。local provider 仍依赖控制面与 Remote Daemon 共享同一 storage root。

应只接受短期 HTTPS storage URL/鉴权 blob proxy，逐跳校验 redirect 与解析 IP，流式读取到 `expectedSize + 小容差` 的硬上限，并显式校验 Remote 模式的 storage provider 能力。

### P1-2：package contract 和 ingress budget 仍不统一

- submitted manifest 仍只检查“声明文件存在”，不拒绝实际包中的未声明文件。
- submitted artifact version 仍被 frontmatter 覆盖；dependency integrity 没有权威合并规则。
- import 传给 validator/artifact 的文件仍未保留来源 mode。
- ZIP raw entry 在严格审计前 normalize，可能抹掉原始 traversal 证据。
- Git/Skills.sh/local directory 缺统一累计文件数、字节、深度、请求数和并发预算；ZIP 仍是全量内存解压。

需要一份 submitted/computed 字段权威矩阵和单一 ingress pipeline，所有来源共享 raw path audit、streaming budget、mode、provenance 和 manifest actual/declared 集合校验。

### P1-3：release lock 与 rollback 尚未成为完整执行约束

lock 已生成并能做重建检查，但 task snapshot、dependency env、service binding 和 rollback 没有共同校验同一个 lock digest。`providerCompatibilityRevision` 仍为 0。rollback 只检查 previous installation 状态，不预检 blob/cache/dependency env/service binding，也没有 compare-and-set current revision。

approval 表已持久化 policyVersion，但查询唯一键和消费校验没有包含 policyVersion；Web 仍用同一 admin 请求中的 `approved?: boolean` 即时生成 approval，缺少独立审阅页面、原因输入和职责分离策略。

### P1-4：所谓 canary 实际是一次性蓝绿全量切换

`upgradeManagedSkillServiceSync` 会创建 blue，但完成后 `switchSkillServiceBindingsSync` 一次切换 green 的全部 binding；没有流量比例、观察窗口、健康阈值、自动中止或显式回绑 green。应把 UI/文档命名改为 blue-green，或实现真正 canary rollout；冷却窗本身不等于 rollback 编排。

普通 provision binding 还写入硬编码 `catalogTemplateVersion: "1"`、`serviceImageDigest: "managed"`、`configSchemaVersion: 1`，会破坏 release/audit 真实性，应使用实际 catalog 数据。

### P1-5：service admission 的安全项仍可选

`signatureRequired` 默认 false，`runAsNonRoot` 也不是 managed_service 的硬要求；测试明确接受只有 key 但不强制验证的模板。若产品目标是运行不受信任第三方服务，应由 workspace/platform policy 强制签名、非 root、只读 rootfs、cap-drop ALL 和允许 registry，而不是由模板自我声明是否启用。

### P1-6：任务 bundle 仍缺内容 digest、聚合预算和 cache 复用

mode 已修复，但 `DaemonBundleFile` 没有 sha256，Daemon 写入后不验内容。Web 仍把完整文件 base64 内联并复制 provider 投影，没有任务级聚合文件/字节上限、分块传输或 verified Runtime cache 复用。多 Skill/大 asset 会增加控制面内存与响应体，并使安装证据与执行字节不是同一来源。

### P1-7：UIUX 仍是单步控制面入口

`InstallSkillModal` 仍只有 Runtime 单选和“创建计划”；没有 inspection、文件/脚本/依赖/license/权限审阅、配置授权、breaking diff 审批、service 运维交接或草稿恢复。安装 panel 只显示基础组件/operation 文本，缺 evidence、release lock、重试、换 Runtime、卸载和诊断动作，也没有专项组件测试。

### P1-8：迁移、更新与可观测性仍未产品化

仍缺 lineage/backfill dry-run/checkpoint、orphan artifact/cache GC、workspace 分阶段 feature flag、Skill registry 更新检查、候选版本通知，以及 import/prepare/ready/cache-integrity/dependency-env/service/rollback 指标与告警。运维还需要冻结新安装、禁用某类 capability、批量回滚和清理 stale operation 的受审计入口。

## 5. 建议实施顺序

### M0：先消除“ready 但不可运行”和安全边界失真

1. 把 dependency env 绑定 task snapshot 并注入真实任务执行。
2. 用 L3/L4 策略重做 service egress；secret 改为非 argv/inspect 的挂载或 broker。
3. 把 plan/upgrade/service complete 改为原子、幂等状态转换；补 Skill upgrade service orchestrator。
4. cache verifier 绑定当前 operation；lease 增 claim token/generation。
5. 完成 artifact binding 的 ingest、history、upgrade、rollback 全调用链。

### M1：统一供应链和执行证据

1. 修复下载 SSRF/streaming limit 与 local-provider Remote 能力协商。
2. 完成 package authority matrix、raw path、mode 和全 ingress budget。
3. 让 artifact/cache/dependency env/service binding/task snapshot 共用 releaseLockDigest。
4. bundle 增 sha256、聚合预算与分块/缓存投影。

### M2：版本治理、UI 和运维产品化

1. approval policyVersion 原子消费、rollback 健康预检/CAS、真实 canary 或准确改名 blue-green。
2. 五步安装、inspection、权限与配置、service 运维交接、失败恢复和卸载 UI。
3. backfill/GC、feature flag、更新检查、指标告警和应急 runbook。

## 7. 文档维护结论

1. 旧第三轮文档同时声称 managed-node “未实现”和“全部闭环”，并重复 egress 段落；本轮已删除这些冲突。
2. [12-依赖安装验证计划.md](./12-依赖安装验证计划.md) 应增加“任务期消费 dependency env”阶段，当前只完成 install/verify。
3. [11-版本治理后端核心计划.md](./11-版本治理后端核心计划.md) 应增加 approval 与 candidate/service queue 同事务、Skill service release orchestrator 和 stale-worker fencing。
4. 所有“安全闭环”必须以不可绕过的负面 E2E 为证据；只检查 Docker args 或记录已知 raw-IP 残余，不能标记完成。
