# Skill 安装实施差距复审

> 复审日期：2026-08-02
>
> 审查范围：`docs/0801/skill-install` 与当前 domain / db / services / daemon / web 实现及定向测试。
>
> 结论：**控制面和 artifact 基础已明显推进，但尚不具备“任何受支持形态的 Skill 在 Remote 模式下直接安装并使用”的上线条件。M0 只能判定为部分完成。**

## 1. 本轮结论

当前已经实现不可变 artifact/blob、installation/component/operation 数据模型、DSP 高级声明的部分保留、ZIP 限额、pinned artifact 完整性 fail-closed、升级 diff 和基础回滚。这些修复是真实有效的。

仍有四类上线阻断：

1. **导入不是原子操作**：先创建或更新 legacy Skill，再校验和持久化 artifact；坏包会返回失败，但已产生部分写入。
2. **Remote 执行面不存在**：Web 能创建 operation，Daemon 没有 claim/poll、artifact 下载、依赖准备或隔离 runner。
3. **任务门禁未接入**：任务仍未绑定 Runtime 上的 ready installation/revision，assignment digest pin 也没有进入任务解析路径。
4. **服务与版本治理未闭环**：service 只到 DB CRUD；approval 只是一次请求布尔值；release lock、Git SHA、canary、可重现回滚均未完成。

因此产品必须继续标记为 **开发中 / 控制面预览**。在 Daemon worker 上线前，“安装计划已创建”不能表述为“Daemon 将准备环境”。

## 2. 阻断上线的问题

### P0-1：导入校验已接入，但顺序错误，失败后会留下部分状态

`persistImportedSkillDefinition` 在新建路径先写 `skill` 和文本 `skill_file`，第 227 行才调用 validator/artifact 持久化；replace 路径同样先更新、upsert、删除旧文件，第 298 行才校验。见 [import.ts](../../../packages/services/src/skills/import.ts#L204)。

这意味着坏 manifest、digest mismatch 或超限单文件会抛错，但：

- 新建导入可能留下一个没有 active artifact 的 Skill；
- replace 可能已经覆盖描述、配置和文本文件，并删除旧文件；
- import event 不会写入，造成 UI 返回失败但工作区数据已改变。

**必须修复**：把 source resolve、原始路径检查、package validation、manifest 归一化、digest/blob 准备放在任何 Skill 写入之前；Skill、artifact 关联、active digest、文本投影和 import event 必须在同一事务提交。blob 上传若不能参加 DB 事务，需先写临时/内容寻址 blob，再以 DB 事务提交引用，并由回收任务清理孤儿 blob。

**缺失测试**：新建和 replace 各增加一个坏 manifest 用例，断言所有相关表和 active digest 在失败前后完全一致。

### P0-2：package contract 仍有语义损失和入口绕过

统一 validator 已接入 artifact 构建，`capabilities`、`services`、`entrypoints` 能够保留；坏 JSON、manifest 声明但实际缺失的文件和显式 symlink 也会拒绝。以下问题仍未完成：

1. validator 只验证“manifest 声明文件必须存在”，不验证“包内实际文件必须全部被 manifest 声明”。当前保留高级声明的测试用 `baseFiles()` 带有额外 asset，但提交 manifest 未声明该 asset，结果仍预期 `ok=true`。见 [package-validator.test.ts](../../../packages/services/src/skills/package/package-validator.test.ts#L125)。README 中“未声明文件会被拒绝”不成立。
2. 提交 manifest 的 `artifact.version` 被 SKILL.md frontmatter 覆盖；测试明确断言提交的 `1.0.0` 变成空字符串。manifest 的 dependencies/integrity 也被 legacy frontmatter parser 重建，`integrity` 无法保留。见 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts#L264)。
3. import 层构造 validator/artifact 输入时不传 `mode`，真实可执行位被扩展名启发式替代。无扩展名脚本或提交 manifest 中的 `0755` 可能变成 `0644`。见 [import.ts](../../../packages/services/src/skills/import.ts#L338)。
4. ZIP/ClawHub 先用 `normalizeSkillFilePath` 删除 `..`，再进入严格 validator；例如原始 `../evil.sh` 会变成 `evil.sh`，审计无法发现来源包曾含 traversal。见 [helpers.ts](../../../packages/services/src/shared/helpers.ts#L150) 与 [import.ts](../../../packages/services/src/skills/import.ts#L782)。
5. `buildAndPersistSkillArtifactSync` 命中已有 digest 时在设置 skill active digest 之前直接 return；去重 artifact 复用到新 Skill 实例时可能没有关联和 active pin。见 [skill-artifacts.ts](../../../packages/services/src/skills/skill-artifacts.ts#L296)。

**必须修复**：定义 submitted manifest 的权威字段合并规则；严格比较 declared/computed path 集合；先校验 raw entry name 再归一化；从 ZIP/Git/目录携带 mode；修复 artifact 去重后的 skill 关联与 pin，并覆盖删除后重建、同 digest 重导入测试。

### P0-3：Remote installation 只有协议和表，没有真实执行面

- claim/start/complete/fail 路由存在，[daemon-client.ts](../../../packages/daemon/src/daemon-client.ts#L168) 已新增 Skill operation API（`claimSkillInstallationOperation`、`startSkillInstallationOperation`、`completeSkillInstallationOperation`、`failSkillInstallationOperation`）。
- [remote-daemon.ts](../../../packages/daemon/src/remote-daemon.ts#L714) 的轮询 loop 已接入 Skill installation operation，当前以 fail-fast 明确拒绝执行（`skill_installation.remote_execution_not_implemented`），避免 operation 永远停在 `preparing` 或被伪造成功。
- 计划中的 `packages/daemon/src/skill-install/{artifact-materializer,operation-worker,runner-client}.ts` 仍不存在；claim payload 只有文件元数据，没有短期鉴权 blob URL、流式下载协议和 resume/cleanup 语义。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L153)。
- 没有 Runtime 专属 cache/env、精确依赖 resolver、无凭据/无网络 runner 和脚本 verify evidence。

**影响**：依赖、脚本、CLI 和服务仍不会在 Remote Runtime 上变为可用，但 Daemon 不再静默挂起，而是返回可观测的失败码。

**必须修复**：实现 artifact materializer（按 digest 下载并逐文件校验）、依赖 planner/verifier、受限 runner；为 claim payload 增加短期 blob URL 和 resume/cleanup 语义；complete 必须要求可验证 evidence。

### P0-4：任务投影已 fail-closed，installation readiness 已进入任务路径

`injection.ts` 对已有 active digest 的 artifact 缺失或完整性失败已经抛错，不再退回 legacy 文本，这项修复有效。见 [injection.ts](../../../packages/services/src/skills/injection.ts#L95)。

本次推进补充：

- `agent_skill` 新增 `skill_artifact_digest` 字段；[setStoredEmployeeSkillAssignmentsSync](../../../packages/db/src/skills.ts#L457) 在分配时写入 skill 当前 active digest，[rollback](../../../packages/services/src/skills/release.ts#L379) 会批量更新 assignment pins。
- [collectSkillReadinessBlockers](../../../packages/daemon/src/task-context.ts#L1142) 已按 `runtimeId + artifactDigest` 调用 `assertSkillInstallationReadyForTaskSync`；非 builtin Skill 未就绪会阻止任务启动，并返回具体原因。

仍有以下缺口：

- 任务 snapshot 尚未固定 `runtimeId + installationId + artifactDigest + revision`，执行前缺少第二次 freshness check。
- `assertSkillInstallationReadyForTaskSync` 仍固定查 `revision: "v1"`，无法正确门禁升级后的 v2/v3。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L325)。
- 在途任务没有保留所用 revision 的审计记录；状态降级后只阻止新任务，对在途任务无显式处理。

**必须修复**：任务创建时生成不可变 Skill execution snapshot；按当前 Runtime 和 assignment pin 解析最新被批准的 ready revision（支持多 revision）；执行前再次 freshness check；状态降级后阻止新任务，并保留在途任务所用 revision 的审计记录。

### P0-5：complete 协议可伪造组件成功

complete route 把请求体直接断言为类型，未进行 runtime schema 校验；services 先把 operation 标为完成，再逐条更新 Daemon 提交的 `componentStatuses`，两者不在同一事务。它没有拒绝未知、重复或缺失组件，也没有验证 artifact digest、完整性证据、runner policy、prepared location 抽象标识。见 [complete route](../../../apps/web/app/api/daemon/skill-operations/%5BoperationId%5D/complete/route.ts#L26) 和 [installations.ts](../../../packages/services/src/skills/installations.ts#L193)。

攻击或实现错误的 Daemon 可以把所有期望 key 直接报告为 ready 而不提供可验证证据；非法 payload 还可能造成 operation 已成功、组件更新失败的部分状态。

**必须修复**：对 complete/fail payload 使用共享 schema；operation claim 时固定期望组件和 artifact digest；complete 必须全量覆盖且集合完全一致；控制面验证证据摘要后重算 readiness，拒绝未知状态、重复 key 和跨 installation 数据。

## 3. 高优先级完整性、版本与服务差距

### P1-1：限额覆盖范围已扩展，但 Git/目录仍未统一

本地/上传 ZIP 与 ClawHub 已检查压缩字节、文件数、总解压字节和嵌套深度；本地目录也拒绝 symlink。这些改进有效。

仍有缺口：

- Git/Skills.sh 递归拉取没有总字节、总文件数、深度、API 请求数和并发上限。
- 本地目录没有累计总字节和深度限制；validator 自身只使用 single-file/package-files，未使用 `limits.uncompressedBytes` 和 `limits.nestingDepth`。
- fflate 全量解压在内存中，压缩炸弹可能在事后统计前已耗尽内存；需要流式或可在膨胀前终止的解压方案。

### P1-2：Git/Skills.sh 已锁定 commit SHA，ClawHub provenance 仍不足

GitHub URL 与 Skills.sh 默认分支在读取文件前已解析 commit SHA，同一次递归读取固定使用该 SHA；artifact provenance 保存 `resolvedRef` 与 `originalUrl`。见 [import.ts](../../../packages/services/src/skills/import.ts#L592)。

仍需补齐：

- Skills.sh 解析也应记录 resolver 版本和获取时间。
- ClawHub 需记录 registry package digest/signature，而不只记录下载 URL。
- 本地目录/ZIP 上传可记录来源路径/上传 ID。

所有来源应在 provenance 中保留足够信息，使旧 revision 在原始来源消失后仍可验证。

### P1-3：升级 diff 修复有效，但 approval 不是可验证审批

已有 `0755` 脚本内容变化会进入 execution/breaking，capability kind 和 service required 变化也能识别；这是有效修复。

但 `approved?: boolean` 由一次 Web action 请求直接传入：

- 没有 approval record、批准人、原因、时间和权限范围；
- 没有把批准绑定到 `fromDigest + toDigest + diffHash + policyVersion`；
- 创建计划前 active digest 可变化，存在 TOCTOU；
- service 层不强制 previous installation 为 ready、属于同 Runtime/Skill，Web action 也允许传入不同 runtimeId。见 [installation-actions.ts](../../../apps/web/features/skills/installation-actions.ts#L96) 与 [release.ts](../../../packages/services/src/skills/release.ts#L328)。

必须新增不可变 approval 实体并在事务内消费；任何 digest/diff/policy 变化使审批失效。service 层必须独立校验 previous ready、同 workspace、同 runtime、同 Skill lineage。

### P1-4：回滚只完成基础事务，归属模型和任务效果仍不完整

基础回滚现在会在一个 DB 事务内取消未完成 operation、降级当前 installation，并切换 Skill active digest 和 assignment pins，这项修复有效。见 [release.ts](../../../packages/services/src/skills/release.ts#L379)。

仍需补齐：

- `skill_artifact` 只有一个可空 `skill_id`，但 digest 在 workspace 内唯一，无法严谨表达“不可变 artifact 被多个 Skill 实例/历史 lineage 引用”；回滚不应靠 artifact 单 FK 推断目标 Skill。
- assignment pins 当前未被任务加载使用，切换字段并不等于实际任务按该版本运行。
- 回滚没有验证目标 artifact blob 健康、依赖 cache、能力/服务兼容性；服务 rollback class 未执行。
- 没有并发升级/回滚锁和 revision 乐观并发控制。

建议增加明确的 `skill_artifact_binding`/release lineage，rollback 请求固定 skillId、current installation、expected revision，并在事务中做 compare-and-set。

### P1-5：service 仍停留在数据层

[skill-services.ts](../../../packages/db/src/skill-services.ts#L53) 只有 catalog/instance/binding CRUD。installation components 不读取 manifest services。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L95)。

尚缺 catalog 准入、image digest/SBOM/签名、非 root/只读 rootfs/cap drop/无 socket/网络策略、集中外部 PostgreSQL/Redis/RabbitMQ 配置校验、managed node 生命周期、健康/协议握手、升级/蓝绿/回滚/退役 worker，以及 service readiness 向 Skill/任务状态传播。

在这些能力完成前，“需要现创支撑服务的 Skill 可直接安装”未实现。应用部署不得自行创建 PostgreSQL、Redis 或 RabbitMQ 服务。

### P1-6：release lock 不可重现

初始 lock 除 digest/schema 外均为空；升级直接写 `{}`。`computeSkillReleaseLockSync` 没有进入生产安装路径，service image/config schema、MCP tool fingerprint、provider compatibility revision 均未真实填充。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L136) 与 [release.ts](../../../packages/services/src/skills/release.ts#L350)。

需要在 installation 创建前解析完整 lock，写入 canonical JSON 和 lock digest；任务、审批、回滚、审计全部引用同一个 lock。还需历史重建测试，证明旧 revision 在来源消失后仍可从 artifact/blob/lock 恢复。

## 4. 产品、UIUX、迁移与运维未完成

### 产品与 UIUX

- 当前 `InstallSkillModal` 仍是单步 Runtime 选择器，没有“来源 -> 检查 -> Runtime -> 配置/授权 -> 确认/进度”五步向导、草稿恢复、`aria-current=step` 和 timeline。
- 没有 inspection 服务/页面，安装前无法审阅文件、脚本、依赖、license、风险、MCP/CLI/service 请求。
- 没有 breaking diff 审批界面和审批记录；只有 action 布尔参数。
- 没有 service 生命周期、健康、责任人和运维交接 UI。
- Library / Runtime installations / imports 信息架构、详情 tabs、digest/risk/聚合状态/分配数仍不完整。
- 安装 modal/panel/action 缺专项交互、可访问性和错误恢复测试。

P0-3 完成前应以 workspace feature flag 隐藏安装命令，或把操作明确命名为“创建安装计划（执行器未启用）”。

### 迁移、可观测性与运维

- 有 legacy artifact helper 和健康检查，但无可重入 backfill job、checkpoint、dry-run、失败报告、assignment 映射和回滚演练。
- 无 workspace 级 inspection-only -> assets -> dependencies -> scripts/MCP/service 渐进开关。
- 无 import/prepare 成功率、ready 延迟、runner 拒绝、任务门禁失败、capability/service 健康、rollback 指标和告警。
- 无冻结 capability kind、停止新 installation、批量回滚 assignment 的运维开关和自动化 runbook。
- 无 Remote Runtime 的无凭据/无网络/无 socket/资源超限/中断恢复/清理集成证据。
- 无 artifact/lock schema 版本迁移策略、旧版本兼容窗口和 registry/Skill 更新检查任务。

## 6. 建议的补齐顺序

### M0：消除控制面“假失败/假成功”

1. 导入前完成 raw path + package validation，事务性提交 Skill/artifact/pin/projection/event；补失败零写入测试。
2. 明确并实现 manifest 合并规则，保留 version/dependency integrity/mode，严格校验文件集合。
3. 修复 artifact 去重后的关联/active pin；补删除重建和相同 digest 重导入测试。
4. UI 隐藏或降级未具备执行器的安装语义；Git/ClawHub/目录统一限额并锁定 immutable provenance。
5. 审批绑定精确 diff/digest，upgrade service 强制 lineage/runtime/ready invariants。

**M0 尚未完成。** 完成标志是失败零写入、所有 ingress 同一安全语义、控制面不承诺不存在的执行能力、审批不可伪造或复用。

### M1：打通真实 Remote 执行闭环

1. Daemon operation poller、短期 blob 下载、逐文件/root digest 校验、幂等租约和清理。
2. Runtime 专属 cache/env、精确依赖 planner/verifier、受限 runner 和证据上报。
3. complete schema 和服务端期望集合/证据验证。
4. 任务 snapshot 固定 ready installation revision，并使用 assignment digest pin；新任务 freshness fail-closed。

**M1 验收**：真实 Remote Runtime 上完成 artifact -> dependency -> script verify -> task 调用；断网、无凭据、资源超限、完整性失败、重复 operation 和中断清理测试通过。

### M2：支撑服务、版本治理和产品化

1. service catalog 准入、managed node worker、健康/协议握手、binding/readiness、升级/回滚/退役。
2. 生成真实 release lock，实现持久审批、canary、assignment revision pin 和历史重建。
3. 完成五步 UI、inspection、权限/配置、service 运维交接、迁移、feature flag 和可观测性。
