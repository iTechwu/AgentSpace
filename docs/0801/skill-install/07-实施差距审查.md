## 2. 尚未完成的上线门槛

第六轮实现补齐了大量能力，但最新 codeview 发现 **Remote 安装与 MCP 代理链仍存在可导致“组件 ready 后任务不可用”或“风险能力绕过审批”的代码缺口**。这些缺口不是仅靠环境 E2E 就能验收的，必须在代码层关闭。

### P0-1：MCP egress policy 身份模型不安全

`packages/services/src/mcp-center/egress.ts` 的 `derivePolicyRevisionId`（约 line 280）仅包含 workspace、connection、release、origin、allowedHosts 和 `approvedTools`，未纳入 endpoint path（`allowedPathPrefix`）、TLS 模式（`tlsMode`）、`redirectPolicy`、`authMode`、资源上限（`maxRequestBytes` / `maxResponseBytes` / `maxConcurrentStreams`）等安全字段。代理缓存（`apps/mcp-egress-proxy/src/policy-cache.ts`）只按 revision ID 覆盖存储，意味着同一 ID 可能对应不同权限策略。

同时 `canonicalizeMcpEgressPolicyRevision`（约 line 39）虽已纳入大部分安全字段，但存在两个缺陷：

1. `approvedTools` 只进入 `derivePolicyRevisionId` 却没有进入 canonical digest，导致 manifest digest 不能认证工具允许列表；
2. canonical payload 包含 `createdAt`，使 digest 随时间变化，无法作为稳定内容地址。

`buildMcpEgressPolicyRevision` 先构造 base revision（含占位 `manifestDigest`），再用 `digestMcpEgressPolicyRevision(base)` 回填，形式上是 two-pass，但由于 `createdAt` 在 canonical payload 中且 `approvedTools` 不在，结果仍不是纯粹由安全策略内容决定的稳定 digest。

需要：

1. 定义排除 `manifestDigest` 自身和 `createdAt`、包含全部安全字段（含 `approvedTools`）的 canonical payload；
2. 用 canonical payload 的 SHA-256 同时作为不可变的 `id` 与 `manifestDigest`（或明确分开但均由 canonical payload 派生）；
3. 在 `buildMcpEgressPolicyRevision` 中先算 canonical digest，再回填，避免自引用；
4. 复用 `packages/services/src/skills/package/package-digest.ts` 的 `stableStringify` 或类似排序逻辑，防止字段顺序漂移；
5. 更新 `egress.test.ts` 验证相同输入产生相同 revision ID、不同安全字段产生不同 revision ID。

### P0-2：MCP 代理执行链仍未闭环且租约权限过宽

`packages/services/src/mcp-center/connections.ts` 的 `claimMcpTaskSession`（约 line 1087）已签发任务租约，但使用 `toolName: "*"`，没有按实际批准的每个工具单独签发。`apps/mcp-egress-proxy/src/lease-verifier.ts` 仅校验 lease 签名、TTL、JTI replay 和 policy snapshot 存在性，不校验 `claims.toolName`；`packages/daemon/src/mcp/gateway.ts` 的 per-call 校验只对照内存中的 `approvedTools` 和 DB，不对照 lease 中的 `toolName`。因此 `toolName: "*"` 实际上未在任何下游被强制执行。

更关键的是 `packages/daemon/src/mcp/client.ts`（约 line 88）仍直接连接上游 endpoint（`StreamableHTTPClientTransport`），没有消费 policy snapshot、代理地址或租约。虽然 `packages/daemon/src/mcp/egress-client.ts` 已存在 `createMcpEgressProxyClient`，但没有任何 daemon 文件引用它。这意味着即使控制面生成了策略，容器/Provider 侧仍可直接访问原始 MCP endpoint，网络阻断和策略吊销无法生效。

需要：

1. 实现 daemon MCP proxy transport：daemon 通过 egress proxy 地址 + lease 转发 tool call，而不是直连上游；
2. 逐调用工具租约：每个 tool call 的 lease 必须绑定到具体 `toolName`，且代理端按 `approvedTools` 严格校验；
3. snapshot 同步与吊销验证：daemon 定期拉取或主动接收 policy snapshot 吊销事件，吊销后新调用立即失败；
4. 补齐 proxy transport 测试和端到端 negative 测试（无 lease、lease 过期、工具未批准、snapshot 吊销均失败）。

### P0-3：首次安装缺少高风险能力逐项审批

规格要求脚本、网络和高风险 MCP 工具独立审批。当前五步向导只检查 `unresolvedRequired`，`apps/web/features/skills/installation-actions.ts` 的 `createSkillInstallationAction`（约 line 127）没有接收或记录任何风险决定、策略版本或审批记录。管理员可直接安装带 executable / MCP / 网络声明的 Skill，服务端没有强制校验。

需要：

1. 在 installation plan 中增加不可变风险快照：声明的 executable entrypoints、依赖、MCP/CLI 能力、网络/secret 需求；
2. 向导要求管理员对每类高风险能力做逐项决定（approve/reject），并记录审批人、时间、策略版本；
3. `createSkillInstallationAction` 服务端强制校验：存在未审批的高风险能力时拒绝创建 installation，不得仅依赖前端隐藏按钮；
4. 审批记录进入 workspace audit log 和 release lock，作为后续任务调用的授权依据。

### P0-GATE-1：真实 Linux 网络与密钥负面 E2E 尚未执行

实现已不再依赖 Docker 参数“看起来正确”，但本轮工作站未运行 Linux Docker/eBPF 环境。生产放行前必须在与 managed node 相同的 Linux kernel、iptables/ip6tables backend 和 Docker 版本上证明：

1. 空 allow-list 无法访问任意 IPv4、IPv6、DNS、DoH 和默认网关。
2. 非空 allow-list 只能访问解析时固定的全部 A/AAAA + 精确端口；域名旁路、raw IP 和其他端口失败。
3. `docker inspect`、`ps`、daemon 日志和 operation evidence 均不出现 secret 明文；轮换后旧 generation 被删除。
4. daemon crash/restart 后策略状态能重建或安全清理，不留下无规则但仍运行的容器。

这是环境验收门，不是待补的应用代码。失败时必须禁止 image-based service 安装，不能降级为 DNS-only。

### P0-GATE-2：Remote 真实 Runner 与依赖消费演练尚未执行

单元测试已覆盖 Runner 容器参数、Unix socket broker、Provider stub、entrypoint/cache digest、env 发布、release-lock freshness、只读依赖挂载和缺失/篡改 fail-closed。真实 Docker 演练已固化为 `packages/daemon/scripts/dofe-skill-runner-e2e-run.sh`：强制在 Linux managed node 使用三个 digest-pinned 本地镜像，运行 Node/Python/Bash entrypoint，消费冻结 npm/Python 环境，并验证无额外网络接口、workspace 只读、Docker socket/宿主 secret 不可见及短时 config 可用。本工作站未满足 Linux 门禁，尚未产生放行证据；删除/篡改 cache/env metadata 与 snapshot 重试仍由单元/集成测试覆盖。

实测 `skills-storage.test.ts` 12 项中 3 项失败（assignment 镜像、模板 Skill 预载、自动绑定），MCP egress/connections 等套件也未被根脚本覆盖。根 `pnpm test` 可能因此通过，与 [04-执行计划与验收.md line 55](04-执行计划与验收.md:55) 的“根 `pnpm test` 通过 `turbo run test` 调度，不允许跳过真实失败”冲突。

### P1-2：依赖 ready 状态不能证明脚本可执行

`packages/daemon/src/skill-install/dependency-installer.ts`（line 79 附近）对 pip 使用 `--no-deps`，且验证仅检查文件存在性：`npm` 读 `node_modules/<name>/package.json` 版本，`pip`/`uv` 扫描 `<normalized_name>-<version>.dist-info` 目录。它既不执行 `node -e require(...)` / `python -c import ...`，也不验证 ABI、可执行入口或运行时版本兼容性。

`packages/daemon/src/skill-runner.e2e-real-docker.test.ts`（line 75 附近）为了通过 Runner E2E，手工在 envs 目录创建假模块（`dofe-runner-fixture`），完全绕过安装器。这意味着安装器本身的验证路径与 Runner 实际消费路径脱节。

需要：

1. 在冻结 env 中执行真实 `npm install` / `pip install` / `uv pip install`（pip/uv 是否保留 `--no-deps` 需与依赖解析语义一致；若保留，则必须显式处理 transitive 依赖的 lock）；
2. 安装后执行独立 smoke：Node `require`/`import`、Python `import`、检查版本/ABI；
3. 修改 `skill-runner.e2e-real-docker.test.ts` 让它经过真实安装器生成 env，而不是手工造假；
4. 为失败场景保留脱敏原因和审计证据。

### P1-3：服务型 Skill 的安装向导未闭环

`apps/web/features/skills/components/install-skill-modal.tsx`（line 171 附近）在“能力与服务”步骤只展示服务声明，没有“创建受管服务”或“绑定已有服务”的交互；确认提交时也只发送 `skillId` + `runtimeId`。后台编排存在不等于产品流程可用。

需要：

1. 对 managed_service 类型的声明，向导提供“创建新实例 / 绑定已有实例 / 跳过（仅可选）”选择；
2. 提交时携带服务选择结果，服务端校验所选服务满足 catalog 准入和配额；
3. 对 external/shared 类型保持 fail-closed，不允许通过 UI 直接创建；
4. 补充 `install-skill-modal.test.tsx` 覆盖服务选择路径。

### P1-4：目录来源缺少管理员入口

`apps/web/features/skills/components/import-skill-modal.tsx`（line 7 附近）只支持 `github`、`gitlab`、`skills.sh`、`clawhub` 和 `upload`（ZIP）。规格要求支持目录选择、目录上传或可审计的服务器端目录导入。

需要：

1. 在 import modal 增加“本地目录”来源，支持选择目录并打包上传；或提供服务器端目录路径导入（限管理员）；
2. 目录导入必须经过与 ZIP/Git 相同的 validator、digest 和来源审计；
3. 服务器端目录导入不得读取任意文件系统路径，需有白名单/审计。

### P1-5：Runner 调用审计未持久化

`packages/daemon/src/skill-runner.ts`（line 353 附近）执行脚本后仅返回结果，没有审计写入器。架构要求记录 script invocation 与 failure code，以支持安全排查和合规审计。

需要：

1. 在 `handleBrokerRequest` 中调用 `recordAuditLogSync`（`packages/db/src/audit-log.ts`）或复用 `McpAuditOutbox`（`packages/daemon/src/mcp/audit-outbox.ts`）模式；
2. 记录字段：workspace、task、installation、artifact digest、release lock digest、entrypoint key/path/runtime、调用人/会话、容器镜像 digest、argv、结果码、超时/输出超限标志、安全摘要（不记录 secret 值）；
3. 新增/补充 `skill-runner.test.ts` 验证审计写入。

### P1-6：当前服务升级是 blue-green，不是真正 canary

`upgradeManagedSkillServiceSync` 创建 blue，健康后一次性切换 green 的全部 binding。它没有百分比流量、观察窗、指标阈值、自动中止或显式一键回绑。当前产品和运维文档必须称为 **blue-green**。

若要支持真正 canary，需要引入 rollout 资源和状态机：目标 binding 集合、批次、观察窗口、成功/失败阈值、当前批次、旧/新 endpoint、暂停/恢复/回滚审计。没有这些字段前不得在 UI 宣称 canary。

### P1-7：回滚控制面预检已完成，节点本地环境由任务门禁复验

回滚现在重算 release lock，并校验 artifact/blob/root digest、prepared digest、全部组件状态和 service/MCP/CLI 当前健康；active digest 与 assignment 均有事务 CAS，失败提供结构化 preflight code。dependency env/cache 的物理文件位于 managed node，控制面不能越权读取；恢复后的首个任务仍由 daemon 的 cache/env metadata、file set 和 SHA 校验 fail-closed。显式固定到其他 revision 的灰度 assignment 目前会让整体回滚拒绝，待真正 canary rollout 模型完成后再支持按目标集合回滚，不能静默覆盖 operator pin。

### P1-8：远程大包仍以内联 base64 传输

完整性和预算已解决，但 Web 到 daemon 仍会复制完整 base64 文件及 Provider 投影。下一步应改为 content-addressed bundle：task 只传 manifest + blob URL/cache key；daemon 使用已验证 artifact cache，缺失 blob 才分块下载。需要断点续传、短期 URL、每块 digest、最终 root digest 和 cache eviction policy。

### P1-9：系统依赖仍是显式不支持

DSP 能表达 `system` dependency，但 daemon verifier 会以 `dependency_manager_unsupported` 阻断，避免假 ready。若要支持 ffmpeg、LibreOffice 等系统能力，应建立 Runtime App/catalog resolver，锁定 image/package digest 和 Runtime inventory；不得恢复为自由 `apt`/`brew` shell。

### P1-10：定时更新、迁移、GC 与可观测性未产品化

GitHub/GitLab 已提供无副作用的按需检查：只把可变 ref 解析为 SHA 并与 active artifact provenance 比较；内容去重导致共享 artifact 缺少 Git ref 时，仅对单一绑定 Skill 回退到其导入配置，多候选状态继续 fail-closed。`检查更新` 与 `获取候选版本` 是两个独立动作，无变化检查不写 artifact/binding。运维可通过 `DOFE_SKILL_SOURCE_UPDATE_CHECKS_ENABLED=false` 同时冻结检查和候选重新导入。

仍缺：

- GitHub/GitLab 的定时检查，以及 Skills.sh/ClawHub 的版本探测、通知和变更 diff 队列。
- 私有 GitHub/GitLab 的不可变 credential reference、最小权限、轮换与审计；当前禁止在 URL 或配置 JSON 保存 token。
- legacy lineage/backfill 的 dry-run、checkpoint、失败重试和覆盖率报告。
- orphan artifact/blob、Remote cache、dependency env、secret generation 和 retired service 的保留策略与 GC。
- import/inspection/prepare/cache corruption/dependency install/service provision/task gate/rollback 的指标、SLO 和告警。
- workspace 分阶段 feature flag、按 capability kind 紧急停用、批量回滚和 stale operation 管理入口。

### P1-11：外部/共享服务与 managed MCP bridge 尚未建模

`external_connection`、`platform_shared`、MCP `managed_service`/`managed_stdio` 虽保留在领域枚举中，但当前没有不可变 connection reference、shared-service inventory、租户隔离 binding，也没有 daemon 可访问且不暴露到公网的 MCP service endpoint。此前无条件走 Docker 会产生假支持，本轮已在 catalog 与 lifecycle 全层阻断。

正式支持前必须新增：按 workspace/runtime/version 固定的外部连接引用；共享实例 inventory、容量/数据域/租户隔离状态；service binding 到 MCP connection 的原子关系；managed node 私网 endpoint broker；discovery/approved-tools/health/audit 联动；停用服务后 MCP connection 与 Skill installation 同步 degraded。不得把任意 URL、stdio command 或空 endpointRef 写入 binding 代替这些模型。

### P1-12：Runner 短时配置已闭环，网络 allowlist 仍待节点级 egress broker

entrypoint `configKeys` 已从 DSP manifest 进入任务 snapshot；daemon 将声明键从 Provider 环境中剥离，只把它们挂载为随机短时只读 JSON，缺键 fail-closed，值不进入 Provider 环境、Docker argv 或工作目录，调用后清理。Runner 仍固定 `--network none`。要支持合法联网脚本，必须先提供 managed-node egress broker/网络策略，按 installation + entrypoint + host/port 审批和审计，并证明容器不能绕过代理直连；在此之前不得改为普通 Docker bridge 或仅依赖 `HTTP_PROXY` 环境变量。

### P2：产品体验继续完善

五步安装与证据面板、Git 更新检查、候选获取、按 Runtime 准备升级和 ready 后发布入口已经可用。候选导入不再提前覆盖当前元数据/文本投影，发布事务同步切换 digest、assignment 与兼容投影。面板已展示变更数量和 breaking 标识，但仍缺独立职责分离的升级审批收件箱、逐项 semantic diff UI、service 专属运维页、服务器端草稿恢复和诊断包下载。可用性指标（完成率、耗时、状态理解率、误授权率）尚未通过真实管理员研究验证。
