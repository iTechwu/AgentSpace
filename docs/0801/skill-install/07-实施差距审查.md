# Skill 安装实施差距审查

> 审查日期：2026-08-02  
> 审查范围：`docs/0801/skill-install` 产品、架构、UIUX、运维与实施计划，以及当前 domain / db / services / daemon / web 实现与测试。  
> 结论：**尚不具备“任何受支持形态的 Skill 在 Remote 模式下直接安装并使用”的上线条件。**

## 1. 总体判定

当前实现已经建立不可变 artifact/blob、installation/component/operation 表、部分 MCP/CLI resolver、release diff/rollback 函数，以及 Runtime 选择和安装状态 UI。这些是有价值的控制面骨架，但关键数据面尚未闭环：

1. 导入主路径没有使用统一 package validator，DSP manifest 中的 capability/service/entrypoint 声明会被丢弃。
2. Web 已能创建 Remote installation operation，但 Daemon 没有 skill operation client/worker/runner，operation 不会被真正执行。
3. 任务路径仍按 assignment + active artifact 投影 Skill，未校验对应 Runtime installation 是否 `ready`；artifact 完整性失败时还会退回旧文本投影。
4. 支撑服务只有表和 DB CRUD，无准入服务、managed node worker、健康握手、binding readiness 与运维 API。

因此，当前应标记为 **开发中 / 不可用于真实 Remote Skill 执行**，不应对用户展示“Daemon 将准备环境”或“回滚成功”之类无数据面保证的成功语义。

## 2. 阻断上线的问题

### P0-1：DSP 声明在导入时被绕过或丢失 ✅ 已修复

- 导入主路径现在先调用 `validateSkillPackage`，再使用其返回的 manifest 构建 artifact。见 [import.ts](../../../packages/services/src/skills/import.ts:326) 与 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts:51)。
- validator 在提交 manifest 通过 schema 校验后，会保留其 `capabilities`、`services`、`entrypoints` 并仅覆盖 files/digest/size/mode。见 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts:230)。
- `.dofe/manifest.json` JSON 解析失败、声明文件缺失、symlink 和包限额超限现在都会 fail closed。见 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts:218) 与 [archive-limits.ts](../../../packages/services/src/skills/package/archive-limits.ts:7)。

新增回归测试覆盖：manifest 保留高级声明、坏 manifest JSON、缺失声明文件、undeclared symlink。

### P0-2：Remote installation 只有 API，没有执行面

- 路由可以 claim/start/complete/fail operation，但 [daemon-client.ts](../../../packages/daemon/src/daemon-client.ts:142) 只有 task/runtime app/MCP operation 方法，没有 Skill operation 方法。
- 计划要求的 `packages/daemon/src/skill-install/{artifact-materializer,operation-worker,runner-client}.ts` 尚不存在。
- claim 响应只下发文件元数据，没有可供 Daemon 按 digest 下载 blob 的鉴权 URL/blob API。见 [installations.ts](../../../packages/services/src/skills/installations.ts:153)。

**影响**：安装操作会长期停在 `pending`；依赖、脚本、只读 cache、断网/无凭据 runner 都不会发生。

**必须修复**：先完成 Daemon client + worker + artifact 下载协议，再开放 UI 安装入口；依赖计划必须是参数数组、精确版本/integrity 和 allow-listed registry，不接受包内自由 shell。

### P0-3：任务启动未使用 installation readiness，完整性检查还是 fail open

- `assertSkillInstallationReadyForTaskSync` 只在测试中被调用，运行路径无引用。见 [installations.ts](../../../packages/services/src/skills/installations.ts:319)。
- Daemon 仍按 `agent_skill` 赋值选取 Skill，没有绑定 runtime + artifact revision。见 [task-context.ts](../../../packages/daemon/src/task-context.ts:1102)。
- artifact blob 丢失或 digest 校验失败时，投影代码捕获异常并退回旧 `skill_file` 文本，这与“完整性优先，禁止静默降级”直接冲突。见 [injection.ts](../../../packages/services/src/skills/injection.ts:88)。

**必须修复**：任务快照固定 `installationId + artifactDigest + revision`；在构建 input bundle 前验证该 Runtime 上的 installation 仍为 `ready`；完整性失败时阻断该 Skill 并将 installation 置为 `degraded`，不得回退到可能过期或不完整的文本副本。

### P0-4：脚本内容变更被误判为非 breaking，且升级未强制批准 ✅ 已修复

- `diffSkillArtifactsSync` 现在把已有 `0755` 脚本的 sha256 变更从 `content` 重分类到 `execution`，并标记 `breaking=true`。capability `kind` 变更、service `required` 标志变更也被识别。见 [release.ts](../../../packages/services/src/skills/release.ts:106)。
- `createSkillUpgradeAction` 新增 `approved?: boolean` 入参；当 `diff.breaking=true` 且未显式批准时直接抛出错误，不会创建 prepare operation。见 [installation-actions.ts](../../../apps/web/features/skills/installation-actions.ts:112)。

新增回归测试：修改现有 `0755` 脚本内容 → `execution` + `breaking=true`。

### P0-5：回滚 action 会返回成功，但不会切换活动 artifact ✅ 已修复

- Web rollback action 现在通过 installation 的 artifact 反查 `skillId` 并传入 `rollbackSkillInstallationSync`。见 [installation-actions.ts](../../../apps/web/features/skills/installation-actions.ts:162)。
- `rollbackSkillInstallationSync` 已在 `withTransaction` 中统一完成：取消当前 installation 的未完成 operation、将其置为 `degraded`/`rolled_back`、把 skill 的 active artifact digest 切回前一个 ready digest、并把该 skill 下所有 `agent_skill` 的 `skill_artifact_digest` 同步切回。见 [release.ts](../../../packages/services/src/skills/release.ts:346) 与 [skill-artifacts.ts](../../../packages/db/src/skill-artifacts.ts:235)。

安装测试已增加断言：rollback 后 `readActiveArtifactDigestForSkillSync` 返回旧 digest。

## 3. 高优先级完整性与安全差距

### P1-1：非受信归档可绕过统一限额 ✅ 已部分修复

- `import.ts` 现在从 `archive-limits.ts` 导入统一的限额常量，ZIP 入口校验文件数、总解压字节和嵌套深度。见 [import.ts](../../../packages/services/src/skills/import.ts:100) 与 [readSkillZipFiles](../../../packages/services/src/skills/import.ts:755)。
- 本地目录导入现在拒绝 symlink。见 [readLocalSkillDirectoryFiles](../../../packages/services/src/skills/import.ts:701)。
- validator 输入模型已增加 `symlinkTarget`，提交含 symlink 的包会被 `UNDECLARED_SYMLINK` 拒绝。见 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts:66)。

**仍留缺口**：ClawHub 下载路径仍直接 `unzipSync` 后遍历，未在解压前应用统一的 archive bytes/files/uncompressed/nesting 限额；Git 来源也未纳入统一限额。需与 Git SHA 锁定一并补齐。

### P1-2：Git/registry 没有锁定不可变来源

GitHub 导入将 URL 中的 branch/tag 直接作为 `ref`，Skills.sh 使用默认分支，没有调用 commit API 解析 SHA，provenance 也没有 `resolvedRef/originalUrl`。见 [import.ts](../../../packages/services/src/skills/import.ts:490) 和 [import.ts](../../../packages/services/src/skills/import.ts:552)。

必须在读文件前锁定 commit SHA，且同一次导入的所有 Contents API 请求都使用该 SHA；版本发现保留可变 URL，安装和审计只使用 SHA/digest。

### P1-3：installation complete 缺少证据与服务端约束

complete route 直接采信 Daemon 提交的 `componentStatuses`，控制面没有校验每个状态是否属于该 operation 期望组件，也没有校验 artifact digest、prepared path 抽象标识、verify evidence 或必要组件全量覆盖。见 [complete route](../../../apps/web/app/api/daemon/skill-operations/%5BoperationId%5D/complete/route.ts:26) 和 [installations.ts](../../../packages/services/src/skills/installations.ts:193)。

应对 request schema 严格校验，拒绝未知/重复组件，要求 artifact integrity 和 runner policy 证据，并由控制面根据期望组件重算状态。

### P1-4：支撑服务尚停留在数据表阶段

[skill-services.ts](../../../packages/db/src/skill-services.ts:53) 可以写 catalog/instance/binding，但缺少：

- `packages/services/src/skill-services/{catalog,bindings}.ts` 准入与生命周期服务；
- image digest/SBOM/非 root/只读 rootfs/cap drop/无 socket/网络/集中外部依赖策略验证；
- managed node 创建、健康、升级、蓝绿/金丝雀、退役 worker；
- service component 纳入 installation readiness。当前 [installations.ts](../../../packages/services/src/skills/installations.ts:95) 甚至不会为 manifest services 生成 component。

该差距使“Skill 需要现创支撑服务时可直接安装”完全未实现。不得用 Web/Runtime 直接起容器补位，也不得在部署中新建 PostgreSQL、Redis 或 RabbitMQ。

### P1-5：release lock 不可重现

- 初始 installation 写入的 lock 除 digest/schema 外全是空值，升级 installation 直接写入 `{}`。见 [installations.ts](../../../packages/services/src/skills/installations.ts:136) 和 [release.ts](../../../packages/services/src/skills/release.ts:309)。
- `computeSkillReleaseLockSync` 没有被生产路径调用，且 service image/config schema、MCP tool fingerprint 和 provider compatibility revision 仍是占位值。见 [release.ts](../../../packages/services/src/skills/release.ts:31)。
- 尚无 canary assignment、任务快照 revision pin、服务 rollback class 执行和历史重建验证。

## 4. 产品、UIUX 与运维未完成项

### 产品/UIUX

已有的 `InstallSkillModal` 是单步 Runtime 选择器，`SkillInstallationPanel` 能展示组件与 operation 列表，但与 [03-UIUX设计方案](./03-UIUX设计方案.md) 仍有以下差距：

- 无“来源 -> 包检查 -> Runtime -> 配置/授权 -> 确认/进度”五步向导，无 `aria-current=step`、草稿/恢复和安装 timeline。
- 无 inspection 服务及 `package-actions.ts`，不能在安装前展示文件、脚本、assets、依赖、license、风险、MCP/CLI/service 需求。
- 无 `service-actions.ts`、service 详情/健康/运维交接界面。
- 无 Library / Runtime installations / imports 信息架构和完整详情 tabs；列表尚未系统呈现 digest、risk、聚合状态和分配数。
- 无 breaking diff 审批界面和可验证审批流；现有 action 只在创建升级后返回“需重新批准”文案。
- 新增安装组件没有专项 UI 测试；现有 Skill 页测试出现 `act(...)` 告警。

在 P0-2/P0-3 完成前，UI 应以 feature flag 隐藏“安装到 Runtime”命令，或明确标记为“仅创建计划，尚无执行器”。

### 运维/迁移/可观测性

- 已有 `buildLegacyArtifactFromSkillSync` 辅助函数和 `legacy_incomplete` 健康检查，但无可重入的后台 backfill job、进度/失败报告、assignment 映射与干跑演练。
- 无 workspace feature flag 实现，无 inspection-only -> assets -> dependencies -> scripts/MCP 逐级放量和回退。
- 无 import/prepare 成功率、ready 时间、runner 拒绝率、任务门禁失败、capability 健康和 rollback 指标/告警。
- 无安全冻结 capability kind、停止新 installation、批量回滚 assignment 的运维开关与 runbook 自动化。
- 无 Remote Runtime 的 runner 无凭据/无网络/无 socket/资源超限/清理集成证据，无支撑服务蓝绿、回滚、退役演练证据。

## 6. 建议的补齐顺序

### M0：先消除“假成功” ✅ 已完成

1. ✅ 将所有来源接入同一 validator，保留 DSP 高级声明，严格拒绝坏 manifest、未声明文件、缺失文件、symlink 和超限包。
2. ✅ 修复脚本 diff、审批门禁和回滚 active/assignment pin 事务。
3. ⏳ 在 Daemon worker 上线前隐藏安装命令；禁止 integrity 失败回退旧文本投影（任务门禁待 M1，当前 injection 对 pinned artifact 已是 fail-closed）。
4. ⏳ 锁定 Git commit SHA，统一 ZIP/ClawHub/Runtime artifact 限额和 provenance（ZIP/目录限额已统一，Git/ClawHub 待 M1）。

**M0 验收**：P0-1/P0-4/P0-5 复现用例已转为回归测试；包存在高级声明时 artifact manifest 字节级保留语义；symlink 与坏 manifest 有负面测试。

### M1：打通真实 Remote 执行闭环

1. 增加 Daemon Skill operation client/poller，通过短期鉴权 blob URL 下载并校验 artifact。
2. 完成 Runtime 专属 cache/env、精确依赖 planner/verifier 和隔离 runner；不写 Provider HOME/全局 PATH，不挂 Docker socket。
3. complete protocol 上报安全摘要证据，控制面校验后重算 readiness。
4. 任务快照固定 ready installation revision，状态降级后新任务 fail closed。

**M1 验收**：真实 Remote Runtime 上完成 artifact -> dependency -> script verify -> task 调用；断网、无凭据、资源超限、完整性失败和清理测试全绿。

### M2：接入 MCP/CLI/支撑服务与版本治理

1. 从完整 manifest 生成 MCP/CLI/service components，只注入 ready + approved 能力。
2. 完成 service catalog 准入、managed node worker、健康/协议握手、binding 与降级传导。
3. 生成真实 release lock，实现 approval/canary/assignment revision pin/服务 rollback class。
4. 完成五步 UI、迁移、feature flag、可观测性和运维演练。
