# Skill 安装实施差距第二次复审

> 复审日期：2026-08-02
>
> 审查范围：`docs/0801/skill-install`、当前未提交实现，以及 domain / db / services / daemon / web 的真实调用链和定向测试。
>
> 结论：**Remote artifact 准备、operation 完成协议、任务版本快照已经形成真实闭环，但系统仍可能把“未安装的依赖/未创建的服务”判定为 ready，且缓存与任务投影存在完整性缺口。当前仍不满足“任意受支持 Skill 可在 Remote 模式直接安装并使用”的上线标准。**

## 1. 相比上轮已经真实完成的内容

以下能力已有生产调用链和负面测试，不再列为缺失：

1. **导入失败不再修改 Skill。** `prepareSkillArtifact` 先验证并持久化不可变 artifact，随后才在事务中创建或替换 Skill、文本投影、active digest 和 import event。新建/替换坏包均有零 Skill 状态变更测试。见 [import.ts](../../../packages/services/src/skills/import.ts#L206)。
2. **GitHub 与 Skills.sh 先解析 commit SHA。** 同次递归读取固定使用 resolved SHA，provenance 保存 `resolvedRef` 和原始 URL。
3. **Remote Daemon worker 已投入真实轮询。** `remote-daemon` 会 claim operation 并调用 materializer、component verifier、operation worker；不再是 fail-fast 骨架。见 [remote-daemon.ts](../../../packages/daemon/src/remote-daemon.ts#L720)。
4. **complete/fail 协议已 fail-closed。** 共享 payload parser、冻结组件集合、重复/未知/缺失组件拒绝、artifact digest evidence 验证，以及 operation/component/readiness 原子提交均已实现。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L309)。
5. **任务 readiness 与版本快照已接入。** 任务按 Runtime 和 assignment digest 解析最高 revision，持久化 `installationId + artifactDigest + revision`，重试复用快照，并在执行前重新检查状态。见 [installations.ts](../../../packages/services/src/skills/installations.ts#L585) 与 [task-context.ts](../../../packages/daemon/src/task-context.ts#L489)。
6. **Release lock 已接入安装生产路径。** 当前未提交实现让初始安装和升级统一调用 `computeSkillReleaseLockSync`，生成 `lockDigest`，并把 digest 放入 claim payload；service/MCP 字段、稳定 digest、安装/升级落库和 claim 都已有定向测试。该项已从“未接入”推进为“核心生成链完成、执行消费链未闭环”。

这些进展解决了上轮“只有控制面、没有执行面”和“任务固定查询 v1”的主要问题。当前风险已转移到执行真实性、缓存可信度、artifact lineage 和恢复能力。

## 2. 上线阻断项

### P0-1：Runtime cache 可被同尺寸内容篡改后继续命中

[operation-worker.ts](../../../packages/daemon/src/skill-install/operation-worker.ts#L59) 的 cache hit 只检查 sentinel、普通文件和文件大小；[verifyCachedFiles](../../../packages/daemon/src/skill-install/operation-worker.ts#L176) 不重算逐文件 SHA256，也不根据当前 operation manifest 重算 root digest。随后 [readCachedMaterializeResult](../../../packages/daemon/src/skill-install/operation-worker.ts#L128) 直接信任 cache meta 中记录的 computed/expected digest。

因此，缓存文件被替换为同尺寸内容时仍会命中，旧 meta 会继续声称 root digest 正确。脚本 verifier 只做存在性、执行位和语法检查，合法语法的恶意替换可以进入 complete evidence。

必须完成：

- cache hit 时以 operation 冻结 manifest 为权威，校验路径集合、文件数、mode、size、每文件 SHA256 和 root digest；meta 只能作为索引，不能作为证据。
- 拒绝额外文件、symlink/hardlink 和越界路径；发布后将 cache 目录与文件设为只读，写入新 digest 使用新目录。
- 增加“同尺寸篡改”“meta 篡改”“额外文件”“并发 publish”负面测试。

### P0-2：依赖与服务存在“假 ready”

[component-verifier.ts](../../../packages/daemon/src/skill-install/component-verifier.ts#L97) 对依赖的验证仅确认 manifest 中存在非空 version，然后直接返回 ready；它没有在 Runtime 专属环境安装包，也没有验证包版本、lock/integrity、ABI、入口命令或 import 能力。

服务问题更严重：

- verifier 对 service 明确返回 `service_not_implemented`；
- 但 [buildInstallationComponents](../../../packages/services/src/skills/installations.ts#L116) 的 manifest 类型和生成逻辑根本不读取 `manifest.services`，所以需要服务的 Skill 不会产生 service component，也就不会被上述 blocker 阻止；
- 当前 release-lock 实现中，catalog 查不到时选择留空，也不会阻止 installation ready。

这意味着一个带 npm/Python 依赖或 required service 的 Skill 可以在真实依赖/服务不存在时进入 ready。

必须完成：

- 设计 Runtime 隔离环境，例如 digest/lock 级 venv、node_modules 或受管 toolchain；解析、下载、安装、验证必须使用精确版本和完整性锁。
- 把 `manifest.services` 全量转为 service component；required catalog/template 无法解析必须在创建计划时失败或保持 blocked。
- Daemon 只上报本地执行证据；控制面基于 lock 和 catalog 再验证，服务必须绑定健康 instance 后才 ready。
- 增加依赖缺失、版本错误、离线缓存、安装失败和 required service 不存在的端到端测试。

### P0-3：导入 artifact 未绑定 Skill，安装历史与回滚断链

原子导入先在 Skill 创建前调用 `prepareSkillArtifact`，而 [prepareSkillArtifact](../../../packages/services/src/skills/import.ts#L359) 持久化 artifact 时没有传 `skillId`。后续事务只设置 `skill.active_artifact_digest`，没有把 artifact 关联回新 Skill。

当前 `skill_artifact.skill_id` 仍可能为 `NULL`；[listSkillArtifactsForSkillSync](../../../packages/db/src/skill-artifacts.ts#L163) 只按该列查询。因此：

- 导入 Skill 的安装历史面板可能为空；
- [rollbackSkillInstallationAction](../../../apps/web/features/skills/installation-actions.ts#L167) 从 `artifact.skillId` 推导目标 Skill，可能报“Cannot determine skill id”；
- 相同 digest 被多个 Skill 使用时，单个可空 `skill_id` 也无法表达多对多 lineage。

必须完成：

- 短期至少在创建/替换事务中显式 attach artifact，并补 import 后 list/history/rollback 测试。
- 正式模型应新增 `skill_artifact_binding` 或 release lineage 表，以 `(workspaceId, skillId, artifactDigest, revision)` 表达不可变引用；安装与回滚显式携带 skillId，不再反向猜测。
- 为 artifact 已写入但 Skill 事务失败的情况增加可观测 orphan GC，不删除仍被 installation、task snapshot 或 assignment 引用的对象。

### P0-4：entrypoint 与 0755 文件会生成重复 component

[buildInstallationComponents](../../../packages/services/src/skills/installations.ts#L116) 先把每个 entrypoint path 加为 script，再把所有 mode 为 `0755` 的文件加为 script，没有去重。数据库对 `(installation_id, kind, key)` 有唯一约束，见 [postgres-schema.ts](../../../packages/db/src/postgres-schema.ts#L2591)。

正常的可执行 entrypoint 通常正是 0755，因此创建 installation 时会触发唯一键错误。现有 installation 测试没有覆盖 entrypoint。

必须按 `kind:key` 稳定去重，并验证同一路径的声明一致；补 entrypoint + 0755、重复 capability、重复 dependency 三类测试。

### P0-5：安装阶段保留的可执行位在真实任务 bundle 中丢失

安装 materializer 会写入 manifest mode，cache copy 也会保留执行位；但任务输入 bundle 只传 `{path, contentBase64}`。见 [input-bundle route](../../../apps/web/app/api/daemon/tasks/%5BtaskId%5D/input-bundle/route.ts#L319)。Daemon [materializeInputBundle](../../../packages/daemon/src/bundle.ts#L13) 使用普通 `writeFileSync`，没有 chmod。

结果是安装验证通过的 `0755` 脚本在 Remote task workDir 中通常变成 `0644`，直接执行 `./script` 会失败。当前任务也没有复用 installation prepared cache，而是在 Web 端再次 materialize、base64 编码并复制到 provider 目录，安装证据与实际执行字节不是同一来源。

必须完成：

- bundle file 增加 canonical mode 和 sha256，Daemon 校验 digest 后写入并应用 mode；或让任务从已验证的 Runtime cache 只读投影。
- snapshot 应绑定 releaseLockDigest/preparedDigest，任务开始时验证 cache 和 installation evidence 一致。
- 增加真实 Remote 端到端测试：安装一个 0755 脚本，在任务中直接执行并验证内容 digest。
- 为多 Skill bundle 增加聚合文件数/字节上限、去重和分块下载，避免多份 provider 投影造成无界内存与响应体。

### P0-6：operation 无租约、心跳和崩溃恢复

[claimNextSkillInstallationOperationForRuntimeSync](../../../packages/db/src/skill-installations.ts#L444) 只把 pending 改成 claimed 并记录 `claimed_at`。表和 worker 没有 lease token、`lease_expires_at`、heartbeat、attempt、retry/backoff 或 stale requeue。

Daemon 在 claim/start 后崩溃，operation 会永久停留在 claimed/running；后续 worker 无法接管，installation 也不会形成结论。

必须复用项目其他 Runtime operation 已有的租约模式：claim 生成 fencing token，周期续租，complete/fail 校验 token；过期后按 attempt/backoff 重排，超过上限进入明确失败，并清理 staging/workDir。需要覆盖 claim 后崩溃、running 中断、旧 worker 迟到 complete、重复交付和清理失败。

## 3. 高优先级完整性与治理差距

### P1-1：下载协议仍有 SSRF、内存和部署拓扑风险

[artifact-materializer.ts](../../../packages/daemon/src/skill-install/artifact-materializer.ts#L145) 对 control-plane 返回的 URL 直接 `fetch`，允许默认 redirect，没有协议/域名/IP allowlist。Content-Length 检查使用 `max(expectedSize * 2, 64MB)`，小文件也允许先接收至 64MB；无 Content-Length 时 `arrayBuffer()` 会无界读入内存，之后才由 size/digest 校验失败。

另外 local attachment provider 的 `createReadUrl` 固定返回 null，见 [storage.ts](../../../packages/services/src/attachments/storage.ts#L477)。Daemon 只能从自己的 `local:///` root 读取；控制面和 Remote Runtime 不共享同一文件系统时必然失败。

必须只接受短期 HTTPS 签名 URL 或鉴权 blob proxy，锁定允许的 storage origin，禁用或逐跳校验 redirect，并流式读取到严格上限。使用 local provider 时应在安装前验证共享存储契约，否则明确拒绝 Remote install。

### P1-2：package contract 仍会丢失提交语义

统一 validator 已能保留 capabilities/services/entrypoints，并拒绝坏 JSON、缺失的声明文件和显式 symlink；但仍有以下缺口：

1. 只验证“声明的文件存在”，不拒绝包内未声明文件；当前测试明确允许 submitted manifest 漏报 asset。见 [package-validator.test.ts](../../../packages/services/src/skills/package/package-validator.test.ts#L125)。
2. submitted `artifact.version` 被 SKILL.md frontmatter 覆盖，测试断言 `1.0.0` 变为空字符串；submitted dependency integrity 也没有按权威规则保留。见 [package-validator.ts](../../../packages/services/src/skills/package/package-validator.ts#L264)。
3. import 传给 validator/artifact 的文件不含 mode，无扩展名 executable 的 `0755` 会丢失。
4. ZIP 在严格审计前先 normalize path，原始 `../evil.sh` 可能被改写成普通相对路径，丢失攻击证据。
5. Git/Skills.sh 递归读取和本地目录仍没有统一的总文件、总字节、深度、请求数限制；ZIP 使用 fflate 全量解压，统计前可能已产生内存压力。

必须定义 submitted/computed 字段权威矩阵，先审 raw path，再归一化；校验 declared 和 actual path 集合完全一致；所有 ingress 携带 mode 并使用同一 streaming budget。

### P1-3：Release lock 已可重现生成，但尚未成为执行约束

当前未提交实现已经：

- 在初始安装和升级中调用 `computeSkillReleaseLockSync`；
- 解析 service catalog image/config schema 与 MCP declared tools fingerprint；
- 生成 `lockDigest` 并放入 claim payload；
- 新增 [10-release-lock计划.md](./10-release-lock计划.md)。

已经完成的测试包括 service/MCP 字段填充、digest 稳定性、provenance 无关、安装/升级落库和 claim payload。仍未完成：

- catalog 缺失或 declaredTools JSON 无效时静默留空，lock 仍可生成；这不是“完整 resolved lock”。应记录 unresolved 项并阻止 required component ready。
- `providerCompatibilityRevision` 仍固定为 0；Daemon 只接收 lock digest，不验证 lock 内容。
- task snapshot、approval、rollback 和审计尚未绑定同一个 lock digest；catalog 改变后的旧 revision 重建能力未验证。
- 当前 `JSON.stringify(lock)` 依赖对象构造顺序；存储层应明确保存 canonical JSON 与独立 lock digest/schema version。

该项只有在 unresolved required 项 fail-closed、Daemon/task/approval/rollback 消费同一 lock，并完成至少一次“来源消失后由 artifact/blob/lock 重建旧 revision”的演练后才能关闭。

### P1-4：升级审批与 lineage invariant 仍可绕过

Web action 的 `approved?: boolean` 是一次请求布尔值，不是不可变审批记录；没有批准人、原因、权限、时间，也没有绑定 `fromDigest + toDigest + diffHash + policyVersion`，存在复用和 TOCTOU。

[createSkillUpgradePlanSync](../../../packages/services/src/skills/release.ts#L400) 仍没有强制 previous installation 为 ready、与目标 Runtime 相同、与目标 artifact 属于同一 Skill lineage。调用者可把不相关 installation 当 previous 生成新 revision。

必须新增 approval 实体并在事务内一次性消费；service 层独立校验 workspace/runtime/skill lineage/previous ready/current active digest，并用 optimistic concurrency 或 compare-and-set 防止并发升级、回滚交错。

### P1-5：支撑服务只有 catalog/instance/binding 数据表

生产代码中除 release-lock 查询外，没有 services/daemon/web 对 `skill_service` 的生命周期调用。尚缺 catalog 准入、签名/SBOM、managed node 创建、健康和协议握手、secret/network policy、升级/蓝绿/回滚/退役，以及 service readiness 向 installation/task 的传播。

第三方 Skill 只能引用审核 catalog，不能自行启动 Compose、Docker socket 或后台进程。应用部署继续只连接 `../docker-helm.dofe.ai` 管理的 PostgreSQL、Redis、RabbitMQ，不得创建这些基础设施容器。

### P1-6：回滚仍缺健康预检、并发控制和可重现验证

基础事务会取消未完成 operation、切换 active digest 和 assignment pin，这是有效进展。但回滚没有验证目标 artifact/blob 完整性、Runtime cache、release lock、依赖和 service compatibility；也没有执行 service rollback class。artifact 单 FK 导致的 skillId 断链会直接阻止导入 Skill 回滚。

回滚请求应显式固定 skillId、current installation、expected revision/lock；事务内 compare-and-set，Runtime 预检通过后再激活，并为失败自动恢复原 revision。

## 4. 产品、UIUX、迁移与运维差距

### 产品与 UIUX

- `InstallSkillModal` 仍是单步 Runtime 单选器，且文案会让用户认为依赖和服务都会被准备；缺来源检查、风险/文件审阅、配置授权、确认和进度恢复。
- 没有 artifact inspection 页面/API 的生产实现，用户无法在执行前审阅脚本、依赖、license、MCP/CLI/service 权限和网络风险。
- 没有持久化 breaking diff 审批 UI、service 生命周期/健康/责任人界面、失败重试/换 Runtime/查看 evidence 的恢复动作。
- 安装历史依赖 artifact.skillId，当前对导入 Skill 可能为空；modal、panel、actions 没有专项交互、可访问性或错误恢复测试。

在 P0-2 关闭前，UI 不能把 installation ready 解释为“全部依赖与服务可用”；应显示按 component kind 的真实验证级别。

### 迁移、可观测性与运维

- 无 legacy Skill -> artifact/lineage 的可重入 backfill、checkpoint、dry-run、失败报告和回滚演练。
- 无 workspace 级 `inspection-only -> assets -> dependencies -> scripts/MCP -> service` 渐进开关。
- 无 import/prepare 成功率、ready 延迟、cache integrity miss、runner 拒绝、任务 gate 失败、stale operation、service 健康和 rollback 指标/告警。
- 无冻结 capability kind、停止新 installation、批量回滚 assignment、清理 cache/orphan artifact 的运维开关和 runbook。
- 无 artifact/manifest/lock schema 版本迁移策略、兼容窗口、registry 更新检查、候选版本通知和自动/手动升级策略。

## 6. 建议实施顺序

### M0：先消除假 ready、完整性绕过和直接运行失败

1. cache hit 重算文件 SHA/root digest，并增加同尺寸篡改测试。
2. dependency 未真实安装验证不得 ready；services 必须生成 component，required service 未绑定健康实例不得 ready。
3. 修复 artifact-Skill lineage，恢复安装历史和回滚；增加 orphan GC。
4. component 按 `kind:key` 去重，覆盖 entrypoint + 0755。
5. task bundle 保留 mode/SHA，或直接使用 Runtime verified cache。
6. operation 加 lease/fencing/heartbeat/retry/cleanup。

**M0 验收：** 在独立 Remote Runtime 安装并直接调用带 executable、npm/Python 依赖和 required service 的样例；缓存篡改、Daemon 崩溃、依赖缺失、服务不健康均 fail-closed，且可重试恢复。

### M1：统一供应链契约和下载安全

1. 完成 manifest 权威矩阵、raw path、mode、全量 path 集合和全入口 streaming budget。
2. 使用受限签名 blob 协议，解决 SSRF、无界下载和 local-provider 拓扑问题。
3. 将安装 cache、task snapshot、preparedDigest 和 releaseLockDigest 绑定为同一执行证据链。
4. 完成 release-lock 计划中的测试和历史重建演练。

### M2：完成版本治理、服务和产品化

1. 持久审批、upgrade invariant、并发控制、canary、健康预检与服务回滚。
2. service catalog 准入、managed node worker、健康/协议握手和运维交接。
3. 五步 UI、inspection、权限配置、错误恢复、迁移、feature flag、指标告警与更新检查。
