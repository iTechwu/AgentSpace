# M2 版本治理后端核心：审批 + rollout_pin + catalog 准入

## 背景（为什么做）

用户要求实施剩余全部项目。经评估，剩余工作横跨后端版本治理、基础设施（managed node）、前端（Phase 5）、可观测性（Phase 6），无法在一次计划内全部高质量完成。**本计划实现可测试、价值最高的后端治理核心**（P1-3/P1-4 审批、rollout_pin/canary、P1-5 catalog 准入校验）；managed-node worker、Phase 5 UI、Phase 6 可观测性作为后续独立计划明确列出。

现状（已核实，三个 Explore agent 报告）：
- **审批（P1-3/P1-4）**：`createSkillUpgradeAction`（`apps/web/features/skills/installation-actions.ts:96-165`）是唯一生产调用方，`approved?: boolean` 一次性布尔（`:100,:131`），无审批记录（批准人/理由/时间/权限/绑定 digest/diffHash/policyVersion）。`diffSkillArtifactsSync` 只在 web action 计算（`:122`），`isSkillUpgradeApprovalRequiredSync` 零生产调用。`createSkillUpgradePlanSync`（`release.ts:400-444`）只查 previous 存在 + artifact 存在，**不强制** previous-ready / 同 runtime / 同 skill lineage。无升级 API 路由、无审批 UI（`createSkillUpgradeAction` 在 UI 中是死代码）。
- **rollout_pin/canary**：`agent_skill` 无 `rollout_pin` 列；任务快照（`resolveTaskSkillExecutionSnapshotSync`，installations.ts:663）用 assignment `skill_artifact_digest` → 最高 revision ready 安装。无 canary 概念。
- **catalog 准入（P1-5）**：`upsertSkillServiceCatalogSync`（`db/skill-services.ts:53-98`）零校验盲写；无 SBOM/镜像格式/网络/安全校验；`external_dependencies_json` 无解析；CLAUDE.md 的"不新建 PG/Redis/RabbitMQ"只有文档规则无代码校验。`managed_skill_service` 缺 upgrade/retire/delete；无 daemon 容器编排代码（需复用的 claim 模式在 `runtime-provisioning` + `managed-runtime-provisioning.ts:54-126`）。

## 目标（本计划）

1. **持久化不可变审批记录** + 把 `diffSkillArtifactsSync` 接进真实审批门；`createSkillUpgradePlanSync` 强制升级不变量（previous-ready/同 runtime/同 lineage）。
2. **rollout_pin / canary**：`agent_skill.rollout_pin` 固定 assignment 到指定 revision；任务快照 honor pin；rollout 切换（pin 更新）让新任务用新 revision。
3. **catalog 准入校验**：`upsertSkillServiceCatalogSync` 校验镜像 digest 格式、rollback_class、外部依赖仅集中托管（拒绝模板内嵌 PG/Redis/RabbitMQ 创建）、network JSON 合法、部署类型合法。

## 本轮不做（明确后续计划）

- **Managed-node worker**（容器生命周期）：需复用 runtime-provisioning claim 模式 + Docker 集成，重。
- **Phase 5 UI**（五步向导、inspection、审批界面、升级触发）：`createSkillUpgradeAction` 目前 UI 死代码，需前端工作。
- **Phase 6 可观测性**（指标/告警/feature flag/backfill）。

## 关键决策（已定）

- **审批表**：新表 `skill_upgrade_approval`（不可变）：`id, workspace_id, skill_id, from_digest, to_digest, diff_hash, policy_version, decision, reason, actor_user_id, created_at, consumed_at`，`UNIQUE(workspace_id, from_digest, to_digest, diff_hash)`。`diff_hash = sha256(stableStringify(diff))`（复用 `stableStringify`，`package/package-digest.ts:71`）。
- **审批门**：`createSkillUpgradePlanSync` 增可选 `approvalId`；diff breaking 时必须有未消费的匹配 `(from_digest, to_digest, diff_hash)` 审批，事务内 `consumed_at` 消费；不 breaking 不需要。web action 调 `approveSkillUpgradeSync` 生成记录再传 `approvalId`。
- **升级不变量**：previous 必须 `status === "ready"` + `previous.runtimeId === input.runtimeId` + `readSkillArtifactByDigestSync(fromDigest).skillId === readSkillArtifactByDigestSync(toDigest).skillId`（同 lineage）。
- **rollout_pin**：`agent_skill.rollout_pin TEXT`（revision 字符串，nullable）；assignment 写入时记录当前 revision；`setSkillRolloutPinSync` 批量切换（canary 开关）；任务快照 honor pin（有 pin → 解析该 revision 的 ready 安装，无 pin → 最高 revision）。
- **catalog 准入**：校验函数放 `packages/services/src/skill-services/catalog.ts`（新建目录，目前不存在）；`upsertSkillServiceCatalogSync`（db）保留原样，services 层 `createSkillServiceCatalogEntrySync` 先校验再落库。校验项：`imageDigest` 匹配 `/^sha256:[a-f0-9]{64}$/`；`rollbackClass ∈ {stateless, backward_compatible, irreversible_migration}`；`deploymentType ∈ {external_connection, managed_service, platform_shared}`；`external_dependencies_json` 为 `kind:name` 数组且**不允许创建** PG/Redis/RabbitMQ（仅引用集中托管）；`network_json` JSON 可解析且含 egress 白名单；`templateDigest` 非空。

## 关键改动

### A. 审批 + diff 门 + 升级不变量
- `packages/db/src/postgres-schema.ts`：新增 `skill_upgrade_approval` 表 + bump `POSTGRES_SCHEMA_VERSION`（64→65）。
- `packages/db/src/skill-upgrade-approvals.ts`（新）：`createSkillUpgradeApprovalSync`（不可变 insert，UNIQUE 去重）、`readSkillUpgradeApprovalSync(id, workspaceId)`、`consumeSkillUpgradeApprovalSync`（事务内 set consumed_at）、`listSkillUpgradeApprovalsSync`。从 `index.ts` 导出。
- `packages/services/src/skills/release.ts`：
  - `approveSkillUpgradeSync({workspaceId, skillId, fromDigest, toDigest, diffHash, decision, reason, actorUserId})`。
  - `computeSkillUpgradeDiffHashSync(fromManifestJson, toManifestJson)` = `sha256(stableStringify(diffSkillArtifactsSync(...)))`。
  - `createSkillUpgradePlanSync` 增 `approvalId?`：校验不变量（ready/同 runtime/同 lineage）→ 计算 diff → breaking 时校验+消费 approval → 事务建安装。
- `apps/web/features/skills/installation-actions.ts`：`createSkillUpgradeAction` 改为调用 `approveSkillUpgradeSync`（记录批准人/理由/diffHash）再传 `approvalId`（替换裸 boolean）。

### B. rollout_pin / canary
- `packages/db/src/postgres-schema.ts`：`ALTER TABLE agent_skill ADD COLUMN IF NOT EXISTS rollout_pin TEXT`。
- `packages/db/src/skills.ts`：`setStoredEmployeeSkillAssignmentsSync` 写入 `rollout_pin`（当前 active revision）；新增 `setSkillRolloutPinSync({workspaceId, skillId, revision})`（批量更新该 skill 所有 assignment 的 pin）。
- `packages/services/src/skills/installations.ts`：`resolveTaskSkillExecutionSnapshotSync` 增 honor pin：`rollout_pin` 存在 → `readSkillInstallationByLockSync({..., revision: pin})` 需 ready，否则回落最高 revision。

### C. catalog 准入
- `packages/services/src/skill-services/catalog.ts`（新目录+文件）：`createSkillServiceCatalogEntrySync(input)` 校验（见关键决策）后调 `upsertSkillServiceCatalogSync`；`assertSkillServiceCatalogAdmissionSync(input)` 导出供测试。从 `index.ts` 导出。
- `packages/db/src/skill-services.ts`：不改（db 层保持 CRUD；准入在 services 层）。

### 测试
- `packages/services/src/skills/release.test.ts` 增：breaking 升级无 approval 拒绝；有匹配 approval 通过；diffHash 不匹配拒绝；approval 一次性消费（二次使用拒绝）；升级不变量拒绝（previous 非 ready / 跨 runtime / 跨 lineage）。
- `packages/daemon/src/task-context-skill-env.test.ts` 增：rollout_pin 固定 assignment 到指定 revision；pin 更新后新任务用新 revision。
- `packages/services/src/skill-services/catalog.test.ts`（新）：合法条目通过；坏 imageDigest / 非法 rollbackClass / 内嵌 PG/Redis/RabbitMQ 创建 / 坏 network JSON / 空 templateDigest 均拒绝。
- 共享 PG 测试库脆弱性：单文件串行；先重新 seed default 工作区（见 [[mcp-center-test-db-fragility]]）。

## 已确认决策

1. 审批 = 新不可变表 `skill_upgrade_approval`，`diff_hash` 绑定，一次性消费。
2. 升级不变量：previous-ready / 同 runtime / 同 lineage。
3. rollout_pin 列 + 任务快照 honor pin；canary = 按 assignment 的 pin 切换。
4. catalog 准入校验在 services 层（db 保持 CRUD）。
5. managed-node worker / Phase 5 UI / Phase 6 观测为后续独立计划。
