# 执行计划与验收

## 1. 交付顺序

| 阶段 | 目标 | 主要交付 | 完成门槛 |
| --- | --- | --- | --- |
| 0：契约 | 统一模型，不改变现有行为 | DSP schema、类型、artifact validator、错误码 | 目录/ZIP/Git fixture 均可产生相同 digest |
| 1：完整导入 | 不再丢脚本、assets 或 mode | blob store、文件清单、统一 resolver、来源锁定 | services 与 daemon 使用同一 allow-list/validator |
| 2：Remote 安装 | 依赖与脚本可受控使用 | installation operations、Runtime cache、runner、readiness gate | 无全局/宿主机写入，失败不进入任务 |
| 3：能力绑定 | CLI/MCP/支撑服务真实可用 | CLI resolver、MCP Center bridge、service catalog/binding | 只有 ready/approved capability 能进入 Provider |
| 4：版本与发布 | 可灰度、可回滚 | release lock、semantic diff、canary、服务 upgrade policy | 能重现历史任务并回滚到 ready revision |
| 5：产品体验 | 可解释、可维护 | Skill Library、五步向导、服务详情、升级 diff、审计 | 管理员测试达到产品指标 |
| 6：迁移与加固 | 兼容旧数据并可运营 | legacy migration、rollout、指标、回滚 | 老 Skill 不丢失，风险 Skill 不自动执行 |

## 2. 建议代码落点

| 责任 | 建议模块 | 变更 |
| --- | --- | --- |
| 领域模型 | `packages/domain/src/skill-package.ts` | `SkillArtifact`、`SkillInstallation`、component、状态和 operation 协议 |
| 存储 | `packages/db/src/skill-artifacts.ts` | artifact/file/blob/installation/component/operation 表及 workspace 约束 |
| 解析与策略 | `packages/services/src/skills/package-*` | YAML/manifest schema、Git SHA/registry resolver、风险、安装计划 |
| 兼容导入 | `packages/services/src/skills/import.ts` | 保留当前入口，改为生成 artifact；删除重复文件白名单 |
| 运行时 | `packages/daemon/src/skill-*` | artifact materializer、operation worker、runner client、任务 freshness check |
| Provider | `packages/daemon/src/agent-router/adapters/*` | 只接收 ready skill projections 与 MCP/CLI tool bridge |
| MCP | `packages/services/src/mcp-center/*`、`packages/daemon/src/mcp-*` | 完成 connection operation、discovery、ready context、调用审计 |
| 支撑服务 | `packages/services/src/skill-services/*`、managed node worker | service catalog、实例/绑定、健康、灰度、升级和退役；不在 Web 或 Runtime 直接编排容器 |
| Web | `apps/web/features/skills/*` | Library、向导、安装详情、diff；市场只提供 capability 选择 |

现有 `packages/services/src/skills/injection.ts`、`packages/daemon/src/skill-imports.ts` 和 `packages/services/src/skills/import.ts` 应先共享一套 package validator，消除双份扩展名和路径逻辑。不得通过新增 Docker Compose 服务解决 runner、MCP 或依赖问题；PostgreSQL、Redis、RabbitMQ 继续使用集中管理基础设施。

## 3. 迁移与兼容策略

1. 新建表和 API，旧 `skill`/`skill_file` 继续读写，不做破坏性替换。
2. 后台为每个旧 Skill 构造 `legacy_unverified` artifact：内容 hash 可用，mode 默认 `0644`，二进制缺失或不可信文件显示需重新导入。
3. 现有 assignment 映射到 artifact，但不自动创建 dependency/script/MCP installation；首次任务前显示需准备。
4. Provider 原生目录在双写期同时投影新/旧来源，比较 manifest digest 和文件清单，稳定后移除旧 materializer。
5. 对每个 installation 保留上一个 ready digest；升级失败或健康降级时一键回滚 assignment。

## 4. 测试矩阵

| 层级 | 必测案例 |
| --- | --- |
| package 单元测试 | YAML 正确/错误、二进制、mode、symlink、路径穿越、ZIP bomb、hash 不符、相同来源 digest 一致 |
| resolver 集成测试 | Git SHA、可变 branch 拒绝/锁定、Skills.sh/ClawHub artifact、Runtime artifact provenance、私有源授权 |
| installation 服务测试 | 每种依赖 manager、cache 隔离、失败/重试/幂等、ready/degraded 转换、assignment 门禁 |
| daemon 集成测试 | Remote Runtime materialization、runner 无 credential/no network、输出边界、资源超限、清理 |
| service 集成测试 | managed/external/shared service 的准入、scope、健康、密钥、蓝绿/金丝雀、失败回滚和退役 |
| MCP 测试 | HTTP initialize/tools/list/call、认证、重定向/DNS 拒绝、tool allow-list、停用后不注入；stdio 仅受管容器 |
| provider 合约测试 | Codex/Claude/OpenCode 等投影内容相同、只显示 ready tools、拒绝未批准脚本/MCP |
| Web 测试 | 向导成功/阻断/恢复、密钥不回显、升级 diff、移动端与键盘、无权限 |
| E2E | 从 ZIP/Git/registry 安装复合 Skill 到真实 Remote Runtime，运行脚本、调用 MCP、升级回滚 |

测试必须为每个测试创建独立 workspace/database namespace，禁止并发测试共享 `default` workspace。所有 Jest/monorepo 运行遵守仓库既定并发限制；不使用 Jenkins 部署或触发 Jenkins。

根 `pnpm test` 通过 `turbo run test --concurrency=2` 调度。DB、services、daemon 均提供真实 Skill 安装测试入口，不允许以 `<NONEXISTENT>` 跳过；共享 PostgreSQL 的 services 套件逐文件、文件内单并发执行，避免 release/installation 生命周期测试互相污染。

## 5. 非功能验收

- **完整性**：任一允许文件在导入、导出、artifact、Remote materialization 的 SHA-256 一致；unsupported 文件使检查失败或明确需转换，绝不静默跳过。
- **隔离**：检查容器/进程确认无宿主机写入、无 Docker socket、无 Provider HOME/密钥挂载；依赖不出现在另一个 Runtime 的 PATH。
- **可用性**：所有 required component ready 后，任务可调用脚本/CLI/MCP；任一 component 降级后，新任务不再接收它。
- **安全**：分支/tag、无 digest 的 registry 包、任意 shell、裸 stdio command、私网/metadata MCP endpoint 均被策略拒绝或要求审核转换。
- **可复现**：给定 artifact digest、installation lock 和 Runtime base version，可重建等价安装；任务审计能关联到确切 digest。
- **性能**：P95 检查在 10 秒内完成（不含下载）；小于 10 MB 的纯文本包 P95 导入在 30 秒内；安装进度至少每 5 秒更新一次。

## 6. 上线与回滚

使用 feature flag 按 workspace 开启：先内部只读 inspection，再允许纯指令/资产包，再允许声明式依赖，最后允许受控脚本和 MCP capability。每阶段监控 import/prepare 成功率、ready 时间、runner 拒绝率、任务前置失败率、MCP/CLI capability 健康与回滚率。

出现安全策略误放行、跨 Runtime 文件/凭据可见、digest 不一致或任务执行越权时，立即停用相应 capability kind、冻结新 installation、保留 artifact/审计并回滚 assignment 到最后一个 ready digest。部署在本机到此为止：完成实现、验证和用户明确要求的提交/推送；不执行 Jenkins 部署。
