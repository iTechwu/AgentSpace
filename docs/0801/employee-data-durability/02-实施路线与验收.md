## 1. 实施原则

- 先建立事实来源和提交语义，再优化运行时缓存与界面。
- 迁移期间不改变既有员工的稳定 ID，不自动覆盖现有 Skill 绑定。
- 每一阶段均需能在没有旧容器、旧镜像和旧状态卷的情况下验证恢复。
- 所有数据库、对象存储和消息依赖使用既有集中管理服务；本项目的 Docker 配置不新增基础设施服务。

## 2. 分阶段路线

| 阶段 | 交付内容 | 完成门槛 |
| --- | --- | --- |
| P0：基线与防护 | 记录当前存储位置、标记临时目录、禁止任务成功后仅保留在 `workDir` | 建立资产清单，完成一次当前环境的只读恢复风险检查。 |
| P1：Skill 制品闭环 | 全量导入、manifest、digest、对象存储、固定版本绑定 | 脚本和二进制资源可从制品重建，缺失任何声明文件时导入失败。 |
| P2：员工持久工作空间 | 工作空间实体、revision、产物提升、任务提交账本 | 任务完成后的成果能脱离 Daemon 状态卷读取。 |
| P3：运行时恢复编排 | 绑定 generation、健康预检、重建/重新绑定 API、恢复审计 | 删除运行时容器和状态卷后，能恢复员工到可调度状态。 |
| P4：产品与运维闭环 | 数据保护页面、告警、备份策略、恢复手册和演练自动化 | 恢复演练按周期通过，RPO/RTO 指标可观测。 |

### P0：基线与防护

> **实施状态**：已修复 committed 语义；其余清单/文档标识待补齐。

1. 为现有 `workDir`、Provider Home、Daemon 状态目录、Skill 导入存储和员工产物建立数据分类清单。
2. 在任务执行模型中定义 `preparing_commit` 与 `committed`，禁止仅以 Provider 返回成功作为任务成功。
3. 将临时目录、缓存目录和可持久目录在日志与运维文档中明确标识。
4. 为现有 Docker Compose 增加运行手册说明：普通重启可保留 named volume，但卷删除不等于安全恢复方案。

### P1：Skill 制品闭环

> **实施状态**：已修复导入二进制/脚本完整进入制品与运行时 fail-closed；稳定 `employeeId` 已覆盖 Skill assignment、requirement config、Knowledge、binding、workspace、recovery 与 mount 关系，`employee_name` 仅作为显示快照。

基于 `docs/0801/skill-install/` 的 DSP 设计完成以下能力：

1. 导入端递归读取文件并以二进制安全方式写入对象存储，不得静默跳过 `scripts/`、图片、字体或其他二进制资源。
2. 生成确定性 manifest：相对路径、大小、媒体类型、SHA-256、blob 引用和制品 digest。
3. `employee_skill_assignment` 保存 `skillArtifactDigest`；名称仅用于显示和搜索。
4. Runtime 安装器在缓存构建和任务投影前校验 manifest 与每个文件摘要。
5. 安装依赖、下载工具和 Provider 专有适配信息写入安装计划；依赖缓存可删除且必须能重新执行。

首个回归样本使用 `guizang-ppt-skill`：其 `scripts/validate-swiss-deck.mjs` 和 `assets/` 必须同时出现在制品清单、运行时缓存和任务 `.codex/skills` 投影中，且摘要一致。

### P2：员工持久工作空间与提交账本

> **实施状态**：已修复。`employee_persistent_workspace`、`employee_workspace_revision`、`employee_artifact`、`task_commit_journal` 已实现；`promoteTaskOutputsToWorkspaceSync` 幂等；孤儿 blob 扫描 `reclaimOrphanContentBlobsSync` 已可运行。

1. 新增 `employee_persistent_workspace`、`employee_workspace_revision`、`employee_artifact` 和 `task_commit_journal`。
2. 实现内容上传、manifest 生成和数据库提交的幂等接口；所有写入使用任务 ID 作为幂等键。
3. 在任务上下文向 Agent 提供明确的“保存检查点/发布产物”能力，避免要求 Agent 猜测哪个目录会持久保存。
4. 对会话型任务也使用相同提交路径。会话目录可以存续，但不成为唯一工作空间。
5. 实现孤儿 blob 扫描和延迟回收，避免中断任务留下不可达内容。

### P3：恢复编排

> **实施状态**：【部分实现】控制面 phase 推进与 binding generation 切换已落地；真正的容器创建、workspace 挂载、secret 注入仍由外部 runtime-provisioning 服务完成。

恢复 API 可以采用如下资源模型，具体路由沿用现有 API 风格：

| 操作 | 输入 | 幂等键/保护 | 成功条件 |
| --- | --- | --- | --- |
| 创建工作空间快照 | `employeeId`、当前 head | `taskId` 或请求 ID | 新 revision 已提交且 manifest 可读取。 |
| 重新绑定运行时 | `employeeId`、目标 runtime/provider | binding generation | 新运行时通过预检，旧代次失效。 |
| 重建运行时 | `employeeId`、镜像/Provider 选择 | `recoveryOperationId` | 工作空间、Skill 和密钥引用均校验通过。 |
| 恢复历史 revision | `employeeId`、目标 revision | 二次确认、审计 ID | 产生新的 head revision，不覆盖历史。 |

恢复编排必须逐步记录 `allocate`、`mount_workspace`、`install_skills`、`resolve_secrets`、`health_check`、`activate`。任何步骤失败都保留故障上下文，允许从安全步骤重试；不能把未验证的运行时切换为当前绑定。

### P4：产品、告警与演练

> **实施状态**：已实施员工详情页数据保护面板、健康告警、恢复操作/演练历史与手动演练触发；Cron 调度与管理员通知已接入。D-10 当前为元数据级演练，真正的跨环境物理恢复仍需外部 PostgreSQL PITR / 对象存储备份与隔离恢复环境。

员工详情页增加“数据保护”区域：最近已提交 revision、最近备份/恢复演练、绑定 Skill 摘要、运行时 generation、恢复操作状态、员工级健康告警，以及手动“运行演练”按钮。对以下情况告警：

- 工作空间最新 revision 超过策略时间未备份或无法读取。
- 制品摘要校验失败、Skill 文件缺失或安装缓存与绑定摘要不一致。
- 恢复操作失败、反复重试或运行时长时间处于 `offline`/`degraded`。
- 任务长时间卡在 `preparing_commit`，或孤儿 blob 超过阈值。

## 3. 迁移方案

### 3.1 现有数据迁移

> **实施状态**：稳定 `employeeId` 全链迁移已完成。PostgreSQL v92 将关系主键、唯一约束、冲突键和查询切到 `employee_id`；名称变更由触发器同步显示快照；旧 SQLite 迁移会生成确定性 ID 并回填关联，旧名复用不会继承原员工数据。

1. **盘点**：导出现有员工、绑定关系、工作区、已导入 Skill 和可识别的产物；保留旧主键与创建时间。
2. **制品化**：为每个现有 Skill 创建初始 artifact。无法完整读取的历史 Skill 标记 `legacy_incomplete`，禁止新绑定，不能伪造完整校验结果。
3. **创建工作空间**：为每位员工创建 `employeeWorkspaceId` 与空的初始 revision；将可确认的正式产物导入为独立 revision。
4. **双读校验**：先由新控制面读取绑定和制品摘要，旧运行时仍可执行；不在此阶段删除旧状态卷。
5. **切换**：新建或重新绑定运行时使用新恢复链路。旧运行时在完成验证后仅作为只读回退窗口。
6. **回收**：在保留期和至少一次恢复演练后，回收不可重建的旧运行时数据；回收清单需人工审批并可追溯。

### 3.2 数据迁移判定

| 情况 | 处理 |
| --- | --- |
| 现有 Skill 有完整源目录 | 制作制品并比对文件数量、路径、大小和 digest。 |
| 历史导入曾跳过二进制或脚本 | 标记不完整，要求从可信源重新导入。 |
| 任务目录中存在未发布文件 | 不自动当作正式成果；由管理员选择导入、舍弃或归档。 |
| 员工原运行时已离线 | 创建持久工作空间和绑定记录后，按恢复流程重新绑定。 |
| named volume 已丢失 | 从控制面制品、工作空间 revision 与备份恢复；不存在这些来源的历史临时文件不可承诺找回。 |

## 4. 故障恢复手册

### 4.1 运行时或 Docker 容器离线

1. 监控将绑定标记为 `offline`，停止向旧 generation 分派写任务。
2. 检查最近 `committed` 任务和工作空间 head revision；未提交任务进入待恢复队列。
3. 创建新运行时或绑定已有兼容运行时。
4. 从控制面加载员工期望配置，挂载最新已验证工作空间，安装锁定的 Skill digest，并解析运行时密钥引用。
5. 执行只读工作空间校验、Skill manifest 校验和 Provider 健康检查。
6. 原子提升 binding generation 为当前版本，恢复任务调度；旧 generation 不再具有写权限。

### 4.2 镜像重建、错误卸载或状态卷删除

1. 不尝试从被删除的 `.codex/skills` 或 `workDir` 恢复唯一业务数据。
2. 以新镜像启动运行时，执行 P3 的恢复编排。
3. 比对恢复后的工作空间 head manifest、Skill digest 和绑定清单与控制面记录。
4. 若摘要不一致，保持 `needs_attention`，禁止写入，记录差异并从已验证快照重新恢复。

### 4.3 工作空间或制品存储故障

1. 冻结该工作空间的新提交，保留任务账本和诊断信息。
2. 从版本化存储或备份恢复到新的存储位置，不直接覆盖原数据。
3. 对恢复内容重算或验证 manifest digest，通过后更新 `storageRef`。
4. 在隔离运行时执行只读恢复检查，确认后解除冻结。

### 5.1 建议自动化覆盖

- 数据库/服务层：revision 原子提交、并发写冲突、幂等重试、绑定 generation 和权限隔离。
- Skill 服务层：二进制文件导入、递归目录、manifest 可复现性、摘要不匹配失败、安装缓存重建。
- Daemon 集成：模拟 `workDir` 清理、容器重启、状态卷为空、运行时离线和重新绑定。
- 端到端 UI：导入 Skill、绑定员工、查看数据保护状态、触发恢复、观察错误状态与审计记录。
- 演练脚本：在隔离测试环境中销毁运行时容器/缓存后恢复，不删除集中管理的基础设施服务。

遵守仓库测试资源限制：单 API Jest 文件使用 `pnpm --filter @repo/api exec jest path/to/file.spec.ts --runInBand`；完整测试使用受限并发，不执行无约束的根 `pnpm test`。

## 6. 可观测性指标

| 指标 | 用途 | 告警建议 |
| --- | --- | --- |
| `workspace_revision_commit_latency` | 监测提交路径性能 | 超过目标或持续升高。 |
| `workspace_head_age` | 发现长期未成功持久化的活跃员工 | 超过策略窗口。 |
| `skill_artifact_verification_failures_total` | 发现制品损坏或安装不兼容 | 任意新增失败。 |
| `runtime_recovery_duration` | 验证 RTO | 超过约定 RTO。 |
| `runtime_binding_generation_conflicts_total` | 发现脑裂/陈旧写入 | 任意新增冲突。 |
| `task_commit_reconciliation_backlog` | 发现中断后的待处理提交 | 超过阈值或持续增长。 |
| `backup_restore_drill_success` | 验证备份真实可用 | 最近一次失败或超期未演练。 |

## 7. 上线前待确认项

以下事项需要产品、平台和安全共同确认后才可将状态改为 Accepted：

1. 员工工作空间选用的受管存储、数据驻留区域、加密和跨区域恢复策略。
2. 不同套餐/工作区的容量、revision 保留期限、软删除期限与成本上限。
3. 最终 RPO/RTO、恢复演练频率和故障通知责任人。
4. 任务可自动恢复的边界，以及涉及外部副作用时的人工确认策略。
5. Skill 安装依赖的允许列表、网络策略与供应链扫描要求。
6. 管理员可执行恢复、导出、删除与重新绑定操作的权限模型。

确认后，应在对应的 ADR 中固化选型、迁移日期、回退窗口和责任归属，并将验收矩阵纳入发布门禁。
