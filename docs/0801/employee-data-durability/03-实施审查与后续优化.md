# 员工数据持久化实施审查与后续优化

状态：Implementation Review
审查日期：2026-08-02
审查基线：当前工作树中的 Domain、DB、Services、Daemon、Web、Docker 配置与定向测试

## 1. 总体结论

当前实现已经完成了持久化控制面的主要骨架，并修复了最初审查发现的多项高风险问题：Skill 全量制品化、固定摘要、完整快照 manifest、真实对象存储引用、制品损坏 fail-closed、任务提交门禁、恢复 provisional binding、严格 generation 比较、数据保护只读页面和健康检查入口、稳定 `employeeId`、可留存备份-恢复演练、Cron 调度与管理员通知均已存在。

但系统目前仍不具备“Docker、Daemon 或员工运行时被删除后，可在新运行时完整恢复员工工作状态并继续工作”的生产级保证。核心原因不是缺少表，而是以下数据面尚未闭环：

1. 员工长期工作状态仍未从真实 `workDir` 或受管工作区持续提交和重新挂载；当前主要持久化显式返回的附件。
2. 恢复流程验证了控制面记录与 blob，却没有实际创建运行时、还原工作目录、执行 Skill installation operation、验证目标 Runtime 健康后再恢复任务。
3. D-10 演练已持久化元数据级结果并接入 Cron，但仍不是从数据库备份和对象存储版本恢复到干净环境，真实跨环境物理恢复需外部 PostgreSQL PITR / 对象存储备份与隔离恢复环境。
4. 员工持久化身份已在 EAD 表落实稳定 `employeeId`，`employee_skill_assignment` 等非 EAD 表仍以 `employee_name` 关联，为后续迁移剩余项。

因此，当前合理的产品状态是：**持久化基础能力开发中，显式产物具备较强保护；整名 AI 员工的灾难恢复尚未完成，不应承诺运行时销毁后可无损恢复全部工作状态。**

## 3. 阻断生产级持久化的事项

### P0-1：尚未持久化员工的真实长期工作目录

当前任务完成路径只将 `outputEnvelope.attachments` 或 `persistedAttachments` 提升为 workspace revision。任务在项目目录中创建或修改的代码、草稿、工具状态、会话检查点和未显式附加的文件不会进入员工持久工作空间。

这意味着：

- 完整快照目前是“历次已发布附件的完整集合”，不是员工实际 `workDir` 的完整快照。
- 会话型 `workDir` 即使暂时留在 Daemon volume 中，卷删除或节点迁移后仍会消失。
- 恢复服务没有可用于还原 `repository/`、`state/` 和 `checkpoints/` 的真实内容。

**必须补齐**：定义员工工作空间挂载协议和显式提交协议。任务开始时将指定 revision materialize 到受控目录；任务结束时按允许路径计算 diff，提交新 revision；大项目使用 Git/对象存储混合模型，工具缓存和 Provider Home 不进入快照。

**验收**：在员工 `workDir` 修改多个未作为附件返回的文件，销毁运行时和状态卷，在新节点恢复后文件内容、权限和路径一致。

### P0-2：恢复流程仍是控制面校验，不是真实运行时恢复

[recovery.ts](../../../packages/services/src/employees/recovery.ts:191) 的阶段名称已经与设计一致，但具体行为仍有限：

- `allocate` 只接收或复用一个 `runtimeId`，没有调用 runtime provisioning 创建替代运行时。
- `mount_workspace` 只检查 head manifest 中的 blob 是否存在，没有把文件还原到目标 Runtime。
- `install_skills` 只验证中央 artifact 完整性，没有为目标 Runtime 创建/等待 installation，也没有验证 Runtime cache。
- `health_check` 只读取控制面状态，没有调用目标 Runtime 的心跳、Provider smoke 或只读文件检查。
- Recovery API 中的 `rebuild` 和 `rebind` 当前走同一函数，`action` 不改变执行行为；见 [recovery route](../../../apps/web/app/api/daemon/employees/%5BemployeeName%5D/recovery/route.ts:83)。

**必须补齐**：恢复编排改为可暂停的异步 operation，由 provisioning worker 和 Daemon worker 逐阶段回报证据。只有工作空间已实际 materialize、锁定 Skill installation 全部 `ready`、密钥注入验证和 Provider smoke 通过后，才能执行 `activate`。

### P0-3：Remote Skill installation 已有 Daemon 执行器，但尚未接入恢复端到端

Daemon 侧已实现 Skill installation operation worker：

- `packages/daemon/src/skill-install/artifact-materializer.ts` 下载/物化 artifact 文件、校验每文件 sha256 与根 digest。
- `packages/daemon/src/skill-install/component-verifier.ts` 对 dependency/script/cli/mcp 组件做轻量校验。
- `packages/daemon/src/skill-install/operation-worker.ts` 编排 start → materialize → verify → complete/fail，并清理工作目录。
- `packages/daemon/src/remote-daemon.ts` 的 `executeRemoteSkillInstallationOperation` 已调用该 worker。
- 控制面 `resolveClaimedSkillInstallationOperation` 已为每个文件生成 `downloadUrl` / `storedPath` 并下发 manifest。

但 worker 尚未被真实 Recovery 流程调用，`assertSkillInstallationReadyForTaskSync` 也未接入任务启动主路径；端到端证据（从 claim 到 complete 的真实 runtime installation）仍待验证。详细差距见 [Skill 安装实施差距审查](../skill-install/07-实施差距审查.md)。

**必须补齐**：将 Skill installation operation 接入 recovery 的 `install_skills` phase，并在任务启动前检查 installation readiness；补充端到端测试覆盖 TOS 签名 URL 下载、本地回退、文件损坏、组件校验失败场景。

### P0-4：generation guard 取值时机不能识别旧运行时（已修复）

`agent_task_queue` 新增 `binding_generation` 列；`claimNextQueuedTaskForRuntimeSync` 在任务被认领时读取当前 `employee_runtime_binding.generation` 并写入该列；`ClaimedDaemonTask` 携带 `bindingGeneration` 下发到 Daemon。

任务完成入口（[daemon.ts](../../../apps/cli/src/commands/daemon.ts:1290) 与 [complete route](../../../apps/web/app/api/daemon/tasks/%5BtaskId%5D/complete/route.ts:331)）现在优先使用 `task.bindingGeneration`，仅对无该值的遗留任务回退到读取当前 generation。这样任务执行期间员工被重新绑定到更高 generation 时，旧 Runtime 携带的仍是认领时的 generation，会触发 `STALE_BINDING_GENERATION` 而不是错误写入新 workspace。

遗留任务或外部直接调用若未经过 claim 路径，仍可能重新采样当前值；这些入口应逐步改为强制携带 claim 时 generation。

### P0-5：员工身份仍依赖可变名称（已部分修复）

`workspace_employee` 已新增不可变 `id` 列，`ActiveEmployee` 暴露 `id`；EAD 表（`employee_persistent_workspace`、revision、artifact、runtime binding、recovery operation、`task_commit_journal`）已新增 `employee_id` 外键并回填非空化，生产写入通过 `resolveStoredEmployeeIdSync` 解析为外键。

但 `employee_skill_assignment` 等非 EAD 表仍以 `employee_name` 关联。员工改名、同名迁移或历史名称复用仍可能导致这些非 EAD 数据关联错误。这与 EAD-002 的稳定身份决策尚未完全一致。

**必须补齐**：将 `employee_skill_assignment` 等剩余表迁移到 `employee_id`；在迁移期间保留旧名称映射，重命名必须保持同一 workspace head、Skill assignment、artifact 和 binding generation。

### P0-6：D-10 已持久化但仍不是真实备份恢复演练

`runBackupRestoreDrillRunSync` 会创建 `backup_restore_drill_run` 记录，抽样员工并验证 workspace head manifest digest 与 bound Skill artifact digest 能否从控制面重算一致；Cron 路由 `app/api/cron/backup-recovery-drill/route.ts` 失败返回 503 并通知管理员。源码仍明确说明没有执行跨环境物理恢复；见 [data-protection-health.ts](../../../packages/services/src/employees/data-protection-health.ts:191)。

它可以发现元数据被篡改，也能留存演练结果供 UI 与审计，但不能证明以下能力：

- PostgreSQL PITR 或备份可用；
- TOS versioning、生命周期和误删除恢复可用；
- 数据库与对象存储恢复点一致；
- 在干净环境中能达到约定 RTO。

**必须补齐**：由外部受管基础设施执行数据库与对象存储备份，在隔离环境恢复抽样 workspace，重新计算全部 blob、manifest 和 Skill digest，并保存演练时间、恢复点、耗时与结果。AgentSpace Compose 不新增 PostgreSQL、Redis 或 RabbitMQ。

## 4. 高优先级优化项

### P1-1：提交链不是端到端原子且 formal artifact 重试可能重复

任务输出提升依次执行 blob 上传、`employee_artifact` 发布、revision 创建/提交、queue 状态更新和 journal upsert。这些动作跨对象存储与多个数据库事务。`employee_artifact` 没有 `(source_task_id, content_digest, file_name)` 等幂等约束，任务在中间失败后重试可能产生重复正式产物。

应采用 pending publish/session：先以 task/output 幂等键登记待发布内容，再提交 revision、artifact references 和 journal；数据库事务成功后再标记可见。为 artifact 增加唯一幂等键和状态，补充“发布 artifact 后、revision 提交前崩溃”的故障注入测试。

### P1-2：只有 backlog 告警，没有自动 reconciliation worker

`listStaleCommitJournalsSync` 能发现长期处于 `preparing` 的任务，健康检查也会告警，但没有负责重新读取已保存附件、继续提升、提交或回滚的 worker。CLI 本地执行失败后尤其不能依赖 HTTP 503 自动重试。

应增加可重入 reconciliation job，区分可重试、永久失败和需人工处理；记录下次重试时间、退避、最大次数和 dead-letter 状态。只有确认原始附件不可恢复时才允许标记失败。

### P1-3：Secret 恢复校验会要求每个已制品化 Skill 都存在配置行

[resolveSecretsResolvable](../../../packages/services/src/employees/recovery.ts:329) 的注释要求“只有声明 requirements 的 Skill 才检查配置”，但实现仅根据是否有 artifact digest 判断，并为每个已锁定 Skill读取 `agent_skill_requirement_config`。

普通、无配置要求的 Skill 如果没有空配置行，也可能被错误判为不可恢复。应从锁定 artifact 的 requirements 或规范化需求模型判断是否需要 Secret/Config，再验证所需 key 是否齐全，而不是只判断配置行是否存在。

### P1-4：健康检查 Cron 仅覆盖 `default` workspace

[data-protection-health route](../../../apps/web/app/api/cron/data-protection-health/route.ts:23) 硬编码 `workspaceId: "default"`。多工作区部署中，其他租户的损坏 artifact、过期快照、恢复失败和提交 backlog 不会被检测。

应枚举所有活动 workspace，逐租户评估并输出聚合结果；对单租户失败隔离处理，避免一个工作区异常阻断其他工作区的检查。

### P1-5：数据保护操作权限和用户恢复流程尚未完成

员工详情已有只读面板，但没有管理员“重建/重新绑定/恢复历史 revision”操作。现有 recovery POST 仅使用 Daemon token，源码明确将管理员权限模型标为待确认；见 [recovery route](../../../apps/web/app/api/daemon/employees/%5BemployeeName%5D/recovery/route.ts:20)。

需要补充管理员授权、二次确认、目标 revision/runtime 预览、异步进度、失败重试、审计和旧 generation 状态展示。普通用户不得通过名称猜测跨员工执行恢复。

### P1-6：遗留 completion API 仍可绕过提交门禁

生产主路径已使用 `completeCommittedTaskSync`，但公共的 `completeQueuedTaskSync` 仍允许从 `running` 直接完成并创建空 `committed` journal；见 [task-queue.ts](../../../packages/db/src/task-queue.ts:363)。当前生产调用已清理，但未来调用者仍可能绕过不变量。

应将其改为仅供迁移/测试的显式 legacy API，或彻底移除；更稳妥的做法是在数据库状态转换层强制 `committed -> completed`，而不是依赖调用者选择正确函数。

## 5. 中优先级优化项

### P2-1：保留策略和软删除只有字段/函数，没有生命周期执行

`retention_policy_json`、`deleted_at` 和 orphan blob 回收函数已经存在，但没有按租户策略执行的定时任务、恢复窗口、legal hold、配额和管理员审计流程。应在真实备份方案确定后实现，避免 GC 先于备份回收数据。

### P2-2：健康指标形成部分运营闭环

Cron API 返回 JSON/HTTP 503，备份-恢复演练结果已持久化到 `backup_restore_drill_run` 并通过员工详情面板展示；管理员可在面板手动触发演练。但部署侧定时调用、指标 exporter、告警去重和恢复通知仍需与外部监控/告警系统对接。

### P2-3：Skills.sh 导入测试基线当前为红色

本轮定向测试共 56 项，54 项通过、2 项失败。两个失败均来自 Git SHA 锁定后测试 mock 未提供 `/commits/{ref}` 响应，导致 `skills.sh` 导入测试收到 404；见 [import.ts](../../../packages/services/src/skills/import.ts:871) 和 [import.test.ts](../../../packages/services/src/skills/import.test.ts:273)。

这更像测试 fixture 未随实现更新，而不是已证明的生产解析失败，但在修复 mock、增加 SHA provenance 断言并恢复全绿前，不能把 Skill 来源锁定标记为验收完成。

### P2-4：测试隔离依赖单并发

数据库型测试共享 `default` workspace 和同一测试数据库，并发执行会相互清理数据、触发唯一键或 FK 失败。目前必须使用 `--test-concurrency=1` 才稳定。应为每个测试文件分配独立 workspace/schema，避免测试并发策略掩盖状态泄漏。

## 7. 建议实施顺序

### M0：先封住错误写入与身份风险

1. 任务 claim 时固定 binding generation，并贯穿 input bundle、attempt 和 completion。
2. 为 artifact/revision/journal 建立统一发布事务与幂等键，完成自动 reconciliation worker。
3. 引入稳定 `employeeId` 并迁移所有持久化、binding、assignment 和 recovery 外键。
4. 修复 Secret requirements 判定和 Skills.sh 测试 fixture，恢复定向测试全绿。

### M1：实现真正的员工持久工作空间

1. 定义受管 workspace mount/materialize/commit API，明确 `repository/`、`state/`、`checkpoints/`、`artifacts/` 边界。
2. 将任务实际文件 diff 提升为 revision，而不只提升附件。
3. 实现权限、配额、快照压实、冲突合并、软删除和恢复。
4. 完成“删除 Daemon state volume 后还原全部文件”的集成测试。

### M2：打通 Runtime 与 Skill 恢复数据面

1. Recovery operation 调用 runtime provisioning，创建 provisional Runtime。
2. Daemon 在目标 Runtime materialize workspace head，并回报文件摘要。
3. Daemon 执行锁定 Skill installation operation，所有组件 ready 后才继续。
4. 执行 Secret/Provider/文件系统健康检查，再原子切换 binding generation。
5. 对失败 operation 提供重试、取消、回滚和 `needs_attention` 管理流程。

### M3：完成灾难恢复与运营闭环

1. 接入外部 PostgreSQL PITR、TOS versioning/retention 和一致恢复点。
2. 在干净隔离环境定期恢复抽样员工，记录 RPO/RTO 和 digest 证据。
