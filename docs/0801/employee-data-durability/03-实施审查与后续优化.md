# 员工数据持久化实施审查与后续优化

状态：Implementation Review（第五轮）
审查日期：2026-08-03
审查基线：当前分支的 Domain、DB、Services、Daemon、Web、恢复编排及定向测试

## 1. 结论

本轮实施后，员工数据持久化已经从“控制面骨架”进入“主要代码路径闭环”阶段。以下旧结论已失效：工作目录只保存显式附件、mount 使用完即删除、Skill 依赖不真实安装、任务不消费依赖环境、恢复历史版本没有产品入口、D-10 只校验 manifest 元数据。

当前已具备：工作目录 diff/tombstone、完整 revision、对象存储 blob、任务启动 fail-closed 还原、持久 mount、恢复 phase 编排、绑定 generation fencing、提交 reconciliation、真实 Skill 依赖安装和任务环境注入、受管 Skill service 生命周期、历史 revision 恢复 UI，以及抽样读取并校验 workspace blob 的演练。

但仍不能将 D-07、D-08、D-10 标为通过。原因已从“核心代码缺失”转为“真实部署环境与外部基础设施尚未完成破坏性验收”。当前合理状态是：**代码级数据保护主链已实现；生产级灾难恢复承诺仍需外部恢复设施、规模化传输和真实销毁演练证明。**

## 3. 尚未完成或仍需进一步优化

### P0-1：D-07/D-08 尚缺真实破坏性恢复证据

代码已能从控制面和对象存储重建 workspace、Skill cache 与 dependency environment，但本机未执行以下完整场景：

1. 使用新镜像创建全新 Runtime。
2. 删除旧 Runtime 容器和 Daemon state volume。
3. 在空节点恢复 workspace、Skill、Secret 和 Provider。
4. 运行真实任务，验证文件内容、权限、任务提交和 generation fencing。

这必须在允许执行容器销毁、且能访问集中 PostgreSQL/TOS 的指定测试环境完成。本工作站禁止使用 Jenkins，不能用本地 Jenkins 代替该验收。

### P0-2：D-10 仍缺 PostgreSQL/TOS 的物理恢复演练

应用内 drill 已能验证当前数据源中的 manifest、Skill artifact 和 workspace blob，但它仍不能证明：

- PostgreSQL PITR/备份能恢复到指定时间点；
- TOS versioning、误删除恢复和生命周期策略有效；
- 数据库 revision 与对象存储恢复点一致；
- 在隔离环境恢复后满足正式 RPO/RTO。

剩余工作属于 `../docker-helm.dofe.ai` 管理的共享基础设施和运维流程。AgentSpace 的 Dockerfile/Compose 不应新增 PostgreSQL、Redis 或 RabbitMQ。

### P0-3：真实项目规模仍受 inline bundle/capture 上限限制

当前工作目录捕获限制为 64 个文件、单文件 10 MiB、总量 25 MiB，并通过 JSON inline bundle 下发。该策略适合状态、检查点和中小型成果，但不适合大型代码库或二进制工程。

应升级为内容寻址的增量协议：manifest 先行、缺失 blob 按需下载、分块/并发传输、断点续传；大型 repository 优先采用 Git commit/object 与 workspace blob 的混合模型。超限必须继续 fail closed，不能恢复为静默截断。

### P0-4：稳定 employeeId 迁移尚未端到端完成

EAD 表已有不可变 `employee_id` 和外键，但部分查询、唯一约束、冲突处理及 `employee_skill_assignment` 等关联仍依赖 `employee_name`。员工改名和历史名称复用仍缺端到端迁移测试。

完成标准：所有持久化关系以 employeeId 为主；名称仅作为可变显示属性；重命名前后 workspace head、Skill assignment、artifact、binding generation、恢复历史保持同一员工身份。

### P1-1：恢复健康检查仍需真实 Provider/Secret/file smoke

恢复 phase 已验证 runtime 在线、心跳、mount 文件数量/路径和 Skill ready，但生产验收还应在新 Runtime 中执行：

- 读取恢复后的抽样文件并比对 digest；
- 使用已解析凭证执行最小 Provider 请求；
- 对声明的 CLI/MCP/service 运行实际 smoke；
- 确认敏感值未进入日志、bundle 文件或审计明文。

只有 smoke 全部通过后才能激活 provisional binding。

### P1-2：跨对象存储与数据库仍不是单一 ACID 事务

对象上传、artifact/revision 可见性和数据库提交无法形成一个跨系统事务。现有幂等键、pending 状态、commit journal 和 reconciliation 已显著缩小风险，但仍需故障注入覆盖每个边界：blob 上传后进程退出、artifact 发布后 revision 冲突、revision committed 后 completion 响应丢失、reconciliation 重复运行。

建议继续坚持“对象先写、数据库 CAS 提交、可见性最后切换、后台回收孤儿”的模型，不尝试伪造跨存储原子性。

### P1-3：持久 mount 与任务 workspace 的统一仍可优化

恢复 mount 目录目前主要作为恢复证据和 Daemon 持久副本；普通任务仍通过 input bundle/任务准备逻辑将 head 还原到 task 或 conversation workDir。两条路径都能读取同一 durable head，但会产生重复物化和额外磁盘占用。

后续可让受管 Runtime 的任务以只读基线 + 可写 overlay 使用 mount，任务结束只提交 overlay diff；在此之前必须保持当前逐任务 head 校验，不能仅信任本地持久目录。

### P1-4：生命周期、配额和 legal hold 仍缺产品闭环

retention、软删除和 orphan blob 回收已有数据结构/基础函数，但租户级配额、legal hold、恢复窗口、审计审批和定时 GC 尚未形成完整策略。GC 上线必须晚于真实备份恢复验收，并保证任何可达 revision、审计保留或 legal hold 对象不会被删除。

### P1-5：workspace mount operation 尚缺租约与崩溃回收

mount 已具备严格状态转换、start 重试幂等和内容级重试安全，但 operation 记录还没有 lease token/expiry。Daemon 在 claim 或 running 后永久退出时，恢复流程会持续等待。应参照 Skill installation operation 增加租约续期、过期重领和 attempt fencing；旧 attempt 的 complete/fail 必须被拒绝，避免两个 worker 同时写同一持久目录。

### P2-1：运维指标仍需接入外部监控

应用已有健康状态、Cron 响应、恢复记录、演练记录和 UI，但还需将 `workspace_head_age`、reconciliation backlog、restore duration、digest failure、binding conflict 和 drill success 接入统一指标/告警系统，并实现去重、升级和恢复通知。

### P2-2：测试隔离与测试环境能力仍需改善

数据库测试依赖本机 PostgreSQL，当前受限沙箱拒绝连接 `127.0.0.1:5432`；监听回环端口的 Provider proxy 测试也会被 `EPERM` 阻断。测试自身应进一步使用独立 workspace/schema，减少共享 `default` workspace 和单并发要求。破坏性恢复测试应在专用环境运行并保存 revision、artifact digest、恢复点和耗时证据。
