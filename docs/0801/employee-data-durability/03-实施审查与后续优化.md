# 员工数据持久化实施审查与后续优化

状态：Implementation Review（第七轮实施后）
审查日期：2026-08-03
审查基线：当前分支的 Domain、DB、Services、Daemon、Web、恢复编排及定向测试

## 1. 结论

本轮实施后，员工数据持久化已经从“控制面骨架”进入“主要代码路径闭环并具备隔离破坏性证据”阶段。以下旧结论已失效：工作目录只保存显式附件、workspace 只能通过 inline bundle 传输、mount 使用完即删除、Skill 依赖不真实安装、任务不消费依赖环境、员工关系仍依赖名称、恢复历史版本没有产品入口、D-10 只校验 manifest 元数据、retention/legal hold 仅有占位结构。

当前已具备：稳定 `employeeId` 全链关系、工作目录 diff/tombstone、完整 revision、双向内容寻址增量传输、对象存储 blob、任务启动 fail-closed 还原、持久 mount、mount/recovery worker 租约与 attempt fencing、恢复 head CAS/原子激活、绑定 generation fencing、提交 reconciliation、真实 Skill 依赖安装和任务环境注入、Secret 解密校验、Provider/CLI/MCP 恢复门禁、受管 Skill service 生命周期、历史 revision 内容校验/原子审计、员工级 retention/legal hold/容量告警，以及维护 Cron 中的受保护 GC。

D-07/D-08 的隔离 Docker 恢复路径已通过真实容器与 named volume 销毁演练；D-10 已通过测试 PostgreSQL custom archive 到 scratch DB 的实际恢复和真实 TOS scratch 对象删除/回灌。它们仍不能等同于指定环境完整控制面 E2E、PostgreSQL PITR/WAL replay 或 TOS versioning/provider undelete。当前合理状态是：**代码级数据保护主链与隔离破坏性恢复已实现并有证据；生产级灾难恢复承诺仍需指定环境重新绑定/任务执行和共享基础设施恢复点验收。**

## 3. 尚未完成或仍需进一步优化

### P0-1：D-07/D-08 已有隔离破坏性证据，仍缺指定环境完整 E2E

`scripts/employee-data-durability/run-docker-volume-recovery-drill.mjs` 已基于真实 Codex runtime 镜像执行以下隔离场景：删除旧容器后以不同 image ID 挂回原卷并零下载复用缓存；删除原状态卷后以空卷从只读 CAS 重建 workspace，并校验所有文件 SHA-256/size。所有任务专属容器、卷和镜像均已清理，证据见 [D-07/D-08 演练结果](./evidence/d07-d08-1785714998462-e0519d.json)。

仍未在指定测试环境执行以下完整场景：

1. 使用新镜像创建全新 Runtime。
2. 删除旧 Runtime 容器和 Daemon state volume。
3. 在空节点恢复 workspace、Skill、Secret 和 Provider。
4. 运行真实任务，验证文件内容、权限、任务提交和 generation fencing。

这必须在允许执行容器销毁、且能访问集中 PostgreSQL/TOS 的指定测试环境完成。本工作站禁止使用 Jenkins，不能用本地 Jenkins 代替该验收。

### P0-2：D-10 隔离实际恢复已通过，仍缺 PITR/versioning 验收

`scripts/employee-data-durability/run-postgres-tos-restore-drill.mjs` 已执行测试 PostgreSQL custom archive 到独立 scratch DB 的实际恢复，并对源/恢复库关键控制面计数做摘要比对；同时在真实 TOS scratch prefix 执行源对象备份、删除、从 backup key 回灌和 SHA-256/size 校验。scratch DB、dump 和 TOS 对象均已清理，证据见 [D-10 演练结果](./evidence/d10-1785715496648-4ff3fc.json)。

它仍不能证明：

- PostgreSQL PITR/备份能恢复到指定时间点；
- TOS versioning、误删除恢复和生命周期策略有效；
- 数据库 revision 与对象存储恢复点一致；
- 在隔离环境恢复后满足正式 RPO/RTO。

剩余工作属于 `../docker-helm.dofe.ai` 管理的共享基础设施和运维流程。AgentSpace 的 Dockerfile/Compose 不应新增 PostgreSQL、Redis 或 RabbitMQ。

### P0-3：大型 workspace 主链已增量化，仍需分块续传与性能验收

远程任务的 durable workspace 已不再把文件内容塞入 JSON：输入先下发内容寻址 manifest，Daemon 只下载本地 digest cache 缺失的 blob，并支持 HTTP Range；输出只回传 descriptor，随后逐文件校验 SHA-256/size 后上传。当前 fail-closed 上限为 100,000 文件、单文件 512 MiB、变更总量 20 GiB。64 文件/10 MiB/25 MiB 的 inline 捕获仍存在，但只服务旧兼容路径和小型 runtime-output，不再是远程 workspace 主链上限。

剩余优化是把单 blob 请求升级为可持久化分块 checkpoint、失败续传和有界并发，并为 20 GiB 级 workspace 建立吞吐、峰值内存和磁盘压力基准。大型 repository 仍可进一步采用 Git commit/object 与 workspace blob 的混合模型。超限必须继续 fail closed，不能恢复为静默截断。

### P1-1：恢复 smoke 主路径已闭环，仍缺指定环境的受管凭证与 service E2E

恢复 phase 已完成以下门禁：workspace head/mount 的 path、digest、size 与新鲜度校验；声明 Secret/config 的真实解密和非空校验；CLI `--version` preflight；存在 OpenAI/Anthropic API-key 环境时通过 stdin 注入 header 执行不计费 `/v1/models` 请求；对所有 ready MCP 连接创建并等待真实 verify operation。Claude/Codex 本地登录态最小推理和 AgentSpace 生产 MCP 客户端的公开端点 `initialize + tools/list` 已实测通过，证据见 [Provider/CLI/MCP smoke](./evidence/provider-cli-mcp-smoke-1785716591000-6cd4628.json)。

- 在指定环境由 runtime-provisioning 创建全新 Runtime，并使用其受管 Secret 完成 Provider 请求；
- 对 OAuth、文件登录态等无法映射 API key 的凭证形态增加 Provider 专用无副作用探针；
- 对绑定的 managed service 执行服务级健康请求，而不仅是 installation ready；
- 使用租户已有 MCP 连接跑恢复创建的 verify operation；当前数据库没有连接样本，不能把公开端点直连等同于完整恢复 E2E；
- 将敏感值不进入日志、bundle 或审计明文纳入指定环境日志扫描。

当前代码会在已有门禁全部通过后才激活 provisional binding；上述剩余项是提升不同凭证形态和 service 的验收强度，不应回退现有门禁。

### P1-2：跨对象存储与数据库仍不是单一 ACID 事务

对象上传、artifact/revision 可见性和数据库提交无法形成一个跨系统事务。现有幂等键、pending 状态、commit journal 和 reconciliation 已显著缩小风险，但仍需故障注入覆盖每个边界：blob 上传后进程退出、artifact 发布后 revision 冲突、revision committed 后 completion 响应丢失、reconciliation 重复运行。

建议继续坚持“对象先写、数据库 CAS 提交、可见性最后切换、后台回收孤儿”的模型，不尝试伪造跨存储原子性。

### P1-3：持久 mount 与任务 workspace 的统一仍可优化

恢复 mount 目录目前主要作为恢复证据和 Daemon 持久副本；普通任务仍通过 input bundle/任务准备逻辑将 head 还原到 task 或 conversation workDir。两条路径都能读取同一 durable head，但会产生重复物化和额外磁盘占用。

后续可让受管 Runtime 的任务以只读基线 + 可写 overlay 使用 mount，任务结束只提交 overlay diff；在此之前必须保持当前逐任务 head 校验，不能仅信任本地持久目录。

### P1-4：生命周期、配额和 legal hold 服务闭环已完成，仍缺治理 UI

员工级 soft-delete recovery window、orphan blob 保留期和 quota 已由 `retention_policy_json` 驱动；legal hold 有显式 active/released/expiry 状态和不可变审计；artifact/content blob 删除在数据库层再次检查 active hold；维护 Cron 已执行跨 workspace 生命周期清理并在任一阶段失败时返回 503。容量按 revision/artifact 引用的 digest 去重统计，超额产生 error alert。

剩余产品治理包括：管理员创建/释放 legal hold 的专用 UI、法务案件/工单引用、双人审批、权限矩阵和导出；revision 本身的长期保留/压缩策略；外部通知接收人和升级策略。未完成这些治理项前，不应提供绕过数据库保护的人工 GC 工具。

### P2-1：运维指标仍需接入外部监控

应用已有健康状态、Cron 失败 503、恢复/演练记录、数据保护 UI，以及 `workspace_head_age`、reconciliation backlog、restore duration、digest failure、binding conflict、去重容量、quota exceeded、active legal hold 等内部指标/告警。仍需接入统一外部监控与 paging，补齐告警去重、责任人升级、恢复通知、SLO 看板和演练超期告警。

### P2-2：测试隔离与测试环境能力仍需改善

数据库集成和破坏性脚本仍依赖共享测试基础设施，应继续使用明确的测试数据库安全门、任务专属 scratch DB/prefix、独立 workspace/schema 和自动清理。Provider/MCP live smoke 应为显式 opt-in，保存去敏版本、结果和耗时，不记录响应正文或 Secret。完整破坏性恢复仍必须在专用环境保存 revision、artifact digest、恢复点和 RPO/RTO 证据。
