状态：核心实施已完成，发布门禁 `NO-GO`

日期：2026-08-07

## 决策摘要

本方案采用“通用自动化引擎内核 + 受控首期能力”的路线。引擎以版本化 Workflow 和有向无环图为统一模型，当前代码基线已实现：

- 手动、定时和受控事件触发；
- AI 员工节点的串行执行；
- AI 员工节点的并行执行与 Join 汇聚；
- 人工审批节点；
- 有限重试、暂停/恢复、取消和失败传播；
- 每次运行的步骤状态、输入映射、产物引用、事件时间线和审计；
- 节点级结构化输出字段、严格下游引用和 256 KiB 输出上限；
- Workflow 级暂停/恢复、错过执行结果与 Trigger 原子推进；
- 任务产物 `prepare -> effects checkpoint -> promote -> finalize` 提交协议、跨 workspace 对账和执行器离线回收；
- 任务级消息/附件/AI 输出提及幂等，支持同一员工并行任务互不覆盖；
- Run 级并发上限、预计成本预算预检和 dispatch 前 readiness 复核。
- 已发布手动 Workflow 可从编辑页立即运行并进入 Run 详情；目标步骤展示固定负责人，并可选择站内状态或工作区频道通知。
- 草稿创建/更新写不可变审计，重试次数由服务端限制为 1-10；运行轮询按事件序号和请求代次防止旧响应覆盖新投影。

首期不开放任意脚本、循环、动态改图、跨 workspace 编排和自动选择员工。节点独立超时、实际成本归集/熔断、从此处继续、人工接管、模板 CRUD 和根任务专用投影明确列入二期，不能作为首期已实现能力宣传。

代码完成不等于可发布。隔离 PostgreSQL 集成、Playwright 五场景、真实负载/故障演练、用户可用性研究和环境签字仍未关闭，具体以 [07-规格实施覆盖矩阵.md](./07-规格实施覆盖矩阵.md) 和 [release-checklist.md](./release-checklist.md) 为准。

## 与现有 AgentSpace 的关系

现有 `/automations`、`/calendar` 和 `/task-board` 不再各自维护独立的任务语义，而是作为同一编排域的不同入口：任务看板强调“要完成什么”，日历强调“什么时候开始”，自动化中心强调“如何触发与协作”。三者最终创建或查看同一份 Workflow、Workflow Run 和 Node Run。

现有 `agent_task_queue`、AgentRouter session、daemon claim/complete、task execution event、approval 和 audit log 继续复用。编排引擎只负责图状态和依赖，不重复实现 Provider 运行时。

## 关键设计原则

1. **运行与步骤分离**：一个 Workflow Run 物化多个独立 Node Run，员工不争抢同一任务行；根任务专用投影在二期补齐。
2. **计划与运行分离**：已发布 Workflow 版本不可变；每次触发生成独立 Run，便于审计、重试和复现。
3. **产物引用优先**：步骤之间传递结构化摘要、Artifact 引用和显式字段，不把上一步全部日志无界塞入下一步上下文。
4. **事实事件驱动**：状态变化由数据库事务事件驱动，定时扫描只做兜底补偿；产物已提交但业务投影未完成时保留可重驱日志。
5. **人类保持控制**：高影响工具、外发动作和人工审批仍走现有治理中心。
6. **租户边界不变**：所有 Definition、Run、Artifact、队列和事件都以 workspace 为第一过滤条件。
