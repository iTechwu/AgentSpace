# Agent Team 编排方案

状态：设计稿，首期范围已确认

日期：2026-08-06

## 决策摘要

本方案采用“通用自动化引擎内核 + 受控首期能力”的路线。引擎以版本化 Workflow 和有向图为统一模型，首期只开放：

- 手动、定时和受控事件触发；
- AI 员工节点的串行执行；
- AI 员工节点的并行执行与 Join 汇聚；
- 人工审批节点；
- 节点级超时、有限重试、暂停、取消和失败转人工；
- 每次运行的步骤状态、产物引用、成本和审计。

首期不开放任意脚本、循环、动态改图、跨 workspace 编排和自动选择员工。这样既保留通用引擎的演进空间，又不把产品变成不可解释的低代码平台。

## 与现有 AgentSpace 的关系

现有 `/automations`、`/calendar` 和 `/task-board` 不再各自维护独立的任务语义，而是作为同一编排域的不同入口：任务看板强调“要完成什么”，日历强调“什么时候开始”，自动化中心强调“如何触发与协作”。三者最终创建或查看同一份 Workflow、Workflow Run 和 Node Run。

现有 `agent_task_queue`、AgentRouter session、daemon claim/complete、task execution event、approval 和 audit log 继续复用。编排引擎只负责图状态和依赖，不重复实现 Provider 运行时。

## 关键设计原则

1. **根任务与步骤分离**：一个协作任务有一个根任务，员工各自执行独立步骤，不争抢同一任务行。
2. **计划与运行分离**：已发布 Workflow 版本不可变；每次触发生成独立 Run，便于审计、重试和复现。
3. **产物引用优先**：步骤之间传递结构化摘要、Artifact 引用和显式字段，不把上一步全部日志无界塞入下一步上下文。
4. **事实事件驱动**：状态变化由数据库事务事件驱动，定时扫描只做兜底补偿。
5. **人类保持控制**：高影响工具、外发动作和人工审批仍走现有治理中心。
6. **租户边界不变**：所有 Definition、Run、Artifact、队列和事件都以 workspace 为第一过滤条件。

## 当前基线与假设

- 已存在数字员工、Runtime、AgentRouter、消息、任务看板、日历、自动化、审批和审计模块。
- 当前 `ScheduledTask` 与 `AutomationRule` 主要是 workspace state 配置，不能单独证明已有可靠调度器；本方案将其迁移到持久化编排模型。
- 用户研究尚未完成。本文把用户明确提出的两类需求和现有代码中的三个产品断点作为 Discovery 证据，发布前需用 5-8 名 workspace 管理员完成可用性验证。
