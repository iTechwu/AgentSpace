# AI 员工团队编排：产品设计文档

> 实施边界（2026-08-06）：首期核心能力已落地，逐项证据见 [07-规格实施覆盖矩阵.md](./07-规格实施覆盖矩阵.md)。节点超时、实际成本熔断、从此处继续/人工接管、模板 CRUD 和根任务专用投影为二期；数据库/E2E/真实容量/用户研究未关闭，当前不可发布。

## 1. 背景与问题

用户希望把“某个 AI 员工在某个时间点做什么”变成可观察、可复用、可治理的工作计划，并处理同一件事需要多个 AI 员工协同的情况。当前 AgentSpace 已有定时任务、自动化规则和任务看板，但这些入口的语义分散：定时任务只描述时间和单一执行者，自动化规则描述触发动作，任务看板描述结果，缺少一个可追踪的协作计划。

本需求不是增加一个 Cron 表单，而是把数字员工从“被单次调用”提升为“可被编排的团队成员”。产品必须同时回答：谁在什么时候做什么、依赖谁的结果、当前卡在哪一步、产物在哪里、下一步为何会启动、失败后由谁接手。

## 2. Discovery 证据与待验证假设

| 证据 | 结论 |
| --- | --- |
| 用户明确提出按时间给 AI 员工分配工作 | 定时触发是 P0，不应隐藏在聊天指令中 |
| 用户明确提出同一任务需要多个 AI 员工协同 | 协作图与步骤状态是核心对象，不是多个独立任务的偶然组合 |
| 代码中已有 `/automations`、`/calendar`、`/task-board`，且已有串行文档流程 | 需要统一入口和迁移适配，而不是再增加第四套任务系统 |

待验证假设：任务负责人更愿意先描述目标，再通过可视化步骤确认员工分工；并行步骤的默认合并方式应为“汇总员工读取上游摘要和产物引用”，而不是自动拼接全部日志。

## 3. 目标与非目标

### 目标

1. 让负责人在 5 分钟内创建一条可运行的协作计划。
2. 支持立即执行、一次性定时和重复定时三类首期入口。
3. 支持 `A → B`、`A → (B ∥ C) → D` 两种核心拓扑。
4. 每个员工步骤显示输入、输出、状态、耗时、已有成本事件、重试和审批原因。
5. 失败可定位到节点和运行实例，并能安全重试、暂停/恢复或取消。
6. 与现有员工权限、Runtime 绑定、审批、审计和 Artifact 体系保持一致。

### 非目标

- 首期不提供任意代码节点、表达式脚本、循环和运行中改图。
- 不允许模型自主改变已发布拓扑或未经授权替换员工。
- 不跨 workspace 共享运行上下文，不把密码、Token 或原始 Provider 日志作为步骤输入。
- 不在应用 Docker Compose 中新增 PostgreSQL、Redis 或 RabbitMQ；这些依赖仍由共享基础设施提供。

## 4. 核心用户与 Jobs-to-be-done

| Persona | 目标 | 关键痛点 |
| --- | --- | --- |
| 工作区管理员 | 建立可复用的团队自动化并控制风险 | 不知道谁可以创建、发布和修改员工协作 |
| 任务负责人 | 在指定时间让多个员工完成完整交付 | 需要手动复制上下文、催进度和交接产物 |
| AI 员工 owner | 确保员工被正确调用且不越权 | 运行环境、Skill、预算和外发权限容易被忽略 |
| 审批人 | 在关键动作前快速做决定 | 需要看到步骤上下文、影响范围和可回滚选项 |
| 执行观察者 | 追踪结果并复盘 | 单个聊天记录无法解释整个协作链路 |

## 5. 领域术语

| 术语 | 定义 |
| --- | --- |
| Workflow | 可复用的编排定义，包含触发器、节点、连线和治理策略 |
| Workflow Version | 已发布的不可变版本；运行实例绑定具体版本 |
| Node | 一个可执行或控制流程的步骤 |
| AI Task Node | 绑定一个具体数字员工、输入模板、输出契约和 Runtime 策略的节点 |
| Join Node | 等待多个上游完成，再把结构化结果交给下游 |
| Workflow Run | 一次手动、定时或事件触发的执行实例 |
| Node Run | Run 中单个节点的一次执行尝试 |
| Artifact | 文件、文档、表格或结构化结果的持久化引用 |

## 6. 首期能力范围

### 触发器

- 手动运行：从任务看板、Workflow 详情或运行历史触发。
- 定时运行：时区明确的一次性、每日、每周和受控 Cron。
- 受控事件：任务完成、文档更新、消息命中等已有事件；每条事件必须有去重键。

### 节点

- AI 员工任务：指定员工、目标、输入映射、输出字段、所需 Skill、协作频道、预算估算和重试策略。
- 并行分组：将一个上游拆为多个可同时运行的 AI 员工节点。
- Join 汇聚：等待策略为“全部成功”或“允许部分成功”；向下游暴露结果清单。
- 人工审批：复用现有 approval 类型，批准后继续，拒绝则终止或走人工处理分支。
- 开始/结束：由引擎生成，不作为用户可自由配置的业务节点。

### 运行控制

- 节点状态：待运行、就绪、排队、运行中、等待审批、重试中、成功、失败、取消、跳过。
- Run 状态：草稿、等待触发、运行中、等待审批、成功、部分成功、失败、取消、暂停。
- 节点级有限重试和退避；首期失败后支持“重试该节点”，“从该节点继续”与人工接管属于二期。
- 运行级暂停、取消、重新运行；不允许在运行中修改已绑定的版本。

## 7. 关键用户流程

### 创建与发布

1. 用户从任务看板点击“编排任务”，或从日历点击“新建定时”；进入同一向导。
2. 输入目标、工作区、频道、时区和触发方式。
3. 在画布添加员工节点，配置 A→B、并行分组和汇总员工 D。
4. 运行预检：员工是否活跃、Runtime 是否就绪、Skill 是否满足、权限和预算是否可用。
5. 发布生成不可变版本；若为手动触发可立即运行，否则进入调度队列。

### 运行与交付

1. Scheduler 领取到期触发器，创建 Run 和首批 Node Run。
2. Dispatch 将每个可执行 AI Task Node 投递到现有 `agent_task_queue`。
3. 员工完成后写入结果摘要、Artifact 引用和执行事件。
4. Join 检查上游完成策略；满足后激活下游汇总员工。
5. 汇总结果写回根任务、关联频道和产物区；高影响动作进入审批。

### 错误状态

- 预检失败：阻止发布，显示具体员工、Runtime、Skill 或权限问题。
- 单节点失败：保留已完成上游，允许节点重试；超过次数进入人工处理。
- Join 部分失败：按策略显示“部分成功”，不得静默拼接不完整结果。
- 定时错过：显示错过原因，按 Workflow 策略选择补跑、跳过或暂停。
- 版本冲突：旧运行继续绑定旧版本，新修改只能生成新版本。
- 结果提交中：禁止取消或重复宣布成功；系统在持久化产物并完成业务投影后自动收敛。
- 副作用不确定：隐藏自动重试，要求负责人先核对外部系统并完成人工补偿。
- 并行消息冲突：同一员工的等待、成功或失败消息按任务实例隔离，不能互相覆盖。

## 8. 权限与治理产品规则

1. 查看 Workflow 需要 workspace 访问权；编辑、发布和删除沿用工作区管理权限模型。
2. 运行前逐节点检查员工可用性、频道访问、Runtime grant、Skill readiness 和外部资源权限。
3. 任何外发、写入外部数据、敏感工具或预算超阈值动作必须进入审批节点或现有 runtime approval。
4. 运行详情默认展示摘要和脱敏事件；秘密只在受控 Runner 内短暂可用。
5. 每次创建、修改、发布、暂停、运行、重试、取消和审批都写审计事件。

## 9. 成功指标与验收目标

| 指标 | 目标 |
| --- | --- |
| 首次创建并发布完成率 | ≥85% |
| 从开始创建到发布的中位时间 | ≤5 分钟 |
| 核心运行成功率（依赖就绪前提） | ≥95% |
| 调度延迟 P95 | 到期后 ≤60 秒 |
| 节点状态可解释率 | 100% 的终态有原因和事件 |
| 失败恢复 | 90% 的可重试失败可由负责人自助恢复 |
| 可用性 | 5-8 人测试 SUS ≥68，核心任务完成率 ≥85% |

## 10. 设计原则与决策

- **目标先于拓扑**：先说业务结果，再配置员工步骤。
- **显式优于猜测**：员工、顺序、Join 策略和失败策略不得由模型隐式决定。
- **观察优先**：运行画布显示事实状态，不用模型文本冒充系统状态。
- **渐进暴露**：首期隐藏高级条件、循环和脚本，保留后续扩展插槽。
- **可恢复优于重跑全部**：节点级重试和版本化运行减少重复成本。
