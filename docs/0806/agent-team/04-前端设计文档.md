# AI 员工团队编排：前端设计文档

> 实施边界（2026-08-06）：实际 Web 采用 Server Actions 完成 mutation，Route Handler 用于事件分页、内部事件入口和恢复 Cron。画布首期实现添加/连接、并行助手、列表替代视图和节点配置；节点搜索、undo/redo、复制节点、离线草稿、“从此处继续/接管”为二期。


## 2. 路由与数据加载

| 路由 | 加载数据 | 主要动作 |
| --- | --- | --- |
| `/automations` | Workflow 摘要、Trigger（含 suspended/paused）与运行摘要、过滤项 | 新建、搜索、状态筛选、查看计划/运行 |
| `/automations/new` | 员工、频道、Runtime readiness | 保存草稿、预检、发布 |
| `/automations/:id` | 草稿/已发布版本、节点、Trigger、权限 | 编辑草稿、发布新版本、手动运行 |
| `/automations/runs/:runId` | Run 摘要、节点 projection、事件分页 | 暂停、恢复、取消、重试失败节点 |
| `/calendar` | Trigger projection | 新建并跳到向导第 2 步 |
| `/task-board` | 现有任务视图 + Workflow 深链 | 新建并跳到向导第 1 步、查看 Run |

首屏数据由 Server Component 提供；客户端只管理画布草稿、筛选、展开状态和乐观反馈。运行时间线通过现有事件/失效通知模式定时补偿或 SSE；断线时显示 `reconnecting`，不在本地猜测状态。

Builder 的服务端首屏同时提供 Definition owner 展示名和 workspace 频道列表。客户端只提交可编辑的 `channelName`，owner 不进入更新 payload；新建和更新均由 Server Action 从当前 workspace context 取 actor。频道通知模式不自动选择首个频道，用户必须再次明确选择。已发布手动 Workflow 通过 `runWorkflowAction` 创建 Run，成功后跳转 `/automations/runs/:runId`；按钮依据已发布 Trigger，而不是尚未发布的表单值。

运行页合并 projection 时必须保持单调：更小 `currentSequence` 的响应永不覆盖当前状态；同一 sequence 下，较早请求的迟到响应不得覆盖较晚请求，终态也不得回退为非终态。事件列表仍以 sequence 去重并在发现缺口时从最后连续序号补拉。

## 3. 前端类型与状态

核心客户端类型：

```ts
type WorkflowNodeDraft = {
  id: string;
  type: "employee_task" | "parallel_group" | "join" | "approval";
  position: { x: number; y: number };
  config: Record<string, unknown>;
};

type WorkflowDraftState = {
  workflowId?: string;
  versionId?: string;
  name: string;
  goal: string;
  trigger: TriggerDraft;
  nodes: WorkflowNodeDraft[];
  edges: Array<{ id: string; source: string; target: string }>;
  governance: GovernanceDraft;
  dirty: boolean;
  preflight?: PreflightResult;
};
```

使用 `useReducer` 管理草稿，所有 reducer 事件必须纯函数：`addNode`、`removeNode`、`connectNodes`、`updateNodeConfig`、`setTrigger`、`applyTemplate`、`markPreflight`。服务端返回的 canonical graph 作为唯一保存结果；客户端不负责生成版本号或运行状态。预览中的“发布版本”必须来自不可变 `WorkflowVersion.versionNumber`；`Definition.draftVersion` 仅显示为“草稿修订”，用于乐观并发控制，二者不得混用。

## 4. Server Actions 与查询契约

沿用仓库已有 Server Action 认证方式，动作建议为：

- `createWorkflowDraftAction`
- `updateWorkflowDraftAction`
- `validateWorkflowAction`
- `publishWorkflowAction`
- `runWorkflowAction`
- `controlWorkflowRunAction`：`pause|resume|cancel|retry_node`

首期已实现上述创建、更新、验证、发布、运行和控制 Action。每个 Action 返回 `{ ok, data?, error?, invalidation? }`；错误带稳定 `code` 和可定位字段。所有 Action 都重新读取 workspace context 和权限，不接受客户端的 owner 或员工授权作为可信结论。Run 投影额外返回服务端计算的 `canControl`，普通观察成员不渲染暂停、恢复、取消和重试入口；Action 仍执行独立授权，不能把 UI 隐藏当作安全边界。

## 5. 画布实现约束

画布业务节点、边和布局数据映射到自己的 `WorkflowNodeDraft`，不把展示组件内部状态落库。首期以受控添加、连接、并行助手和列表替代视图保证可操作性，后续可在不改变 canonical graph 契约的前提下引入成熟节点编辑器。

画布必须提供：

- 列表视图替代方案；
- 连接线方向、错误边高亮和孤立节点提示；
- 删除确认和稳定布局；
- 发布前必须在线执行服务端预检。

节点搜索、员工 readiness 过滤、undo/redo、复制节点和离线草稿属于二期交互增强。

## 6. 前端校验与错误映射

客户端做即时结构校验：名称、至少一个 AI Task Node、无环、无孤立节点、节点字段完整、并行组有 Join。服务端做最终校验：稳定员工 ID、访问权限、Runtime/Skill、频道、预算、版本冲突和策略。两者错误码统一，避免“前端可发布、后端才报未知错误”。

错误展示策略：

| 错误 | 展示位置 | 恢复动作 |
| --- | --- | --- |
| 图不完整 | 画布顶部 + 节点/边 | 定位第一个问题 |
| 员工未就绪 | 节点配置面板 | 打开员工详情或替换为已授权员工 |
| 版本过期 | 发布栏 | 载入最新草稿并显示差异 |
| 预算超限 | 治理步骤 | 降低并发/重试或申请额度 |
| 运行失败 | Run 节点卡片 | 首期重试失败节点；从此处继续/接管为二期 |
| 输出字段无效/过大 | 节点配置或 Run 节点卡片 | 补齐声明字段，或改用 Artifact 引用并缩小摘要 |
| 副作用不确定 | Run 节点卡片 | 显示稳定错误说明，不展示“重试步骤”，引导人工核对与补偿 |
| 结果正在提交 | Run/频道任务 | 禁止取消或停止；轮询服务端，恢复后显示最终投影 |
| 事件断线 | 时间线顶部 | 重连并从 sequence 补偿 |

## 7. 测试策略

- `workflow-validation.test.ts`：DAG、Join、孤立节点、重复连接和字段校验。
- `workflow-builder-client.test.tsx`：创建、并行组、删除、预检阻塞、键盘操作。
- `workflow-run-client.test.tsx`：状态投影、断线、重试、取消和部分成功。
- Server Action 测试：权限隔离、版本冲突、错误码和失效事件。
- Playwright：完整创建流程、从日历进入、从看板进入、移动端窄屏和审批恢复。

测试遵守仓库资源限制：单文件 Jest/Vitest 使用受限 worker；不得运行无约束的根测试。
