# 0815 规格实现一致性复审

## 1. 审查范围与结论

审查对象为 `dev` 分支 `8a990c2a` 及其之前的 0815 优化提交，重点复核
`docs/0815/04`、`05`、`06`、`07`、`08` 与当前 Skill rollout、workflow 编排实现。

结论：**代码主链路已明显改善，但 0815 仍不能作为“文档与实现完全一致”的基线**。
当前主要风险已从最初的 placement/审批绕过，转移为规格版本冲突、失败恢复语义、
能力过滤和测试证据不足。

## 2. 发现

### P1：验收结论相互矛盾，无法作为发布依据

`docs/0815/07-验收审查与差距.md:3-4` 仍写“部分完成，不建议完整验收”，
但 `:14`、`:26`、`:68` 又写 P1/P2/S 全部解决；`:95-101` 再次保留旧的
“不满足完整验收”结论。该文件把历史审查记录和最终状态混在同一结论区，
会导致评审、发布和回滚判断不一致。

建议：将 07 重写成“历史发现（只读）+ 当前状态表 + 未闭环风险 + 证据链接”四段，
只保留一个最终结论；每个已解决项必须链接到提交、测试文件和运行命令。

### P1（已完成）：`SkillRolloutPlan` 契约与落地 API 已显式关联

纯 planner 仍返回内容寻址的 `SkillRolloutPlan`，但当前
`packages/services/src/skills/rollout.ts` 新增 `SkillRolloutPersistedPlan`，并由
`packages/services/src/skills/rollout-dispatch.ts:13-26` 在 dispatch result 中返回
`planId + planDigest + plan` 三者绑定的对象；回归测试已验证 id/digest 一致。
这明确了 planner（纯计算）与持久化审批记录（带 id）的边界。

仍需同步 0815 的历史契约文字，建议：

1. planner 保持纯函数，不承诺数据库 id；
2. 持久化 dispatch 使用 `SkillRolloutPersistedPlan` 承载 `planId`。

### P1：`all-compatible` 只过滤 online，未完成能力选择

`packages/services/src/skills/rollout.ts:250-253` 的 `all-compatible` 查询仅按
`status = 'online'` 返回 Runtime。`docs/0815/04:81` 和 `05:220` 明确要求按 GPU、
出网等能力过滤；当前实现仍可能把需要特定能力的 Skill 下发到不兼容 Runtime。

建议：把 Skill manifest 的 capability/egress 要求编译成可查询的 Runtime capability
谓词，先做 fail-closed 过滤，再把过滤原因写入 plan risk/diagnostic；补充“在线但无 GPU”、
“在线但无出网批准”和“全部不兼容”三类测试。

### P1（已部分完成）：批量派发失败会返回可恢复上下文，但仍缺少持久化 reconcile 状态机

`packages/services/src/skills/rollout-dispatch.ts` 现已在子安装创建失败或 finalize 返回
false 时抛出 `SkillRolloutDispatchError`，携带 `planId`、`planDigest` 和已创建子安装列表；
调用方可以据此定位未消费计划并执行后续恢复。此前“失败被当作成功/丢失 plan id”的问题已消除。

剩余建议：把 dispatch 结果持久化为每项状态（pending/created/failed），采用可重入的
reconcile 任务；finalize 改为“所有必需项达到 ready 或明确失败终态”后原子消费，
失败时保留可查询的错误码和下一步动作。补充中途第 N 项失败、重复 reconcile、并发
 reconcile 三个测试。

### P2：审批幂等决策已变更，但测试矩阵仍引用旧方案

`docs/0815/04:37` 和 `08:3-5` 已决定“非唯一 + 每次审批新行 + consumedAt 防重放”，
但 `docs/0815/05:225` 仍要求 `UNIQUE(workspace_id, plan_digest)`，T14 也仍断言重复
创建返回已有记录。当前 DB 实现 `packages/db/src/skill-rollout-plans.ts:28-30`
明确允许同 digest 新建记录。

建议：把 T14 改为“同 digest 可重新审批且历史可追溯；最新未消费计划查询稳定”，并在
07/08 中记录该设计取舍的生效版本，避免后续开发者按旧测试恢复 UNIQUE。

### P2（已部分完成）：planDigest 已绑定闭包父节点

当前 `packages/services/src/skills/rollout.ts:425-434` 已将
`parentArtifactDigest` 纳入 canonical digest，并由 rollout 回归测试验证父节点变化会使
摘要失效。这补齐了 placement 输入的反篡改边界；但安装校验仍未把每个 artifact 的允许
Runtime 集合持久化为独立字段，跨 Runtime 失败恢复仍按 P1 项处理。

### P2（已完成）：iteration_group 运行时注释与质量门输出契约已同步

`packages/domain/src/workflows.ts:276-283` 已明确说明 coordinator 会消费
`__iterationGate`，与 `packages/services/src/workflows/coordinator.ts:40-119` 的
收敛后跳过剩余轮次和自动批准实现一致。质量门配置现在显式声明
`qualityReportField`，编译器会将其写入 `__iterationGate`；coordinator 只有在
`blockingField` 为整数 0 且报告摘要为非空字符串时才会提前收敛，缺失或非法输出会
fail-closed。对应回归测试位于
`packages/services/src/workflows/coordinator.test.ts` 与
`packages/services/src/workflows/novel-production-template.test.ts`。

仍需补充质量报告内容的完整 schema/版本解析和权限审计断言，避免未经授权的报告摘要
被复用或跨 Workspace 使用。

## 3. 证据缺口

现有 rollout 测试覆盖基本闭包、审批消费和单 Runtime placement，但尚未形成与 05 T06、
T09、T12、T14、T19 一一对应的可追溯矩阵。0816 阶段应要求每个验收项记录：测试文件、
命令、结果、失败时的错误码和对应提交。
