## 1. 审查范围与判定口径

本次覆盖以下目录：

- `docs/0801/mcp-extension`
- `docs/0801/skill-install`
- `docs/0801/employee-data-durability`
- `docs/0801/test-logs`
- `docs/0803/mcp-egress-proxy`

判定遵循四个层级：

1. **已实现并验证**：生产调用路径已有代码，相关自动化测试通过，并已有与目标环境相符的验收证据。
2. **代码已实现、待环境验收**：实现和定向测试存在，但尚无真实 Linux managed node、真实 Provider/CLI、真实共享基础设施或破坏性恢复证据。
3. **部分实现**：只有控制面、协议、UI 或单一执行路径完成，仍有可绕过、缺失消费链或缺失运营闭环。
4. **尚未实现**：文档中已明确设计，但当前代码、UI 或运维能力中不存在完整入口。

本审查只把已提交到上述基线、且通过对应测试或验收的能力视为已交付。代码存在但测试失败，或只有测试模板而没有真实环境证据时，不视为关闭缺口。

## 3. P0：发布前必须关闭

### P0-1：修复服务层测试发现范围，并处理当前 Skill storage 失败

`packages/services/package.json` 仍使用手写测试白名单，未包含 `src/skills/skills-storage.test.ts` 和 `src/mcp-center/*.test.ts`。因此根 `turbo run test --concurrency=2` 可以在真实相关测试失败时保持绿色。

本次定向执行结果：

- MCP egress policy：15/15 通过；
- MCP egress proxy：17/17 通过；
- daemon MCP client/gateway：17/17 通过；
- Skill storage：12/15 通过，仍有 3 个失败。

当前失败集中在员工 Skill assignment 镜像和预置 `financial-analysis-agent` 模板加载。必须先判断这是稳定 `employeeId` 迁移后的断言过期、fixture 缺失，还是实际数据回归；在结论明确前不能把 Skill storage 视为通过。

完成标准：

- 服务包测试改为完整发现，或维护一份由自动化校验“不遗漏测试文件”的显式清单；
- `skills-storage.test.ts` 全部通过；
- 根测试运行能够真实捕获 MCP Center 与 Skill storage 的失败。

### P0-2：首次 Skill 安装缺少高风险能力逐项审批

当前五步安装向导会展示依赖、MCP、服务和脚本，但提交门禁只检查 `unresolvedRequired`。首次安装接口没有接收并消费风险决定、策略版本和不可变审批记录。管理员仍可直接创建带 executable、网络或高风险 MCP 工具的 installation。

完成标准：

- 脚本、网络、高风险 MCP 工具和写能力分别产生明确风险项；
- 审批绑定 `artifactDigest + releaseLockDigest + policyVersion + riskDecisionDigest`；
- 安装提交事务原子消费审批，重复、过期或不匹配审批全部拒绝；
- UI 不以一个总开关代替逐项授权，并提供审计查询入口。

### P0-3：完成 MCP 真实任务与网络旁路 E2E

当前代码已经关闭上一轮审查中的两个实现缺口：policy canonical digest 不再自引用，policy ID 已覆盖路径、认证与资源上限；任务 session 也已按 approved tool 逐工具签发 lease。`MCP_EGRESS_ENFORCE` 在 managed-node Compose 中已默认开启，client 对缺少 lease 的 enforce 场景也会 fail-closed。

仍缺的是生产证明，而不是主要代码骨架：

- 真实 Claude 任务调用 MCP，验证工具结果、审计 outbox、撤销中断和 daemon 重启；
- 真实 Codex 版本验证 `--ignore-user-config` 与 `mcp_servers` 整表替换，确认 project/cloud 配置不能恢复额外 MCP；
- Provider 直连批准 host、raw IP、IPv6、公共代理、DoH 和 metadata/private IP 全部失败；
- proxy 退出、policy push 失败、lease 缺失时任务失败且无直连回退；
- connection disable、release yank 和 policy revoke 在规定 SLA 内阻断新调用。

在这些证据完成前，MCP Extension 应继续使用“已验证/内部实验”措辞，不应承诺正式任务可调用。

### P0-4：完成真实 Linux Skill Runner 与依赖消费 E2E

Runner、依赖安装和任务环境注入已经有代码与单元测试，但尚未在生产同构 Linux managed node 上产生放行证据。

完成标准：

- Node/Python/Bash entrypoint 使用 digest-pinned 本地镜像执行；
- npm `require`、Node `import`、Python `import` 和版本/ABI smoke 使用真实安装器产物通过；
- 删除 Runner image、cache、sentinel、dependency metadata 或篡改 entrypoint 后 fail-closed；
- 网络、Provider HOME/credential、Docker socket 和 workspace 写入全部拒绝；
- timeout、输出超限和 broker 关闭后无残留容器、socket、配置或私有输出。

### P0-5：完成指定环境全控制面恢复与共享基础设施灾备验收

现有 D-07/D-08 证明了隔离容器和 named volume 销毁恢复，D-10 证明了 PostgreSQL custom archive 的 scratch restore 和 TOS scratch object 回灌。它们不能证明完整控制面恢复、PITR/WAL replay、TOS versioning/provider undelete 或正式 RPO/RTO。

现有 `run-designated-e2e-checklist.ts` 和 `run-pitr-tos-versioning-drill.ts` 只是证据模板，不会自动执行销毁、重建、PITR 或对象 undelete。剩余验收必须在指定环境或共享基础设施仓库中完成，不能在本工作站用 Jenkins 代替。

完成标准：

- 销毁 Runtime 容器和 daemon state volume 后，在空节点创建新 Runtime；
- 恢复 workspace、Skill/release lock、Secret、Provider、MCP 和 managed service；
- 运行真实任务并推进新 workspace head，旧 generation/attempt 写入被拒绝；
- PostgreSQL 恢复到指定 LSN/时间点，TOS 从版本或 provider undelete 恢复；
- 数据库 revision 与对象存储恢复点一致，实测 RPO/RTO 达标并保存去敏证据。

## 4. P1：主链完成后继续补齐

### P1-1：MCP proxy 生产信任与运营模型

当前 proxy 仍使用共享 HMAC 和进程内 policy/JTI 状态。生产化还需要：

- 控制面私钥签名、proxy 公钥验签，proxy 不持有签名能力；
- 多副本共享且原子的 JTI replay guard；
- policy/revoke feed 的持久重放、断线恢复和可观测延迟；
- request/reject/latency/revoke 指标、告警和灰度回滚；
- admin policy push token 的轮换、最小权限和审计。

### P1-2：MCP 产品范围补齐

以下目标能力仍未完成：

- 受管 stdio MCP 的独立服务容器、固定镜像 digest、私网 bridge 和短期凭据；
- OAuth token broker 与 proxy 一次性注入；
- 工作区私有目录和私有服务审核；
- OpenCode、OpenClaw、Hermes 等 Provider adapter；
- 管理员可理解的 Codex 实验开关、隔离说明和失败诊断。

### P1-3：Skill 安装与运维体验闭环

仍需实现：

- 服务型 Skill 在向导中选择“创建受管服务”或“绑定已有服务”；
- 本地目录/目录上传/受控服务器目录导入的管理员入口及审计；
- Skill Runner invocation 持久审计，记录 workspace、task、installation、artifact、entrypoint、actor、结果码与安全摘要；
- 独立升级审批收件箱、逐项 semantic diff、service 运维页、服务器端草稿和诊断包；
- 私有 Git 凭证引用、轮换与审计，registry 定时更新检查与通知。

### P1-4：依赖与制品可重现性

真实安装主链已存在，但仍应补齐：

- npm/pip/uv integrity 锁和下载产物摘要；
- 离线或 content-addressed dependency cache；
- system dependency catalog resolver；
- base64 task bundle 向 content-addressed 分块、缓存和断点续传迁移；
- legacy backfill、orphan artifact/env GC 和节点磁盘水位治理。

### P1-5：员工数据一致性与规模验证

继续补齐以下故障注入和性能证据：

- blob 上传后进程退出；
- artifact 发布后 revision CAS 冲突；
- revision committed 后 completion 响应丢失；
- reconciliation 重复执行与跨节点竞争；
- 真实 TOS/弱网下 20 GiB workspace Range 续传和并发上传；
- 持久 mount 的只读基线 + 可写 overlay，减少任务重复物化和磁盘占用。

### P1-6：数据治理与告警运营

legal hold、配额和外部 pager 的代码主链已存在，但仍需：

- 法务案件/工单引用、细粒度权限矩阵和导出能力；
- revision 长期保留、压缩和删除证明；
- 真实 pager 接收端的去重、升级、恢复通知和演练超期告警；
- workspace head age、恢复时长、digest failure、binding conflict、容量和 RPO/RTO 的 SLO 看板。

## 5. 文档自身需要优化

### 5.1 MCP 状态口径互相冲突

`docs/0803/mcp-egress-proxy` 多处写“Phase 0/1/2 已完成”，但发布门禁仍有公钥验签、共享 JTI、完整容器探针、进程隔离和撤销 SLA 未完成。`docs/0801/mcp-extension` 又仍写 daemon 未生成/投递 policy 与 lease、managed-node 未调用 reconciler，这已经被当前代码取代。

建议统一为：

> Phase 2 代码主链已接通；生产 enforce、信任模型和真实旁路验收未完成。

### 5.2 Skill 文档混杂历史现状与当前现状

部分计划正文仍保留“依赖未安装”“daemon 未消费 proxy”等历史问题，而 README 又把它们列为当前阻断。历史说明可以保留，但必须明确标记“已被哪次提交/复审取代”，当前缺口只由一个汇总矩阵维护。

### 5.3 数据耐久性 README 有过期状态

README 顶部仍将分块续传、legal hold UI 和外部 paging 写为待验收，后续审查文档已经说明这些代码主链完成。应区分“代码完成”和“指定环境验收未完成”，避免把实现缺口与环境证据混成同一状态。

### 5.4 测试日志缺少 0803 增量

`docs/0801/test-logs` 只记录 0801 的构建和 sandbox 限制，没有覆盖本轮 egress、Skill Runner、数据恢复及当前 Skill storage 失败。建议新增后续索引，至少记录：commit、命令、worker 限制、通过/失败数、环境阻断、证据文件和未运行原因。

## 6. 建议实施顺序

1. 修复测试发现范围并处理 Skill storage 3 个失败，恢复可信的根测试门禁。
2. 完成首次 Skill 安装的高风险逐项审批和 Runner invocation 审计。
3. 在现有 egress fail-closed 代码基础上执行真实 MCP/Provider/网络旁路 E2E。
4. 在 Linux managed node 执行 Runner 与真实 npm/Python 依赖消费门禁。
5. 在指定环境完成全控制面恢复、PITR/WAL 和 TOS versioning/undelete。
6. 再推进 managed stdio/OAuth、服务运维 UI、私有来源、制品缓存、治理与 SLO。

只有第 1 至第 5 项均有可复核证据后，才适合把整体状态从“核心链路已实现、生产门禁待验收”提升为生产可用。
